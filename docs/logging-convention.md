# Logging Convention

로그 형식·레벨·출력 규칙 — 로그를 새로 쓰거나 고칠 때 모두 이 규칙을 따른다.

## 출력

- 콘솔은 사람이 읽는 텍스트, 파일은 ELK 수집용 ECS JSON이다. 두 출력은 같은 이벤트를 담고 형태만 다르다.
- 파일은 Logstash 가동 여부와 무관하게 쌓인다 — 앱은 파일에만 쓰고, 수집기가 파일을 읽어 간다.

콘솔 한 줄의 구성:

```
2026-09-26T14:03:12.345+09:00  INFO 48213 --- [running-service] [nio-8080-exec-3] [3f2c9a1e] [9b41c7d2] c.r.r.a.running.command.start.StartRunningRoomHandler : [러닝] 러닝 시작 - roomId=12
└ 시간 ──────────────────────┘ └레벨┘ └PID┘ 구분  └ 애플리케이션 ─┘ └ 스레드 ──────┘ └requestId┘ └userId─┘ └ 클래스 ─────────────────────────────────────────────┘   └ 메시지 ─────────────────────┘
```

| 항목 | 콘솔 | 파일(ECS JSON) |
|---|---|---|
| 시간 | `2026-09-26T14:03:12.345+09:00` | `@timestamp` |
| 레벨 | `INFO` | `log.level` |
| 프로세스 ID | `48213` | `process.pid` |
| 애플리케이션 | `[running-service]` | `service.name` |
| 스레드 | `[nio-8080-exec-3]` | `process.thread.name` |
| 요청 ID | 앞 8자리 `[3f2c9a1e]` | `requestId` — 36자 전체 |
| 사용자 ID | 뒤 8자리 `[9b41c7d2]`, 인증 전 요청은 `[-]` | `userId` — 36자 전체, 인증 전 요청은 없음 |
| 클래스 | 축약 패키지 + 클래스명 | `log.logger` — 전체 이름 |
| 메시지 | 본문 | `message` |
| 예외 | 메시지 아래 스택트레이스 | `error.type` · `error.message` · `error.stack_trace` |

## 요청 ID

- HTTP 요청마다 UUIDv4(`UUID.randomUUID()`)를 하나 발급해 MDC `requestId`에 넣는다. 요청이 끝나면 제거한다.
- 발급·MDC 키·태그 같은 로그 추적 코드는 `observability/logging/`에 둔다. 참조 규칙은 [architecture.md](architecture.md)의 의존 방향을 따른다.
- 메시지에 requestId를 직접 쓰지 않는다 — 콘솔 패턴과 JSON 필드가 자동으로 붙인다.
- 추적은 식별자로 문제의 줄을 찾고(`userId`, `roomId`), 그 줄의 requestId로 요청 흐름 전체를 모아 보는 순서로 한다.

## 사용자 ID

- access token으로 인증된 HTTP 요청이면 토큰의 userId(`sub`)를 MDC `userId`에 넣는다. 요청이 끝나면 제거한다. 보안 필터 체인 뒤에 실행해야 인증 결과를 읽을 수 있다.
- 인증된 요청의 모든 줄(중앙 예외 핸들러의 ERROR 포함)에 자동으로 붙으므로, 요청자의 userId를 메시지에 직접 쓰지 않는다.
- 메시지의 `userId=`는 MDC에 userId가 없는 곳에서만 쓴다 — 인증 전 요청(회원가입·로그인·토큰 재발급·소셜 로그인)이 결과로 사용자를 알게 된 경우다.
- 인증된 요청에서 요청자가 아닌 사용자를 가리키면 `userId`가 아닌 이름(`targetUserId`)을 쓴다. 같은 이름이면 수집 단계에서 MDC 필드와 충돌한다.
- 콘솔은 뒤 8자리를 보인다. userId는 UUIDv7이라 앞자리가 가입 시각이어서, 비슷한 때 가입한 사용자끼리 앞 8자리가 같다.

## 메시지 형식

```
[도메인] {동작} {결과}: {원인} - key=value, key=value
```

- `: {원인}`은 결과가 실패·건너뜀일 때만 붙인다.
- `- key=value` 부분이 없으면 생략한다.

```
[인증] 로그인 성공 - userId=0192f3a4-...
[인증] 로그인 실패: 비밀번호 불일치 - userId=0192f3a4-...
[매칭] 신청 건너뜀: 이미 대기열에 있음 - userId=0192f3a4-...
[러닝] 트랙 저장 실패: Redis 오류 - roomId=12, userId=0192f3a4-...
[예약] 복구 시작 - pendingCount=3
```

### 도메인 태그

로그가 속한 기능의 `application/` 패키지로 정한다. 중앙 예외 핸들러만 예외다(아래 레이어별 규칙). 어댑터·리스너도 자신이 처리하는 기능의 태그를 쓴다(`RunningTrackRedisAdapter` → `[러닝]`).

| 패키지 | 태그 |
|---|---|
| `auth` | `[인증]` |
| `user` | `[회원]` |
| `match` | `[매칭]` |
| `running` | `[러닝]` |
| `scheduling` | `[예약]` |
| 기능을 알 수 없음 | `[공통]` |

새 도메인 패키지가 생기면 이 표에 태그를 추가한다.

### 동작·결과·원인

- **동작**: 무엇을 했는지 짧게 적는다(`로그인`, `트랙 저장`, `신청`).
- **결과**: `성공` · `실패` · `시작` · `건너뜀` 중 하나만 쓴다. `에러`·`오류`·`완료` 같은 유사어를 섞지 않는다 — 같은 결과가 여러 단어로 갈리면 검색이 갈린다. 단어가 더 필요하면 이 목록에 먼저 추가한다.
- **원인**: 로그만 보고 다음에 어디를 볼지 알 수 있게 적는다(`비밀번호 불일치` → 사용자 문제, `Redis 오류` → Redis 확인).
- 태그·동작·결과·원인은 **변수 없는 고정 문구**다. 분기마다 문구가 하나로 정해져야 문구로 검색·집계된다. 변하는 값은 전부 `key=value`로 보낸다.
- 원인은 **개발자용 문구**다. 사용자 응답 메시지를 그대로 쓰지 않는다 — 응답은 보안상 일부러 뭉뚱그리지만(`이메일 또는 비밀번호가 다릅니다`), 로그는 원인을 구분해 남긴다(`가입되지 않은 이메일` / `비밀번호 불일치`).

### key=value

- `=` 양옆에 공백을 넣지 않고, 항목 사이는 `, `로 구분한다 — 수집 단계의 key=value 파싱이 공백을 기준으로 자른다.
- key는 도메인에서 쓰는 이름을 camelCase로 쓴다(`roomId`, `userId`, `scheduledJobId`). 같은 대상을 파일마다 다른 이름(`room_id`, `rid`)으로 쓰지 않는다.
- 수치에는 단위 접미사를 붙인다(`distanceM`, `elapsedMs`, `thresholdMs`).
- 값이 여러 개면 대괄호로 묶는다(`fields=[email, password]`). 수집 단계의 key=value 파싱이 괄호 안을 값 하나로 읽는다. `List`를 그대로 넘기면 이 형태로 찍힌다.

## 레벨

판단 기준: **사용자 잘못인가, 서버 문제인가?** 사용자 잘못이면 INFO, 서버 문제면 ERROR다.

| 레벨 | 기준 | 스택트레이스 | 예 |
|---|---|---|---|
| ERROR | 서버에 문제가 생겼다. 예외를 잡고 계속 진행해도 ERROR다 | 필수 | Redis·PostgreSQL 장애, 외부 API(SES·S3·OAuth) 실패, 처리하지 못한 예외 |
| WARN | 아직 실패는 아니지만 주의가 필요한 상태다 | 없음 | 응답 지연, 한도 근접, 미구현이라 대체 동작, 사용자 실수로 보기 어려운 인증 이상(폐기된 refresh token 재사용) |
| INFO | 사용자의 행동과 그 결과다. 사용자 잘못으로 인한 실패도 여기다 | 없음 | 로그인 성공·실패, 매칭 신청 건너뜀, 러닝 시작, 요청 검증 실패 |

- DEBUG는 개발 중 흐름을 확인하는 용도다. 운영에서는 출력되지 않으므로 장애 추적에 필요한 정보를 DEBUG에만 두지 않는다. 형식은 다른 레벨과 같다(`[러닝] 방 채널 구독 성공 - roomId=12`).
- ERROR는 예외가 있으면 반드시 예외 객체를 **마지막 인자**로 넘긴다. `{}` 자리 수보다 인자가 하나 많으면 SLF4J가 마지막 인자를 예외로 처리한다.
- 예외 없이 실패를 알게 되면(외부 API의 5xx 응답, 응답 필드 누락) 넘길 예외가 없으므로 ERROR만 남긴다.
- 예외 메시지에 시크릿이 섞이면(외부 API 키가 되돌아오는 오류) 예외 객체 대신 종류만 `cause=클래스명`으로 남긴다.

```java
log.error("[러닝] 트랙 저장 실패: Redis 오류 - roomId={}, userId={}", runningRoomId, userId, e);
```

## 레이어별 규칙

| 레이어 | 쓰는 레벨 | 무엇을 |
|---|---|---|
| domain | 없음 | 로거를 두지 않는다 |
| application | INFO · WARN · ERROR | 유스케이스의 결과. 업무 실패는 예외를 던지기 전에 INFO로 원인을 남긴다 |
| infrastructure | WARN · ERROR | 외부 시스템 장애·지연. INFO는 쓰지 않는다 |
| presentation | INFO · ERROR | 중앙 예외 핸들러만 쓴다 — 유스케이스에 닿기 전에 거절된 요청(검증·파싱 실패)은 INFO, 처리하지 못한 예외는 ERROR |

- **예외는 처리하는 곳에서 한 번만 찍는다.** 찍고 다시 던지지 않는다 — 같은 실패가 여러 줄로 남으면 추적이 흐려진다.
- 중앙 예외 핸들러는 요청에 매핑된 컨트롤러(`HandlerMethod`)의 패키지로 태그를 정하므로 유스케이스 도메인과 다를 수 있다(`/users/me/status` → `[회원]`). 컨트롤러에 닿기 전에 난 예외(없는 경로, 보안 필터 거절)는 `[공통]`이다.

```
ERROR ... GlobalExceptionHandler : [러닝] 처리하지 못한 예외
java.lang.NullPointerException: Cannot invoke "RunningRoom.getStatus()" because "room" is null
	at ...application.running.command.start.StartRunningRoomHandler.handle(StartRunningRoomHandler.java:58)
	...
```

## 남기지 않는 것

- 비밀번호 — 틀린 비밀번호도 남기지 않는다. 대개 진짜 비밀번호의 오타다.
- 토큰(access·refresh·OAuth), 키, 시크릿
- 이메일 원문 — 사용자를 특정할 수 없어 이메일이 유일한 단서일 때만 마스킹해서 남긴다(`a***@b.com`). 사용자를 찾았으면 `userId`를 쓴다.
- 원본 GPS 좌표
- 요청·응답 바디 전체

## 전환 중

- `GlobalExceptionHandler`는 아직 업무 예외를 WARN으로 찍는다. 유스케이스마다 INFO 로그를 채운 뒤 중앙의 업무 예외 로그를 제거한다 — 먼저 제거하면 업무 실패가 로그에 남지 않는다.
- 기존 코드의 `log.warn(..., e)` 중 서버 장애에 해당하는 것은 ERROR로 옮긴다.
- 문구의 구분자는 `-`다. 기존 로그의 `—`는 해당 코드를 고칠 때 함께 바꾼다.
- HTTP 외 진입점(WebSocket 메시지, Redis 리스너, 예약 작업)과 요청 스레드 밖의 전송(SSE)은 요청 ID·사용자 ID를 붙이는 방식을 아직 정하지 않았다.
