# Runiverse 기능 명세서

## 1. 화면별 기능

> 화면 순서는 사용자 흐름 기준: 인증·온보딩 → 홈·매칭 → 러닝 → 기록 → 피드 → 프로필·설정 → 공통.

> **`[MVP 제외]` 표기**: 지금 만들지 않는 것. 본문은 그대로 두어 확장 시점에 재작성 없이 쓴다. 화면 단위로 제외되는 기능은 **탭과 라우트를 등록**하고 화면만 준비중으로 대체한다 — 탭을 숨기거나 비활성화하지 않는다.
>
> 마커가 없으면 만드는 것이다. 차수(1차·2차)는 적지 않는다 — 일정은 바뀌지만 "지금 만드나 마나"는 바뀌지 않는다.

### 인증·온보딩

**앱 진입(스플래시)**

- 앱을 열면 저장된 refreshToken으로 `POST /auth/refresh`를 시도하고, 성공하면 `GET /users/me`의 `isOnboarded`로 진입 화면을 가른다.

| refreshToken | `isOnboarded` | 진입 화면 |
|---|---|---|
| 없음·만료·무효 | — | 초기 페이지(로그인) |
| 유효 | `false` | 온보딩 |
| 유효 | `true` | 홈 |

- `POST /auth/refresh`는 토큰 두 개만 반환하고 `isOnboarded`를 담지 않는다 — 인증 응답 셋(회원가입·로그인·소셜 로그인)이 모두 같은 형태이고, 온보딩 완료 여부는 `GET /users/me`가 단독으로 판정한다.
- 서비스 소개 화면은 서버가 관여하지 않는다(완료 여부를 서버에 저장하지 않음) — 표시 정책은 클라이언트 문서에서 정한다.

**초기 페이지**

- 로그인 폼: 이메일·비밀번호 입력 필드 제공.
- 로그인 버튼: 입력한 이메일/비밀번호로 로그인 수행.
- 회원가입 버튼 → 회원가입 페이지로 이동.
- Google / Kakao 로그인 버튼: 소셜 계정으로 회원가입 또는 로그인. 네이버는 **[MVP 제외]**.
  - 앱이 provider 인증으로 `authorizationCode`·`codeVerifier`를 받은 뒤 `POST /auth/oauth/google|kakao`에 전달한다. 서버는 코드↔토큰 교환과 유저 조회 후 `provider_id`로 `oauth_users`를 조회하고, 없으면 생성한 뒤 자체 토큰을 발급한다. 카카오는 SDK 앱 전환, 구글은 커스텀 탭·커스텀 스킴을 쓴다(웹뷰는 provider가 차단).
  - 최초 가입 시 온보딩 화면을 거침 — `oauth_users` 생성 후 `user_onboardings` 입력 필요.
  - 카카오 이메일 미동의 시 403 가입 거부(`OAUTH_EMAIL_NOT_PROVIDED` — `users.email` NOT NULL 유지).

**약관 동의 화면**

- **회원가입 버튼을 누르면 가장 먼저 나온다.** 이용약관·개인정보처리방침을 링크로 제공하고 동의를 받은 뒤 이메일 인증으로 넘어간다.
- **소셜 가입에는 이 화면을 끼우지 않는다.** 소셜 버튼은 로그인과 가입을 겸하는데 신규 여부는 provider 응답을 받아봐야 알 수 있어, 앞에 약관을 띄우면 기존 사용자에게도 매번 뜬다. 대신 **초기 페이지의 소셜 버튼 아래에 동의 문구와 약관 링크를 둔다.**
- **서버는 동의 정보를 받지 않는다.** 별도 요청 필드도 저장 테이블도 두지 않고 가입 자체를 동의로 갈음한다 — 동의 시각 증빙은 `users.created_at`.

**회원가입 페이지**

- 회원가입 폼: 이메일, 인증번호, 비밀번호, 비밀번호 확인.
- 이메일 인증 3단계: 인증번호 발송 → 확인(`verificationTicket` 발급) → 티켓+비밀번호로 가입. 이메일은 티켓에서 꺼내 쓰므로 가입 요청에 담지 않음.
  - 이미 가입된 이메일은 발송 단계에서 409 차단 — 가입 여부 노출보다 UX를 택함.
  - 코드 5분·시도 5회, 재발송 쿨다운 30초·하루 10회, 티켓 30분 1회용.
- 회원가입 버튼: 입력 정보 검증 후 회원가입 수행. 가입 즉시 자동 로그인(토큰 발급) — 로그인 화면 거치지 않고 온보딩으로 이동.

**온보딩 화면**

- 온보딩 폼: 닉네임, 생년월일, 성별, 키, 몸무게, 평균 페이스 입력 후 제출. 약관 동의는 받지 않는다 — 가입 흐름 첫 화면에서 이미 받았다.
  - 닉네임 중복 체크(`NICKNAME_ALREADY_EXISTS`)는 온보딩 API의 에러 케이스.
  - 1회성 입력 — 닉네임은 `PATCH /users/me/nickname`, 나머지(성별·생일·키·몸무게)는 `PATCH /users/me/profile`로 수정한다. 평균 페이스는 수정 UI 없이 서버가 러닝 기록 기반 자동 갱신.

**하단 네비게이션 바**

- 홈 / 피드 / 기록 / 프로필 4개 버튼으로 각 화면 이동.
  - **피드 탭은 준비중 화면**으로 연결된다.

### 홈·매칭

**홈 화면**

- 날씨 정보: 현재 위치 기준 날씨 제공.
- 매칭 버튼: 설정된 조건으로 러닝 매칭 시작.
- 매칭 설정 버튼: 매칭 조건 설정 모달 오픈.
- 매칭 정보 입력 모달: 거리/시간 선택.
  - **자유 입력이 아니라 정해진 선택지에서 고른다** — 시작 시각은 **18:00~22:00 30분 간격**, 목표 거리는 **3·5·10km** 셋 중 하나.
    - 조건을 좁게 고정하는 이유는 매칭 성사율이다. 자유 입력이면 같은 조건에 두 명이 모일 확률이 급격히 떨어진다.
  - 시간 선택 박스에 **해당 슬롯의 대기 인원**을 함께 보여준다("19:00 · 3명 대기 중") — `GET /running-matches/slots`.
  - 페이스 조건은 입력받지 않는다 — 서버가 보관한 사용자 평균 페이스를 쓴다.
  - 모집 인원도 입력받지 않는다 — 서버가 2~4명 범위에서 자동 편성한다.
  - 활성 신청은 1개다 — 대기 중에 다시 신청할 수 없다.
  - 활성 신청은 `deleted_at IS NULL AND status='JOINED'`로 판정한다.
  - **친구 초대는 MVP에서 제외한다.** 방장 없이 방 참가자 누구나 친구를 제한 없이 초대할 수 있고, 최대 4명까지 수락 순서대로 입장시키는 원칙만 정했다. 별도 초대 테이블은 두지 않으며 API와 생명주기는 구현할 때 정한다. `INVITE`·`INVITED`는 미래 예약값이다.
  - `running_players` row가 매칭 요청이고, 희망 시작 시각은 `start_at`, 목표 거리는 `target_distance`에 저장한다. 방 배정은 `running_room_sessions`로 기록한다.
- 매칭 대기 화면: 매칭 진행 상태·남은 예상 시간·현재 참가자 확인.
  - **방 생성 시점**: 같은 조건의 모집 중인 방이 없으면 신청과 함께 1인 방을 `status='MATCHING'`으로 만든다. 방이 있으면 신청자를 배정해 마감까지 최대 4명 모집한다. `MATCHING`은 인원 수와 무관하게 "모집 중(마감 전)"인 구간이다.
    - 솔로 러닝도 개시 즉시 방이 생긴다 — 둘은 `running_rooms.type`(`MATCH`/`SOLO`)으로 갈린다. 매칭 후보 스캔은 `type='MATCH' AND status='MATCHING'`이라 솔로 방이 섞이지 않는다.
    - **"방 미배정" 상태는 없다.** 활성 신청이 있으면 방도 반드시 있고, 매칭 진행 단계는 배정 여부가 아니라 `running_rooms.status`로만 판정한다.
  - 확정 판정: 모집 마감 시각은 `start_at - 오프셋`으로 계산한다 — **컬럼에 저장하지 않는다**(오프셋은 운영 설정 한 값이고, 그 값을 바꾸는 건 곧 정책을 바꾸는 것이라 진행 중인 방만 옛 마감을 유지할 이유가 없다). 그 시점에 **인원과 무관하게 `status='MATCHED'` 자동 확정**한다 — 자리 수(`max_player_count`) 도달 여부와도, 최소 인원과도 무관하다. `max_player_count`는 상한이라 갱신하지 않고, 실제 인원은 `current_player_count`가 갖는다.
    - **마감 스케줄러는 `type='MATCH' AND status='MATCHING'`만 본다.** 솔로는 모집 단계 없이 `MATCHED`로 태어나 애초에 걸리지 않고, 친구 초대는 MVP에서 제외한다.
  - **1인이면 매칭 실패가 아니라 1인으로 확정돼 혼자 뛴다.** 인원 부족으로 인한 자동 취소는 없다. 예약 매칭이라 사용자는 이미 그 시각에 뛸 준비를 하고 있고, 초기에는 매칭 풀이 얇아 1인 확정이 자주 나기 때문이다.
    - 대신 **1인 방에서 나갈 때는 페널티를 물리지 않고**(아래 매칭완료 대기방), 나가면 곧바로 다시 신청할 수 있다. 혼자 뛰기를 강제하지 않기 위한 출구다.
  - **매칭이 저절로 실패하는 경로는 없다.** `CANCELLED`는 **참가자가 모두 빠져 방이 빈 경우**(`current_player_count=0`) 중 **남길 러닝이 없을 때** 쓴다 — 시작 전이면 항상(모집 중 전원 취소든 확정 후 마지막 1인 이탈이든 같다), 시작 후면 아래 유효 기록 조건에 걸린다. 각자의 `deleted_at`은 본인이 취소·이탈한 시각이다.
    - **빈 방을 닫는 이유는 후보로 남기 때문이다.** 후보 스캔이 `status='MATCHING' AND current_player_count < max_player_count`라 0인 방도 걸리는데, 그대로 마감을 맞으면 0인 방이 확정돼 시작까지 간다. 참가자가 0이면 `avg_pace`도 사라져(마지막 사람 값을 남기지 않는다) 페이스 근접 판정 자체가 불가능하므로, 남겨두면 아무도 합류할 수 없는 방이 후보 목록만 차지한다.
    - **러닝이 시작(`STARTED`)된 뒤에 방이 비면 유효 기록 유무로 갈린다.** 유효 러닝 판정(최소 거리·최소 시간)을 통과한 기록이 **하나라도 있으면** 정상 종료 경로를 타 `FINISHED`가 되고, **하나도 없으면** `CANCELLED`로 닫는다 — 시작만 눌렀거나 몇십 미터 만에 그만둔 방을 완료로 남기지 않기 위해서다(아래 `STARTED`→`FINISHED` 전환). **마감이 아니라 러닝 시작이 1차 경계이고, 시작 후에는 유효 기록이 2차 경계다.**
  - **홈 화면 상태는 저장값이 아니라 파생값이다.** 별도 상태 컬럼이나 취소 사유 컬럼을 두지 않고 아래 규칙으로 계산한다.

    | 홈 상태 | 조건 |
    |---|---|
    | 대기 없음 | 활성 신청이 없음 |
    | 매칭 대기 중 | 방이 `MATCHING`이고 마감 전 |
    | 매칭 확정 | 방이 `MATCHED` |

  - 이 세 상태가 `GET /users/me/running-match`의 `state`(`NONE`/`WAITING`/`MATCHED`)로 내려간다.
  - **"매칭 실패" 상태는 없다.** 신청이 저절로 끝나는 경로가 없어서다 — 마감은 항상 확정으로 끝나고, 취소는 사용자가 직접 한 행동이라 그 즉시 "대기 없음"으로 돌아간다. 실패를 알리는 화면·배지·표시 기한도 두지 않는다.

- **매칭 현황 배너**: 대기 중에는 모든 화면 하단에 배너를 고정한다(슬롯 시각·현재 인원·마감까지 남은 시간). 다른 탭으로 이동해도 유지된다.
  - **배너 전용 API는 두지 않는다.** 앱 재시작 시 `GET /users/me/running-match`로 복원하고 이후 `RoomInfo` 전체를 담은 SSE로 갱신한다.

**매칭완료 대기방**

- 현재 위치 지도: 사용자 위치 지도 표시.
  - **여는 시점은 클라가 계산한다** — 기기 시각이 `start_at - N분`(N은 설정값)에 도달하면 연다.
  - 지도 오픈용 SSE 이벤트는 두지 않는다.
- 매칭된 참가자 목록: 닉네임·페이스·소개글 표시.
- 시작 타이머: 러닝 시작까지 카운트다운 — **클라이언트가 기기 시각으로 표시한다.** 서버가 매초 틱을 보내지 않는다.
  - **시작 3초 전부터 3-2-1 카운트다운**(화면·음성·햅틱). 이 구간에서는 뒤로가기를 차단한다.
  - 서버는 `start_at`에 방을 `STARTED`로 바꾸고 SSE `MATCH_ROOM_UPDATED`를 보낸다. 클라는 이를 받은 뒤 러닝 화면으로 전환해 WS `RUNNING_START`를 보내며, 이보다 이른 요청은 서버가 거부한다. 시작용 REST API는 없다.
    - **참가자 `JOINED`→`RUNNING` 전환은 스케줄러가 하지 않는다.** 각자의 `RUNNING_START`가 자기 것만 올린다 — 실제로 뛰기 시작한 사람만 `RUNNING`이 된다. 시작 시각에 아직 앱을 안 켠 사람까지 일괄로 `RUNNING`을 만들면 상태가 사실과 어긋난다.
- 나가기: 나간 사람만 `running_players.status='MATCHED_LEFT_*'` 처리 + `deleted_at` 기록, 해당 `running_room_sessions` row는 `is_connected=false`. 방은 유지되고 남은 참가자는 계속 대기.
  - **시작 직전까지 나갈 수 있다.** 시각으로 차단하지 않고 늦은 이탈은 페널티로 다룬다.
- **확정 후 이탈에는 페널티가 붙는다** — 모집이 마감(`start_at - 오프셋`)되고 유예 시간이 지난 뒤에 나가면, 일정 시간 매칭 신청이 제한된다. 한 번이면 걸린다. 판정 방식은 아래 도메인 제약의 이탈 페널티 절에 있다.
  - **유예를 두는 이유**: 마감 직전에 방에 붙은 사람도 확정 통보를 받고 판단할 시간이 있어야 한다. 마감과 페널티 시작 사이의 간격만큼은 **누구에게나 보장된다**.
  - **혼자 남은 방에서 나가는 것은 제재하지 않는다** — 이탈 시점 `current_player_count`가 1이면 유예가 지났어도 `MATCHED_LEFT_NO_PENALTY`다. 판정 기준은 마감 시각이 아니라 **나가는 순간의 인원**이다.
    - 이탈로 손해를 보는 상대가 없다. 제재의 목적은 함께 뛰기로 한 사람을 곤란하게 만드는 행동을 막는 것인데, 혼자면 그 대상이 없다.
    - **1인 확정과 확정 후 이탈로 혼자 남은 경우 모두 해당한다.** 두 경로 모두 "함께 뛰려고 신청했는데 혼자가 된" 같은 상태이므로 같게 다룬다.
    - 이 면제가 곧 1인 확정의 출구다. 나가면 활성 신청이 끝나므로 **곧바로 다른 슬롯에 다시 신청할 수 있다.**
  - **제재는 우선순위 하향이 아니라 매칭 신청 제한으로 적용한다.**
  - 확정 후 방 이탈 제재는 `MATCH`에만 적용한다. 솔로 개시는 쿨다운 중에도 허용하며, 시작한 뒤의 조기 종료는 아래 거리 비율 규칙을 적용한다.
  - **러닝 중 조기 종료는 서버가 계산한 실제 거리 ÷ 목표 거리를 운영 설정 비율과 비교한다.** 비율 미만이면 `RUNNING_LEFT_PENALTY`, 이상이면 `RUNNING_LEFT_NO_PENALTY`로 바꾸고 생성 가능한 트랙은 기록으로 저장한다. 목표 거리를 채우면 `COMPLETED`다.
  - 종료 메시지를 받지 못한 참가자는 타임아웃에 마지막 수신 데이터로 같은 판정을 한다. 거리·시간·경로를 산출할 수 있는 트랙이 없으면 실제 거리를 0으로 판정해 상태만 확정하고 기록 없음으로 남긴다.
  - **취소 안내 문구**: 대기방에서 나가기를 누를 때 제재 구간이면 그 사실을 알린다. "매칭 우선순위가 낮아진다"처럼 실제로 동작하지 않는 안내는 쓰지 않는다.
- **확정 후 이탈로 혼자 남아도 방을 유지하고 자동 재매칭하지 않는다.** `type`은 `MATCH`로 남는다.
  - 모집 중(`MATCHING`) 이탈도 방을 유지한다 — 2명이던 방에서 1명이 빠지면 1인 방으로 돌아가 마감까지 계속 모집한다. 마지막 참가자까지 취소해 방이 빈 경우에만 `CANCELLED`로 닫는다.
  - **`current_player_count`가 0이 되는 경우만 방을 닫는다.** 1은 정상 상태다 — 마감 전이면 계속 모집하고, 마감 후면 혼자 뛴다.
- **대기 취소는 `running_players.deleted_at`을 기록해 신청 시각·종료 시각·당시 상태를 보존한다.**

### 러닝

**러닝 중 - 메인**

- 위치 지도: 현재 위치·이동 경로 표시.
- 러닝 정보: 페이스·러닝 시간·이동 거리·케이던스 실시간 제공.
- 일시정지: 멈춰 있는 동안 경과 시간과 거리 계산이 멈추고 좌표 전송도 중단한다 — GPS 흔들림이 거리로 잡히면 기록이 부풀려진다.
  - **다른 참가자는 계속 진행한다.** 일시정지는 본인 기록에만 영향을 주며, 상태는 참가자들에게 공유돼 화면에 멈춤으로 표시된다.
  - 종료는 2초 이상 길게 눌러야 한다 — 러닝 중 오조작으로 기록이 끊기는 것을 막는다.
- 사진 촬영: 촬영본은 본인 디바이스 갤러리에만 저장. 서버 업로드/조회 API 없음.

**러닝 중 - 다른 유저**

- 유저 트랙: 다른 참가자 진행 상황을 트랙 형태로 표시.
- 유저 비교 정보: 앞뒤 참가자 거리·페이스 정보.
- 음성 안내: 러닝 화면 상단 mic 아이콘으로 켜고 끈다. 본인의 1km 도달·구간 기록은 클라이언트가 처리한다.
- 파티원 비교 코칭(추월·역전·격차)은 **[MVP 제외]**이며 서버 이벤트 계약을 두지 않는다.

**러닝 후 - 대시보드**

- 본인 경로 확인: 달린 경로 지도 표시.
- 참가자 공통 정보: 참가자별 러닝 시간·이동 거리.
- 참가자 상세 정보: 평균 페이스·소모 칼로리·평균 케이던스·구간별 평균 페이스. 같은 방 참가자끼리는 서로의 상세 기록 열람 가능(본인 제한 없음). GPS 트랙 저장 방식은 아래 GPS 트랙 절 참고.
  - **누적 상승 고도는 참가자 상세에 함께 보여준다** — `total_elevation_gain`이 결과·기록 상세 응답에 `totalElevationGainMeters`로 나간다.
  - **구간은 10m 고정이다.** 0m부터 10m씩 자르는 고정 경계(0-10, 10-20…)를 방 전체가 공유하며, 경계가 정확히 10m가 되도록 그 지점을 보간해 만든다. 목표 5,000m면 참가자당 구간이 500개다.
  - **목표를 넘겨 뛰어도 기록은 목표에서 끊는다** — 거리·종료 시각·소요 시간을 모두 목표 지점 보간값으로 확정한다. 그래야 참가자 전원이 같은 구간 경계를 갖고 구간별 비교가 성립한다. 목표 이후 좌표는 S3 원본 트랙에만 남는다.
  - **구간별 고저는 순고도차로 보여준다** — 구간마다 `elevation_change`(끝 고도 − 시작 고도)를 저장하고 `elevationChangeMeters`로 내린다. 부호가 그대로 구간 성격이라(오르막 `+`, 내리막 `−`, 평지 0 근처) 오름/내림 분류를 따로 저장하지 않는다. 다만 **10m 구간에서는 GPS 수직 오차가 구간 길이에 맞먹어 대체로 null이다.**
    - **누적 상승과 순고도차는 다른 값이다.** 기록은 "얼마나 힘들었나"라 올라간 것만 합산하고, 구간은 "어떤 지형이었나"라 오르내림을 상쇄한다. 그래서 구간값을 세로로 더해도 기록의 누적 상승과 맞지 않는다 — 화면에서 총합처럼 보여주지 않는다.
    - 점별 고도는 표시하지 않는다. 서버는 기기 GPS 고도를 운영 설정 임계값으로 노이즈 필터링해 계산하며 외부 고도 API로 보정하지 않는다. 유효 고도 표본이 부족하면 고도 지표는 null이다.

### 기록

**기록**

- 일정 조회: 캘린더로 러닝 기록 확인 — 러닝한 날을 표시하고, 날짜를 선택하면 그날 기록을 보여준다. 같은 날짜에 기록이 여러 건이면 목록으로 표시한다.
  - 기록 카드에는 **달린 경로 모양을 작게 함께 띄운다** — 거리·시간 숫자만으로는 어느 러닝인지 구분되지 않는다. 목록 응답이 경로를 같이 내려주므로(`routePolyline`) 카드마다 추가 조회가 없다.
  - 날짜별 획득 색 표시는 **[MVP 제외]**다.
- 일정 상세 정보: 선택 일정의 경로·러닝 기록 확인.

> **대회 기능은 서비스에서 제외한다.** 마라톤 일정 조회·북마크와 관련 탭·라우트·테이블·API를 두지 않는다.

### 피드 [MVP 제외]

> 인앱 피드·댓글·대댓글·좋아요 전부 해당.

**피드 목록 페이지**

- 무한 스크롤 조회, 목록에서 바로 이미지/전체글/좋아요·댓글 버튼 노출.
- 좋아요 버튼: 목록에서 바로 토글.
- 댓글 버튼 → 댓글 모달로 이동.
- 친구 탭: 친구의 게시물 최신순. 공개 범위 필터: 친구의 "친구"/"전체" 공개 피드 + 내 피드 전부.
- 전체 탭: 친구 + 타 사용자 게시물 혼합(인스타 탐색 방식). 초기 버전은 최신순 + 가벼운 가중치(친구의 친구 등), 개인화 추천은 이후 확장. 공개 범위 필터: "전체" 공개 피드 + 친구의 "친구" 공개 피드.
- 프로필 클릭 → 프로필로 이동.
- 댓글: 작성/수정/삭제, 답글 작성/수정/삭제, 댓글 좋아요.
  - 수정은 작성자 본인만 가능(피드 소유자는 삭제만). 수정 시 이전 내용은 `delete_comments`에 스냅샷 보관(피드와 동일).
  - 대댓글 depth는 1단계 제한 — `comments.parent_comment_id`가 있는 댓글엔 답글 작성 API 자체를 차단.
  - 답글은 목록에 바로 포함하지 않고 "답글 N개 보기" 탭 시 지연 로딩(인스타그램 방식). 댓글 목록 정렬은 등록순.
  - 삭제 권한: 댓글 작성자 본인 또는 그 댓글이 달린 피드의 소유자(악플/스팸 관리 목적).

**피드 작성 페이지**

- 이미지 업로드: 여러 장 선택해 첨부.
- 글 작성: 텍스트/이미지 둘 다 비운 채 게시 불가 — 최소 하나 필수.
- 노출 범위 선택: 친구/전체/나만.
- 위치/경로 첨부: 별도 기능 아님 — 러닝 기록 템플릿 선택에 통합. 템플릿 카드에 경로 미리보기 지도 포함 — 피드 카드 `record.routePolyline`은 `running_records.route_polyline`의 다운샘플 encoded polyline(별도 API 없음).
- 러닝 기록 템플릿 선택: 과거 기록 선택 시 거리/시간/페이스·경로 미리보기가 카드로 자동 삽입. 대시보드에서 진입한 경우 방금 완료한 기록이 기본 선택.
- 게시 버튼: 등록 후 피드 목록 최상단에 노출.

### 프로필·설정

**프로필 페이지**

- 프로필 요약: 사진, 닉네임, 소개글, 친구 수 표시.
  - **러닝 통계(마일리지·최고 페이스·러닝 횟수)는 표시하지 않는다** — FE와 합의로 제외했다. 되살리면 별도 저장 테이블 없이 `running_records`에서 계산하고 유효 러닝 판정을 거친다.
  - 전체 사용자 대비 백분위는 표시하지 않는다.
- **[MVP 제외]** 컬렉션: 획득한 색을 보유 수 / 전체 수와 함께 표시.
  - **못 얻은 색도 함께 보여준다** — 획득 조건 문구와 같이 표시해 "무엇을 더 모을 수 있는지"가 드러나야 한다.
  - 컬렉션은 하나뿐이다.
- 친구 수 클릭 → 친구 목록 페이지로 이동(**본인 프로필에서만**). 타인 프로필에서는 수만 보이고 목록은 열리지 않는다.
- 편집 버튼 → 프로필 편집 페이지로 이동.
- 설정 버튼 → 설정 페이지로 이동.
- 조건부 표시: 본인 프로필이면 편집/설정 버튼, 타인 프로필이면 친구 요청 버튼.
- 사진·닉네임·소개글·친구 수는 항상 공개한다.
- **[MVP 제외]** 컬렉션은 `profile_visibility=FRIENDS`일 때 친구가 아닌 타인에게 가린다(`403 PROFILE_NOT_VISIBLE`).
- **[MVP 제외]** 내가 올린 피드 그리드: 프로필 하단에 본인 작성 피드를 썸네일 그리드로 표시.
- **[MVP 제외]** 피드 작성 버튼: 누르면 피드 작성 페이지로 이동.
- **[MVP 제외]** 피드 편집: 게시글 수정/삭제, 노출 범위 설정.
- **[MVP 제외]** 신고/차단 메뉴.

**프로필 편집 페이지**

- 화면 진입 시 `GET /users/me/profile`로 소개글·성별·생일·키·몸무게의 현재 값을 받아 입력 칸을 채운다.
- 사진 변경, 닉네임 변경(서비스 전반 표시 갱신), 그리고 소개글·성별·생일·키·몸무게 수정. **앞의 둘만 저장 흐름이 달라 API를 나눈다.**
  - **사진**: 업로드 URL 발급 → S3 직접 업로드 → 키 반영의 3단계라 사진을 고르는 시점에 처리된다(저장 버튼과 무관). 삭제도 별도 동작이며, 삭제는 S3 객체를 남기고 DB의 키 연결만 끊는다.
  - **닉네임**: `user_onboardings`에 저장되므로 온보딩을 마쳐야 바꿀 수 있다. 남이 쓰고 있으면 `409 NICKNAME_ALREADY_EXISTS`, 현재 닉네임과 같으면 아무것도 바꾸지 않는다. 저장 전 중복 확인 API로 입력 중에 미리 알려주되, 확인과 저장 사이에 선점될 수 있어 최종 방어는 저장 시점의 409다.
  - **나머지**: 값을 저장하기만 하면 되므로 `PATCH /users/me/profile` 하나로 받는다. 저장 대상 테이블이 갈리는 것(`users`·`user_onboardings`)은 구현 사정이라 API를 나누는 근거가 아니다 — 한 트랜잭션으로 처리한다.
    - 편집 화면 구성이 확정되기 전이라 편집 가능한 값을 한 엔드포인트에 모았다. 저장 버튼이 하나로 묶이든 여러 화면으로 갈리든 클라이언트가 자기 필드만 보내면 되고, 한 저장 버튼이 요청 둘을 필요로 하는 상황이 생기지 않는다.
    - 소개글의 길이 제한(100자)은 요청 검증으로 걸러 `400`으로 답한다. 성별·생일·키·몸무게는 `user_onboardings`에 있어 온보딩을 마쳐야 바꿀 수 있고, 그중 하나라도 담겨 있는데 미완료면 아무것도 바꾸지 않고 `409`다.

**친구 목록 페이지**

- 친구 목록 조회, 이름 기준 검색. **본인 목록만 본다** — 타인의 친구 목록은 열지 않는다. 친구의 친구를 훑어 사람을 찾는 흐름이 없고(사람 찾기는 사용자 검색), 누구와 친구인지는 민감한 정보다.
- 받은 친구 요청 확인 및 수락·거절. 보낸 요청 목록 화면은 두지 않는다.
  - **친구는 요청 → 수락으로 성립하는 대칭 관계다.** 성립한 뒤로는 누가 요청했는지에 의미가 없다.
  - 서로 요청을 주고받으면(A→B 요청 중에 B→A 요청) **바로 성립한다** — 이미 합의된 상황이라 한 번 더 수락을 요구하지 않는다.
  - 거절·요청 취소·친구 삭제는 모두 관계를 지운다. **이력을 남기지 않는다.**
- 사용자 클릭 → 해당 사용자 프로필로 이동.
- **사용자 검색**: 닉네임으로 전체 사용자를 찾는다(`GET /users/search`) — 친구를 추가하려면 먼저 사람을 찾아야 하므로 친구 기능의 진입점이다. 친구 목록 안의 이름 필터와는 대상이 다르다.

**설정 페이지**

- 계정: 이메일과 로그인 수단을 표시한다(`GET /users/me/account`). 이메일을 보여주는 화면은 여기뿐이다.
  - 로그인 수단은 `oauth_users` row 유무로 가른다 — 있으면 그 provider, 없으면 로컬.
  - **소셜 계정**: "구글/카카오 계정으로 로그인 중"을 표시하고 비밀번호 변경 항목을 감춘다 — 어느 provider로 가입했는지 잊으면 다른 소셜 버튼을 눌러 별개 계정이 만들어진다.
  - **로컬 계정**: 로그인 수단 문구 없이 비밀번호 변경 항목만 노출한다.
- 비밀번호 변경: **로컬 계정만.** 현재 비밀번호로 본인을 재확인하고 새 비밀번호를 받는다(가입과 같은 규칙 — 6~16자, 영문·숫자·특수문자 각 1자 이상. 확인 일치 검증은 클라).
  - 소셜 계정은 비밀번호가 없어 변경 대상이 아니다. 클라가 항목을 감추더라도 서버가 `409 PASSWORD_NOT_SET`으로 막는다 — 구버전 앱과 직접 호출이 있다.
  - 비밀번호를 바꿔도 발급된 토큰을 따로 끊지 않는다. 전 기기 로그아웃은 **[MVP 제외]**.
  - **로그인 세션은 계정당 하나다.** 리프레시 토큰을 유저 단위로 보관해, 다른 기기에서 로그인하면 이전 기기의 토큰이 덮어써진다. 이전 기기는 액세스 토큰이 만료되는 시점에 재발급이 실패해 로그아웃된다. 기기별 세션 유지는 **[MVP 제외]**이며 전 기기 로그아웃과 함께 다룬다.
  - **비밀번호 찾기(로그인 전 재설정)는 없다** — 초기 페이지에 "비밀번호를 잊으셨나요" 진입점을 두지 않는다. 이 기능은 로그인된 상태에서만 쓴다.
- 알림 설정: 전체 알림 on/off 단일 토글(`users.alert_consent` — 매칭 확정, 러닝 시작 리마인더, 친구 요청 도착·수락 네 종류 전부 관장). 종류별 개별 토글은 **[MVP 제외]**.
  - **기본값은 on**(`default true`) — 넷 다 거래성 알림이라 별도 수신 동의 대상이 아니고, 가입 직후부터 매칭 확정 푸시가 도달해야 한다.
  - 앱 내 토글은 OS 알림 권한과 별개다. 둘 중 하나라도 꺼져 있으면 푸시가 도달하지 않는다.
- 프로필 공개 범위 설정: `users.profile_visibility`(지인 마스킹 on/off).
- **피드 기본 공개 범위는 저장하지 않는다.** 피드마다 선택하고, 작성 화면 기본값은 클라이언트가 PUBLIC으로 둔다.
- 로그아웃/회원탈퇴: 확인 팝업 후 처리.
  - 로그아웃: `POST /auth/logout`(바디 없음 — 서버가 요청 토큰으로 본인 식별). 해당 access 토큰을 서버 블랙리스트에 올려 즉시 무효화하고(만료 전이라도 그 토큰 요청은 `401 TOKEN_BLOCKED`), **저장된 리프레시 토큰도 함께 지운다** — 남겨두면 재발급으로 새 access 토큰을 받아 계속 쓸 수 있다.
  - 로그아웃 시 기기 단위 푸시 중단(`is_active=false`)은 하지 않는다 — 토큰만 정리한다. 기기 비활성화는 **[MVP 제외]**이며, `device_id` 컬럼과 `POST /devices`는 MVP에 포함된다.

### 공통 (특정 화면 소속 아님)

**알림 (푸시)**

- 매칭 확정, 러닝 시작 리마인더, 친구 요청 도착·수락 — 알림 종류별로 눌렀을 때 최적 화면으로 랜딩.
- **[MVP 제외]** 피드 좋아요/댓글.
- 인앱 알림함(목록 조회 화면) 없음 — 푸시로만 발송, 클릭 시 랜딩만 수행. `notification` 테이블/조회 API 불필요, 디바이스 등록(`user_devices`) API만 유지.

## 2. 도메인 제약

> 전체 테이블·컬럼·타입·PK 규칙·enum·단위는 `erd.md`가 단일 출처. 여기서는 API 작성·구현에 필요한 도메인 제약과 설계 맥락만 남긴다.

**API 리소스 네이밍**: 방을 가리키는 이름은 DB·API·팀 대화 모두 **`room` 하나로 통일한다**(`running_rooms` ↔ `runningRoomId` ↔ `/running-rooms`).

- **"세션"은 방을 가리키는 말로 쓰지 않는다.** 이 단어는 로그인 세션·WebSocket 세션에 이미 쓰이고 있어 겹친다. 러닝을 서술할 때는 "러닝 구간", 방을 가리킬 때는 "방"으로 적는다.
- **`running-match`와 `running-room`은 API 단계 이름이다.** 전자는 매칭 신청·대기, 후자는 방 단위 동작을 가리킨다.
- 신청 즉시 방이 생기므로 `runningRoomId`는 매칭 단계에서도 존재한다. 다만 **경로 체계는 단계로 갈린다** — 매칭 단계는 방 ID를 URL에 쓰지 않고(`GET /users/me/running-match`), 방 단계는 반드시 쓴다(`GET /running-rooms/{runningRoomId}/results`).

**매칭·러닝 설계**: 구간마다 통신 방식이 다르다 — **매칭은 REST + SSE**, **러닝 구간은 WebSocket**(`/api/v1/ws/running`)이다.

- 매칭 구간은 클라가 보내는 것이 신청·취소 둘뿐이라 양방향 채널이 필요 없다 — REST로 보내고 현황은 SSE 스트림(`/running-matches/stream`)으로 받는다. 러닝 구간은 위치를 주기 발신하는 고빈도 양방향 구간이라 WebSocket을 쓴다.
- 대기 인원·성사·취소는 SSE 이벤트로 전달된다(`api-spec.md` 5번).
- **SSE 연결은 화면 생명주기에 묶지 않는다.** 매칭 대기 중 현황 배너가 모든 화면에서 유지돼야 하므로 홈을 벗어나도 스트림은 살아 있어야 한다. 이는 클라이언트 아키텍처 제약이다.
- 매칭 이벤트는 전부 **전체 상태를 담는다** — 놓친 이벤트를 되짚을 필요가 없어 재연결은 곧 스냅샷 재수신이다. 앱 재시작처럼 스트림이 끊긴 뒤에는 `GET /users/me/running-match`가 같은 정보를 돌려준다.
- **SSE → WS 전환**: `start_at` 직전에 WS를 연결하고, 서버의 `MATCH_ROOM_UPDATED(status=STARTED)`를 받으면 `RUNNING_START`를 보낸다. `RUNNING_STARTED` ack를 받은 뒤 SSE를 닫는다.
- 메시지 네이밍 규칙: 클라 발신 현재형 / 서버 발신 과거형.

**방 배정 기준**: 모집 중인 방 중 페이스가 가까운 방(`running_rooms.avg_pace`)을 먼저 고르고, 같으면 `running_room_sessions.leave_count`가 낮은 방을 우선한다.

**이미지 업로드**(`feed_images`, `users.profile_image_key` 등 전체 공통): Presigned URL 방식 — 클라이언트가 업로드용 presigned URL 요청 → 서버가 S3 presigned URL 발급 → 클라이언트가 S3에 직접 업로드 → 반환받은 key를 본 API(피드 작성, 프로필 사진 변경 등) 요청에 포함해 전달.

**GPS 트랙**: 원본 트랙은 Postgres 테이블이 아님 — `running_records.gps_track_key`로 S3 객체를 참조. **매칭 러닝과 솔로 러닝이 같은 경로를 쓴다.**

- 클라이언트가 1~2초 간격으로 좌표를 수집해 **로컬에 쌓으면서** 10초마다 모아서 WS로 보낸다. 서버는 Redis(`runningRoomId+userId` 키)에 버퍼링하고, 종료 신호나 타임아웃에 기록 생성 가능한 트랙이면 S3와 `running_records`에 저장한다.
- **거리·페이스·구간 분할은 서버가 받은 좌표로 계산한다.** 클라이언트 계산값은 러닝 중 화면 표시용이지 저장값이 아니다.
- 칼로리는 러닝 중 표시하거나 전송하지 않는다. 종료 시 서버가 확정 거리·시간과 사용자 체중으로 전체·구간 칼로리를 계산해 결과에만 제공한다.
- **화면에 그리는 경로는 S3가 아니라 DB에서 나간다.** 기록 생성 시 원본 트랙을 다운샘플해 `running_records.route_polyline`(encoded polyline)을 함께 저장하고, 대시보드·기록 목록·기록 상세는 이 값만 쓴다. S3 원본은 재계산·분석용으로 남는다.
- **좌표에는 기기 GPS 고도를 포함한다.** 서버가 노이즈를 필터링해 고도 지표를 계산하며 외부 고도 API는 쓰지 않는다.
- **위치 배치에는 ack가 없다.** 재연결하면 클라이언트가 로컬 트랙 전체를 처음 `sequence`부터 다시 보내고, 서버는 이미 받은 순번을 무시한다. 로컬 트랙은 `RUNNING_FINISHED` ack를 받은 뒤 삭제한다.
  - 연결이 복구되지 않으면 서버가 마지막 수신 데이터로 타임아웃 처리하므로 재연결 전 로컬에만 남은 구간은 기록에 포함되지 않는다.
- **솔로 러닝도 방을 만든다.** `running_rooms`는 개시 즉시 `type='SOLO'`, `status='MATCHED'`이고 참가자는 `JOINED`로 생성된다. 같은 WS를 쓰며 클라이언트가 만들 수 있는 방은 솔로뿐이다.
  - **솔로가 `MATCHED`에서 출발하는 이유**: 모집을 건너뛸 뿐 그 뒤는 매칭과 같은 길이어야 한다. 확정된 방에 WS로 붙어 `STARTED`·`RUNNING`으로 넘어가는 구간이 두 종류에서 한 벌로 유지되고, 핸들러가 `type`으로 분기하지 않는다.
    - **`RUNNING_START`의 상태 전환 규칙은 하나뿐이다** — `MATCHED`이고 `start_at`이 지났으면 `STARTED`로 올린다. 매칭 방은 시작 스케줄러가 `start_at`에 이미 올려놨으니 통과하고, 솔로는 `start_at`이 개시 시각이라 여기서 올라간다. 솔로 전용 스케줄러가 필요 없는 이유다.
  - 대신 **방만 만들고 채널에 붙지 않은 솔로 방**이 생길 수 있다. 시작하지 못한 방은 활성 신청으로 남아 다음 러닝을 막으므로, `start_at + 유예`를 지나도록 시작되지 않은 `MATCHED` 방은 닫아야 한다. 전에는 솔로 방이 `STARTED`로 태어나 이 구멍이 없었다.

**컬러 시스템 [MVP 제외]**: 러닝 지표가 조건을 충족하면 고정 팔레트의 색이 열리는 **잠금 해제 모델**이다. 색을 새로 만들어내지 않는다.

- 생성 모델을 쓰지 않는 이유는 수집이 성립하지 않기 때문이다 — 색 공간이 무한하면 같은 5km를 100번 뛴 결과가 비슷한 색 100개로 쌓인다. **시그니처 컬러도 블렌드 색도 없다** — 사용자가 색을 고르는 지점이 서비스 어디에도 없다.
- 마스터(`colors`)는 운영이 채워 넣는 고정 데이터이고, 획득 이력(`user_colors`)은 복합 PK라 **같은 색을 두 번 얻는 상황이 없다**.
- 12범주 × 셰이드 3~4로 구성하되 **총 색 개수는 명세에 적지 않는다.** 진행률은 마스터 행 수로 계산하므로 색을 추가해도 코드가 바뀌지 않는다.
- **획득 조건은 DB에 두지 않는다.** 조건의 축이 제각각이라(단일 러닝 거리 / 누적 거리 / 페이스 …) 데이터로 표현하기 어렵다 — 판정은 서버 로직에, DB에는 안내 문구만 둔다.
- 범주별 획득 조건표와 자동 획득은 MVP에서 제외한다. 향후 판정을 위해 `total_elevation_gain`·`weather_code`·`temperature`는 지금부터 저장한다.

**피드-러닝 기록 연결**: `feeds.running_record_id`는 `running_records` 참조 — 피드 작성 시 "러닝 기록 템플릿 선택"에 대응. nullable — 러닝 기록 없이 글+사진만으로도 작성 가능.

**피드 공개 범위**: `feeds.visibility` 값은 3종(친구/전체/나만) — "나만"은 본인 피드 목록/프로필 그리드 조회 시에만 노출, 친구 피드·전체 피드 조회에서는 제외.

**날씨**: 홈 화면 날씨는 클라이언트가 키리스 무료 날씨 API(예: Open-Meteo)를 직접 호출한다. 서버 API는 없다.

- **기록에 남기는 날씨는 이것과 별개다.** 기록 생성 시 서버가 시작 좌표·시각으로 날씨를 조회해 `running_records.weather_code`(WMO 4677 코드)·`temperature`(섭씨)에 저장한다. 향후 컬러 `ADVERSITY` 판정에 쓸 관측값이라 클라이언트 신고값을 쓰지 않는다.
- 날씨는 화면·API에 노출하지 않고 판정용 관측값으로 저장한다. `total_elevation_gain`은 `totalElevationGainMeters`로 응답한다.
- **조회에 실패해도 종료 처리를 막지 않는다.** 두 컬럼이 NOT NULL이라 비워 둘 수 없으므로, 서버가 정해진 횟수만큼 재시도하고 끝내 실패하면 기본값을 넣는다. 재시도 횟수와 기본값은 운영 설정이다. 한 시간짜리 러닝 기록이 외부 API 하나 때문에 통째로 날아가면 안 된다.
  - **기본값은 악조건이 아닌 쪽으로 고른다**(맑음·평상 기온). 실측이 아닌 값이 섞이는 건 감수하되, 향후 컬러 `ADVERSITY` 판정에서 **없던 악조건을 만들어내지는 않게** 하기 위해서다. 오차는 "악조건을 놓치는" 방향으로만 생긴다.

**이탈 페널티 판정**: 제재 대상 여부는 이탈 시점에 정해 `status`에 굳히고, 신청 시점에는 그 값만 본다. **모집 마감(`start_at - 오프셋`) + 유예를 지났고 이탈 시점 `current_player_count`가 2 이상**이면 `MATCHED_LEFT_PENALTY`, 둘 중 하나라도 아니면 `MATCHED_LEFT_NO_PENALTY`다(솔로 방 제외). 인원 조건이 붙는 이유는 혼자 남은 방을 나가는 데는 손해를 보는 상대가 없기 때문이다. `status IN ('MATCHED_LEFT_PENALTY','RUNNING_LEFT_PENALTY')`인 이탈 중 가장 최근 것을 찾아 `deleted_at + 쿨다운`이 아직 안 지났으면 `409 MATCH_COOLDOWN`으로 막는다. 방·마감 시각을 조인할 필요가 없다.

- 네 값은 운영 설정으로 뺀다 — **모집 마감 오프셋**(마감 = `start_at - 오프셋`), **유예**, **쿨다운**, **조기 종료 제재 거리 비율**.
- **유예는 마감 오프셋보다 작아야 한다.** 같거나 크면 확정되자마자 페널티 구간이 되어, 마감 직전에 붙은 사람이 판단할 시간 없이 제재받는다. 오프셋에서 유예를 뺀 만큼이 곧 "누구에게나 보장되는 판단 시간"이다.
- **판정 결과를 저장하는 대가**: 유예나 거리 비율을 조정해도 이미 쌓인 row는 당시 기준으로 남는다. 쿨다운 길이는 조회 시점 설정을 쓴다.
- **쿨다운은 이탈 row의 `deleted_at`으로 잰다.** `deleted_at` 자체는 완주에도 찍히지만, 위 `status` 조건이 이탈만 걸러 낸다.

**개인 단위 진행 상태**: `running_players.status`가 갖는다. 러닝 중은 `RUNNING`, 목표 거리 도달은 `COMPLETED`, 조기 종료는 거리 비율에 따라 `RUNNING_LEFT_*`다. 아래 유효 러닝 판정을 통과한 트랙이면 상태 전환과 같은 트랜잭션에서 `running_records`를 만든다.

**유효 러닝 판정**: 기록을 **만들지 말지**를 가르는 단일 문턱이다. 두 조건을 모두 만족해야 저장한다 — 거리·시간·경로를 **산출할 수 있고**, **최소 거리·최소 시간**을 넘겨야 한다. 몇십 초 뛰다 멈춘 러닝이 기록·통계·컬러 판정에 섞이는 것을 막기 위한 것이다.

- 두 값(**최소 거리**, **최소 시간**)도 운영 설정으로 뺀다. 최소 거리 참고값은 **0.8km** — Zwift가 러닝 활동 저장에 쓰는 문턱이다.
- **미달이면 기록을 만들지 않는다.** 이탈 판정은 그대로 돌아 `running_players.status`는 `RUNNING_LEFT_*`로 남는다 — **기록 유무와 개인 종료 상태는 별개다.** 결과 조회도 기록 없는 참가자를 유지한다(erd 결과 조회 절).
- **판정은 저장 시점에 한 번 하고 되돌리지 않는다.** 임계값은 정책이라 바뀌지만 조정해도 이미 쌓인 row는 당시 기준으로 남는다(위 판정 결과를 저장하는 대가와 같다). 대신 저장된 기록은 전부 유효하므로 **유효 여부 컬럼을 두지 않고** 조회 쪽에서 다시 거르지 않는다.
- **저장된 기록의 쓰임에는 예외가 없다**: 본인 기록 목록·캘린더·러닝 후 대시보드·컬러 획득 판정·피드 템플릿이 같은 집합을 본다. (프로필 요약의 통계는 표시 자체가 제외됐다 — 되살려도 같은 집합이다)

**`STARTED` 종료 전환**: 방 시작 때 `RUNNING`으로 전환된 참가자 전원이 종료 상태(`COMPLETED`·`RUNNING_LEFT_*`)가 되고 기록 확정이 끝나면 즉시 전환한다. 타임아웃에는 남은 참가자를 마지막 수신 데이터로 종료 처리한 뒤 전환한다.

- **행선지는 유효 기록 유무로 갈린다** — 위 유효 러닝 판정을 통과해 저장된 기록이 하나라도 있으면 `FINISHED`, 하나도 없으면 `CANCELLED`다. 시작만 눌렀거나 몇십 미터 만에 그만둔 방을 완료로 남기지 않기 위한 것이다. 방 상태는 기록 확정이 끝난 시점 값으로 굳는다.
- **유효 기록이 있는 방은 `CANCELLED`로 닫지 않는다.** `CANCELLED`는 terminal이라 `FINISHED`에 도달할 수 없고, 그대로 닫으면 기록 확정과 결과 조회 경로가 함께 끊긴다.
- **`CANCELLED`로 닫힌 방에는 기록이 없다.** 저장 문턱과 방 상태 문턱이 같은 판정을 쓰므로 "취소된 방에 매달린 기록"은 생기지 않는다. `running_records.running_room_id`가 NOT NULL인 것과 앞뒤가 맞는다.

**회원탈퇴 시 연관 데이터 처리** (테이블별):

- 탈퇴를 막지 않는다. 삭제 전에 대기 중이면 취소하고 확정 방이면 이탈한다. 러닝 중이면 마지막 수신 데이터로 일반 종료 판정을 적용해 목표 달성은 `COMPLETED`, 미달은 거리 비율에 따른 `RUNNING_LEFT_*`로 바꾸며 생성 가능한 기록은 확정한다. 방 인원·상태를 갱신하고 남은 참가자에게 알린 뒤 계정을 삭제한다.
- **유지**: `feeds`, `comments`, `running_records`(+`running_splits`) — 같은 방 참가자의 기록 비교를 위해 탈퇴해도 남긴다. `user_id`는 DB FK 없이 애플리케이션에서 처리하며, 응답의 탈퇴 사용자는 `{ userId, nickname: "탈퇴한 사용자", profileImageUrl: null, isDeleted: true }`로 대체한다.
- **유지 (카운트 재계산 안 함)**: `feed_likes`, `comment_likes` — 탈퇴자가 누른 좋아요는 남겨두고 `like_count` 그대로(인스타그램 방식).
- **즉시 삭제**: `friendships`와 개인 데이터 테이블(`user_onboardings`, `user_devices`, `oauth_users`, `user_colors`). 시작 전 신청의 `running_players`와 세션도 삭제한다.
- **러닝 참가 이력 유지**: 이미 시작한 방의 `running_players`와 `running_room_sessions`는 기록이 없는 참가자도 과거 결과에 남기기 위해 유지한다. 사용자 정보는 탈퇴 유저 형식으로 대체한다.
- 친구 수는 집계 컬럼이 아니라 `friendships` COUNT라 **재계산이 필요 없다** — row가 사라지면 수도 함께 줄어든다. (`feed_likes`는 row를 유지해 카운트도 유지 — 기준이 다름.)

**삭제 처리 방식** (리소스별로 다름 — API 설계 시 각각 구분해서 반영):

- **`users`**: 하드delete + 아카이브 — 실제 DELETE 전에 `delete_users`에 스냅샷 먼저 저장(감사/로그 용도, 복구 기능 없음).
- **`feeds`**: `deleted_at` 소프트delete(복구 가능·조회 제외 처리).
- **`comments`**: 답글 유무로 분기(레딧 방식, 두 경우 모두 `delete_comments` 스냅샷 먼저 저장) — 답글 없으면 하드delete, 답글 있으면 톰스톤(row 유지 + 내용 비움 + `deleted_at` 기록, "삭제된 댓글입니다" 자리표시로 노출하고 답글 스레드 유지).
