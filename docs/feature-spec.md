# Runiverse 기능 명세서

## 1. 화면별 기능

> 화면 순서는 사용자 흐름 기준: 인증·온보딩 → 홈·매칭 → 초대 러닝 → 러닝 → 기록 → 피드 → 프로필·설정 → 공통.

> **`[MVP 제외]` 표기**: 지금 만들지 않는 것. 본문은 그대로 두어 확장 시점에 재작성 없이 쓴다. 화면 단위로 제외되는 기능은 **탭과 라우트를 등록**하고 화면만 준비중으로 대체한다 — 탭을 숨기거나 비활성화하지 않는다.
>
> 마커가 없으면 만드는 것이다. 차수(1차·2차)는 적지 않는다 — 일정은 바뀌지만 "지금 만드나 마나"는 바뀌지 않는다.

### 인증·온보딩

**앱 진입(스플래시)**

- 앱을 열면 먼저 `GET /app/version`으로 업데이트가 필요한지 확인한다(아래 공통 — 앱 업데이트). 업데이트 화면으로 가지 않으면 다음으로 넘어간다.
- 저장된 refreshToken으로 `POST /auth/refresh`를 시도하고, 성공하면 `GET /users/me`의 `isOnboarded`로 진입 화면을 가른다.

| refreshToken | `isOnboarded` | 진입 화면 |
|---|---|---|
| 없음·만료·무효 | — | 초기 페이지(로그인) |
| 유효 | `false` | 온보딩 |
| 유효 | `true` | 홈 |

- `POST /auth/refresh`는 토큰 두 개만 반환하고 `isOnboarded`를 담지 않는다 — 인증 응답 셋(회원가입·로그인·소셜 로그인)이 모두 같은 형태이고, 온보딩 완료 여부는 `GET /users/me`가 단독으로 판정한다.
- 서비스 소개 화면은 서버가 관여하지 않는다(완료 여부를 서버에 저장하지 않음) — 표시 정책은 클라이언트 문서에서 정한다.

**초기 페이지**

- 로그인 폼: 이메일·비밀번호 입력 필드 제공.
- 로그인 버튼: 입력한 이메일/비밀번호로 로그인 수행.
- 회원가입 버튼 → 회원가입 페이지로 이동.
- Google / Kakao / Apple 로그인 버튼: 소셜 계정으로 회원가입 또는 로그인. 네이버는 **[MVP 제외]**. 애플 버튼은 iOS에만 둔다 — iOS에서 다른 소셜 로그인을 제공하면 애플 심사(4.8)가 Sign in with Apple을 요구한다.
  - 카카오는 앱이 카카오 SDK로 `authorizationCode`·`codeVerifier`를 받아 `POST /auth/oauth/kakao`에 전달하고, 서버가 코드↔토큰 교환과 유저 조회를 한다. 구글은 앱이 `google_sign_in`으로 ID 토큰을 받아 `POST /auth/oauth/google`에 전달하고, 서버가 구글 공개키로 검증한다(웹뷰는 provider가 차단). 애플은 앱이 로그인마다 만든 `nonce`의 SHA-256 해시를 애플에 넘겨 ID 토큰을 받고, 토큰과 원본 `nonce`를 `POST /auth/oauth/apple`에 전달하면 서버가 애플 공개키로 검증하고 `nonce` 해시를 대조한다. 이후 서버는 `provider_id`로 `oauth_users`를 조회하고, 없으면 생성한 뒤 자체 토큰을 발급한다.
  - 최초 가입 시 온보딩 화면을 거침 — `oauth_users` 생성 후 `user_onboardings` 입력 필요.
  - 이메일이 없거나 미인증·만료면 403으로 가입·로그인을 거부한다(`OAUTH_EMAIL_NOT_PROVIDED` — `users.email` NOT NULL 유지). 이미 가입한 회원도 로그인할 때마다 검사한다.

**약관 동의 화면**

- **회원가입 버튼을 누르면 가장 먼저 나온다.** 이용약관·개인정보처리방침을 링크로 제공하고 동의를 받은 뒤 이메일 인증으로 넘어간다.
- **소셜 가입에는 이 화면을 끼우지 않는다.** 소셜 버튼은 로그인과 가입을 겸하는데 신규 여부는 provider 응답을 받아봐야 알 수 있어, 앞에 약관을 띄우면 기존 사용자에게도 매번 뜬다. 대신 **초기 페이지의 소셜 버튼 아래에 동의 문구와 약관 링크를 둔다.**
- **서버는 동의 정보를 받지 않는다.** 별도 요청 필드도 저장 테이블도 두지 않고 가입 자체를 동의로 갈음한다 — 동의 시각 증빙은 `users.created_at`.

**회원가입 페이지**

- 회원가입 폼: 이메일, 인증번호, 비밀번호, 비밀번호 확인.
- 이메일 인증 3단계: 인증번호 발송 → 확인(`verificationTicket` 발급) → 티켓+비밀번호로 가입. 이메일은 티켓에서 꺼내 쓰므로 가입 요청에 담지 않음.
  - 이미 가입된 이메일은 발송 단계에서 409 차단 — 가입 여부 노출보다 UX를 택함.
  - 코드 5분·시도 5회, 재발송 쿨다운 30초·하루 10회, 티켓 30분 1회용.
- 회원가입 버튼: 입력 정보 검증 후 회원가입 수행. 가입 즉시 자동 로그인(토큰 발급) — 로그인 화면 거치지 않고 온보딩으로 이동.

**온보딩 화면**

- 온보딩 폼: 닉네임, 생년월일, 성별, 키, 몸무게, 평균 페이스 입력 후 제출. 약관 동의는 받지 않는다 — 가입 흐름 첫 화면에서 이미 받았다.
  - 닉네임 중복 체크(`NICKNAME_ALREADY_EXISTS`)는 온보딩 API의 에러 케이스.
  - 1회성 입력 — 닉네임은 `PATCH /users/me/nickname`, 나머지(성별·생일·키·몸무게)는 `PATCH /users/me/profile`로 수정한다. 평균 페이스는 수정 UI가 없다 — 러닝을 끝낼 때마다 서버가 최근 기록으로 다시 낸다(아래 평균 페이스 갱신). 그전까지는 여기서 받은 자기 신고값이 매칭에 쓰인다.
  - 만 14세 미만은 받지 않는다 — 법정대리인 동의 절차가 없어 개인정보를 처리할 수 없다. 생년월일로 만 나이를 계산해 서버가 `400`으로 막고, 프로필 편집에서 생년월일을 바꿔 우회하는 것도 같은 기준으로 막는다.

**하단 네비게이션 바**

- 홈 / 피드 / 기록 / 프로필 4개 버튼으로 각 화면 이동.
  - **피드 탭은 준비중 화면**으로 연결된다.

### 홈·매칭

**홈 화면**

- 날씨 정보: 현재 위치 기준 날씨 제공.
- 매칭 버튼: 설정된 조건으로 러닝 매칭 시작.
- 매칭 설정 버튼: 매칭 조건 설정 모달 오픈.
- 매칭 정보 입력 모달: 거리/시간 선택.
  - **자유 입력이 아니라 정해진 선택지에서 고른다** — 시작 시각은 **18:00~22:00 30분 간격**, 목표 거리는 **3·5·10km** 셋 중 하나(현재 운영값 — 선택지는 서버 설정이라 코드 수정 없이 바뀔 수 있다).
    - 조건을 좁게 고정하는 이유는 매칭 성사율이다. 자유 입력이면 같은 조건에 두 명이 모일 확률이 급격히 떨어진다.
    - **모집 마감(`start_at - 오프셋`)이 지난 시각은 신청할 수 없다**(`MATCH_SLOT_CLOSED`). 서버가 신청 시각으로 판정한다.
  - 시간 선택 박스에 **해당 슬롯의 대기 인원**을 함께 보여준다("19:00 · 3명 대기 중") — `GET /match-rooms/slots`. 모든 거리의 슬롯을 한 번에 받아, 거리를 바꿔도 다시 조회하지 않는다.
  - 페이스 조건은 입력받지 않는다 — 서버가 보관한 사용자 평균 페이스를 쓴다.
  - 모집 인원도 입력받지 않는다 — 서버가 최대 4명까지 모으고, 마감 때 1명이면 1인으로 확정한다(아래 확정 판정).
  - 활성 신청은 1개다 — 대기 중에 다시 신청할 수 없다.
  - 활성 신청은 `deleted_at IS NULL`로 판정한다. **`status`는 보지 않는다** — 러닝 중(`RUNNING`)인 참가자도 활성이어야 다음 매칭이 막힌다. 종료·이탈은 어느 경로든 `deleted_at`을 찍으므로 이 한 컬럼이 활성 여부의 정본이다.
  - **친구와 뛰는 길은 매칭이 아니라 초대 러닝이다**(아래 초대 러닝 절). 매칭 방에는 친구를 초대할 수 없다 — 랜덤 매칭 방은 모르는 사람끼리 페이스로 묶는 자리라, 초대로 자리를 채우면 배정 기준이 흔들린다.
  - `running_players` row가 매칭 요청이고, 희망 시작 시각은 `start_at`, 목표 거리는 `target_distance`에 저장한다. 방 배정은 `running_room_sessions`로 기록한다.
- 매칭 대기 화면: 매칭 진행 상태·남은 예상 시간·현재 참가자 확인.
  - **방 생성 시점**: 같은 조건의 모집 중인 방이 없으면 신청과 함께 1인 방을 `status='MATCHING'`으로 만든다. 방이 있으면 신청자를 배정해 마감까지 최대 4명 모집한다. `MATCHING`은 인원 수와 무관하게 "모집 중(마감 전)"인 구간이다.
    - 솔로 러닝도 개시 즉시 방이 생긴다 — 둘은 `running_rooms.type`(`MATCH`/`SOLO`)으로 갈린다. 매칭 후보 스캔은 `type='MATCH' AND status='MATCHING'`이라 솔로 방이 섞이지 않는다.
    - **"방 미배정" 상태는 없다.** 활성 신청이 있으면 방도 반드시 있고, 매칭 진행 단계는 배정 여부가 아니라 `running_rooms.status`로만 판정한다.
  - 확정 판정: 모집 마감 시각은 `start_at - 오프셋`으로 계산한다 — **컬럼에 저장하지 않는다**(오프셋은 운영 설정 한 값이고, 그 값을 바꾸는 건 곧 정책을 바꾸는 것이라 진행 중인 방만 옛 마감을 유지할 이유가 없다). 그 시점에 **인원과 무관하게 `status='MATCHED'` 자동 확정**한다 — 자리 수(`max_player_count`) 도달 여부와도, 최소 인원과도 무관하다. `max_player_count`는 상한이라 갱신하지 않고, 실제 인원은 `current_player_count`가 갖는다.
    - **마감은 방을 주기적으로 훑지 않고 예약으로 깬다.** 매칭 방을 열 때 `scheduled_jobs`에 `MATCH_CLOSE`를 마감 시각으로 걸고, 그 시각에만 확정을 돈다. 솔로는 모집 단계 없이 `MATCHED`로 태어나 예약 자체가 생기지 않는다. 초대 방도 같은 다섯 예약을 걸지만 **마감 오프셋은 초대 전용 값(현재 1분)을 쓴다**(아래 초대 러닝 절).
      - **예약은 저장하지만 마감 시각의 정본은 여전히 `start_at - 오프셋`이다.** `scheduled_jobs.execute_at`은 그 계산을 굳혀 둔 사본이라, 오프셋을 바꾸면 아직 실행되지 않은 예약의 `execute_at`도 함께 옮겨야 한다. 클라에 내려가는 `closeAt`은 계속 계산값이다.
      - **확정 직전에 방을 잠그고 `status='MATCHING'`을 다시 본다.** 예약은 인스턴스 여럿이 들고 있고 재시도도 있어 두 번 깰 수 있는데, 이 재확인이 곧 멱등성이다. 사용자 취소로 이미 `CANCELLED`가 된 방도 여기서 걸러진다.
  - **1인이면 매칭 실패가 아니라 1인으로 확정돼 혼자 뛴다.** 인원 부족으로 인한 자동 취소는 없다. 예약 매칭이라 사용자는 이미 그 시각에 뛸 준비를 하고 있고, 초기에는 매칭 풀이 얇아 1인 확정이 자주 나기 때문이다.
    - 대신 **1인 방에서 나갈 때는 페널티를 물리지 않고**(아래 매칭완료 대기방), 나가면 곧바로 다시 신청할 수 있다. 혼자 뛰기를 강제하지 않기 위한 출구다.
  - **매칭이 저절로 실패하는 경로는 없다.** `CANCELLED`는 **남길 러닝이 없을 때** 쓴다 — 시작 전에는 참가자가 모두 빠져 인원이 0이 되면 항상 `CANCELLED`다(모집 중 전원 취소든 확정 후 마지막 1인 이탈이든 같다). 시작 후에는 접속 전 참가자의 취소·탈퇴만 인원을 줄이고(전원이 빠지면 역시 `CANCELLED`), 그 밖에는 뛰던 참가자가 모두 종료됐을 때 아래 유효 기록 유무로 `FINISHED`/`CANCELLED`가 갈린다. 각자의 `deleted_at`은 본인이 취소·이탈한 시각이다.
    - **빈 방을 닫는 이유는 그대로 마감을 맞으면 0인 방이 확정돼 시작까지 가기 때문이다.** 참가자가 0이면 `avg_pace`도 사라져(마지막 사람 값을 남기지 않는다) 후보 스캔(`avg_pace IS NOT NULL`)에는 걸리지 않지만, 마감 예약은 방마다 걸려 있어 닫지 않으면 그대로 돈다.
    - **러닝이 시작(`STARTED`)된 뒤에 방이 비면 유효 기록 유무로 갈린다.** 유효 러닝 판정(최소 거리·최소 시간)을 통과한 기록이 **하나라도 있으면** 정상 종료 경로를 타 `FINISHED`가 되고, **하나도 없으면** `CANCELLED`로 닫는다 — 시작만 눌렀거나 몇십 미터 만에 그만둔 방을 완료로 남기지 않기 위해서다(아래 `STARTED`→`FINISHED` 전환). **마감이 아니라 러닝 시작이 1차 경계이고, 시작 후에는 유효 기록이 2차 경계다.**
  - **홈 화면 상태는 저장값이 아니라 파생값이다.** 별도 상태 컬럼이나 취소 사유 컬럼을 두지 않고 아래 규칙으로 계산한다.

    | 홈 상태 | 조건 |
    |---|---|
    | 대기 없음 | 활성 신청이 없음 |
    | 매칭 대기 중 | 방이 `MATCHING`이고 마감 전 |
    | 매칭 확정 | 방이 `MATCHED` |

  - 이 세 상태는 서버가 상태 조회 API(`GET /users/me/status`)로 직접 준다 — 러닝 중까지 넓힌 같은 판정이다. 앱 진입·복귀 때 이 값으로 화면을 정하고, 대기 중 변화는 스트림이 내려주는 `RoomInfo`(방 `status`·`closeAt`)로 따라간다.
  - **"매칭 실패" 상태는 없다.** 신청이 저절로 끝나는 경로가 없어서다 — 마감은 항상 확정으로 끝나고, 취소는 사용자가 직접 한 행동이라 그 즉시 "대기 없음"으로 돌아간다. 실패를 알리는 화면·배지·표시 기한도 두지 않는다.

- **매칭 현황 배너**: 대기 중에는 모든 화면 하단에 배너를 고정한다(슬롯 시각·현재 인원·마감까지 남은 시간). 다른 탭으로 이동해도 유지된다.
  - **배너 전용 API는 두지 않는다.** 앱 재시작 시 상태 조회로 대기 중임을 확인하고 스트림을 다시 열어 연결 직후 스냅샷으로 복원하고, 이후에도 `RoomInfo` 전체를 담은 SSE로 갱신한다.

**매칭완료 대기방**

- 현재 위치 지도: 사용자 위치 지도 표시.
  - **여는 시점은 클라가 계산한다** — 기기 시각이 `start_at - N분`(N은 설정값)에 도달하면 연다.
  - 지도 오픈용 SSE 이벤트는 두지 않는다.
- 매칭된 참가자 목록: 닉네임·페이스·소개글 표시.
- 시작 타이머: 러닝 시작까지 카운트다운 — **클라이언트가 기기 시각으로 표시한다.** 서버가 매초 틱을 보내지 않는다.
  - **시작 3초 전부터 3-2-1 카운트다운**(화면·음성·햅틱). 이 구간에서는 뒤로가기를 차단한다.
  - 서버는 `start_at - 리드타임`(운영값)에 SSE `RUNNING_READY`를 보내고, 클라는 거기 실린 `startsInMs`로 타이머를 걸어 `start_at`에 WS `RUNNING_START`를 보낸다. 이보다 이른 요청은 서버가 거부한다. 시작용 REST API는 없다.
    - **정각이 아니라 미리 알린다.** 정각에 보내면 네트워크 지연만큼 참가자마다 출발이 어긋난다 — 서버는 기준만 주고 출발 순간은 클라 타이머가 맞춘다.
    - **방의 `MATCHED`→`STARTED` 전환은 `start_at` 정각의 시작 스케줄러가 일으킨다.** `RUNNING_READY`는 통지만 하고 상태를 바꾸지 않는다. 스케줄러가 밀리면 먼저 도착한 참가자의 `RUNNING_START`가 대신 올린다 — 어느 쪽이 이겨도 방 행을 잠그고 상태를 다시 보므로 전이는 한 번뿐이다.
    - **참가자 `JOINED`→`RUNNING` 전환은 시작 스케줄러가 하지 않는다.** 각자의 `RUNNING_START`가 자기 것만 올린다 — 실제로 뛰기 시작한 사람만 `RUNNING`이 된다. 시작 시각에 아직 앱을 안 켠 사람까지 일괄로 `RUNNING`을 만들면 상태가 사실과 어긋난다.
- 나가기: 나간 사람만 `running_players.status='MATCHED_LEFT_*'` 처리 + `deleted_at` 기록, 해당 `running_room_sessions` row는 `is_connected=false`. 방은 유지되고 남은 참가자는 계속 대기.
  - **시작 직전까지 나갈 수 있다.** 시각으로 차단하지 않고 늦은 이탈은 페널티로 다룬다.
  - **러닝을 시작한 뒤(본인이 `RUNNING`)에는 이 버튼으로 나갈 수 없다** — 종료는 러닝 종료가 맡는다. 여기서 끊으면 트랙과 기록이 저장되지 않는다. 방이 시작됐어도 본인이 아직 접속 전(`JOINED`)이면 나갈 수 있고, 확정 후 이탈과 같게 판정하고 방 인원도 하나 줄인다 — 그래야 상대가 먼저 취소해 혼자 남은 사람이 이어서 나갈 때 면제된다.
- **확정 후 이탈에는 페널티가 붙는다** — 모집이 마감(`start_at - 오프셋`)된 뒤에 나가면 일정 시간 매칭 신청이 제한된다. 한 번이면 걸린다. 판정 방식은 아래 도메인 제약의 이탈 페널티 절에 있다.
  - **유예는 두지 않는다** — 마감 시각은 클라가 `closeAt`으로 계속 표시하고 있어 모르고 나가는 경우가 없다. 마감 정각부터 제재 구간이다.
  - **혼자 남은 방에서 나가는 것은 제재하지 않는다** — 이탈 시점 `current_player_count`가 1이면 마감이 지났어도 `MATCHED_LEFT_NO_PENALTY`다. 판정 기준은 마감 시각이 아니라 **나가는 순간의 인원**이다.
    - 이탈로 손해를 보는 상대가 없다. 제재의 목적은 함께 뛰기로 한 사람을 곤란하게 만드는 행동을 막는 것인데, 혼자면 그 대상이 없다.
    - **1인 확정과 확정 후 이탈로 혼자 남은 경우 모두 해당한다.** 두 경로 모두 "함께 뛰려고 신청했는데 혼자가 된" 같은 상태이므로 같게 다룬다.
    - 이 면제가 곧 1인 확정의 출구다. 나가면 활성 신청이 끝나므로 **곧바로 다른 슬롯에 다시 신청할 수 있다.**
  - **제재는 우선순위 하향이 아니라 매칭 신청 제한으로 적용한다.**
  - 이탈·미출석·조기 종료 제재는 `MATCH`에만 적용한다. **초대 방은 어느 시점에 나가도 제재하지 않는다**(아래 초대 러닝 생명주기). 솔로 개시와 초대 방 생성·수락은 쿨다운 중에도 허용한다. 솔로는 목표 거리가 없어 거리 비율 판정이 없고, 사용자가 끝내면 `COMPLETED`다(유효 러닝 판정 미달이면 기록만 없다).
  - **러닝 중 조기 종료는 서버가 계산한 실제 거리 ÷ 목표 거리를 운영 설정 비율과 비교한다.** 비율 미만이면 `RUNNING_LEFT_PENALTY`, 이상이면 `RUNNING_LEFT_NO_PENALTY`로 바꾸고 생성 가능한 트랙은 기록으로 저장한다. 목표 거리를 채우면 `COMPLETED`다.
    - **1인 방에서는 비율이 미달이어도 제재하지 않는다** — 시작 전 이탈 면제와 같은 이유로 곤란해지는 상대가 없다. 판정 순간의 `current_player_count`(확정 인원에서 취소·탈퇴한 미출석자를 뺀 수)가 1인지로 판정한다. 상대가 오지도 취소하지도 않았으면 인원이 그대로라 제재한다.
    - `RUNNING_LEFT_PENALTY`도 `MATCHED_LEFT_PENALTY`와 같이 쿨다운을 건다. 다만 **기간은 따로 설정한다**(조기 종료와 확정 후 이탈의 무게가 다를 수 있다).
  - 종료 메시지를 받지 못한 참가자는 강제 종료 시각에 마지막 수신 데이터로 같은 판정을 한다. 거리·시간·경로를 산출할 수 있는 트랙이 없으면 실제 거리를 0으로 판정해 상태만 확정하고 기록 없음으로 남긴다.
  - **취소 안내 문구**: 대기방에서 나가기를 누를 때 제재 구간이면 그 사실을 알린다. "매칭 우선순위가 낮아진다"처럼 실제로 동작하지 않는 안내는 쓰지 않는다.
- **확정 후 이탈로 혼자 남아도 방을 유지하고 자동 재매칭하지 않는다.** `type`은 `MATCH`로 남는다.
  - 모집 중(`MATCHING`) 이탈도 방을 유지한다 — 2명이던 방에서 1명이 빠지면 1인 방으로 돌아가 마감까지 계속 모집한다. 마지막 참가자까지 취소해 방이 빈 경우에만 `CANCELLED`로 닫는다.
  - **`current_player_count`가 0이 되는 경우만 방을 닫는다.** 1은 정상 상태다 — 마감 전이면 계속 모집하고, 마감 후면 혼자 뛴다.
- **대기 취소는 row를 지우지 않고 `status=MATCHED_LEFT_NO_PENALTY`와 `deleted_at`을 기록한다** — 신청 시각·종료 시각·끝난 사유가 남는다.

### 초대 러닝

> 친구끼리 시각·거리를 정해 함께 뛰는 방이다. **매칭과 다른 점은 셋이다 — 방이 생기는 방식, 사람이 들어오는 방식(초대 수락), 그리고 제재가 없다는 것.** 모집 마감 이후(확정·시작·종료)는 매칭 방과 같은 경로를 탄다. 생명주기 세부는 아래 도메인 제약의 초대 러닝 절.

**초대 페이지**

- 시작 시각과 목표 거리를 **자유롭게 입력한다.** 매칭처럼 선택지로 좁히지 않는다 — 매칭이 선택지를 고정한 이유는 모르는 사람끼리의 성사율인데, 초대는 같이 뛸 사람을 직접 데려오므로 그 제약이 필요 없다.
  - **시작 시각**은 "지금 + 최소 준비 시간(`invite.min-lead-time`, 현재 10분)"부터 **오늘(KST) 23:59**까지, 분 단위다. 다음 날로 넘기는 예약은 받지 않는다 — 23:49가 넘으면 고를 시각이 없어 방을 만들 수 없다. **목표 거리**는 운영 설정의 최소·최대 거리 사이(미터).
  - 초대는 시작 1분 전(`invite.close-offset`)까지 받는다 — 그래서 최소 준비 시간 10분이면 초대를 보낼 시간이 최소 9분 남는다.
- 만들면 본인 혼자인 초대 방(`type='INVITE'`, `status='MATCHING'`)이 생기고 곧바로 아래 초대 방 화면으로 간다. 친구 선택은 방 화면의 초대 버튼에서 한다.
- **활성 신청은 매칭과 합쳐 1개다.** 매칭 대기·러닝 중에는 초대 방을 만들 수 없고, 초대 방에 있는 동안에는 매칭을 신청할 수 없다.
- 매칭 쿨다운 중에도 만들 수 있다 — 쿨다운은 랜덤 매칭 신청만 막는다(솔로와 같다).

**초대 방 화면**

- 매칭완료 대기방과 같은 화면에 **친구 초대 버튼**과 **초대 현황**이 더해진다. 나머지(참가자 목록·모집 마감 표시·카운트다운·나가기)는 매칭 대기방과 같다.
- **친구 초대 버튼**: 친구 목록에서 골라 **한 명씩** 초대한다. 못 보내면 왜 못 보냈는지(친구가 아님·매칭 중·러닝 중·이미 방에 있음·횟수 상한)를 바로 알려준다. 방장은 없다 — **방 참가자 누구나** 초대할 수 있다.
  - 초대는 친구에게만 보낼 수 있다. 초대할 수 있는 친구 수는 제한하지 않는다 — 자리는 수락 순서로 찬다. 한 사람이 같은 친구에게 보내는 횟수(처음 포함)만 상한(`invite.max-invite-count`, 현재 5)이 있다.
  - **모집 마감 전에만** 초대할 수 있다. 마감 뒤에는 버튼을 감춘다.
- **초대 현황**: 아직 응답하지 않은 초대만 보여준다 — **대기중**("…"처럼 기다리는 표시). 수락한 친구는 현황에서 빠지고 참가자 목록으로 옮겨 가며, 거절한 친구와 수락했다가 나간 친구는 현황에서 빠진다. 다시 초대하면 대기중으로 현황에 돌아온다. 상태가 바뀔 때마다 서버가 방 정보를 다시 내려 화면이 갱신된다.
  - 거절했거나 나간 친구에게는 다시 초대할 수 있다.
  - 마감되면 응답하지 않은 초대는 만료되고 현황도 사라진다.

### 러닝

**러닝 중 - 메인**

- 위치 지도: 현재 위치·이동 경로 표시.
- 러닝 정보: 페이스·러닝 시간·이동 거리·케이던스 실시간 제공.
- 일시정지: 멈춰 있는 동안 클라는 경과 시간 표시를 멈추고 좌표 수집·전송도 중단한다 — GPS 흔들림이 거리로 잡히면 기록이 부풀려진다.
  - **다른 참가자는 계속 진행한다.** 일시정지는 본인에게만 적용되며, 상태는 참가자들에게 공유돼 화면에 멈춤으로 표시된다.
  - **화면 상태는 네 가지다** — 뛰는 중(`RUNNING`)·일시정지(`PAUSED`)·연결 끊김(`DISCONNECTED`)·종료(`FINISHED`). 상대가 멈춘 것인지, 끊긴 것인지, 끝난 것인지를 느려진 것과 구분해 보여주기 위해서다. DB에 저장하지 않고 Redis에만 두는 표시용 값이며, 전이 규칙은 api-spec 5-D(`RUNNING_PROGRESS_UPDATED`)가 정본이다.
  - **서버는 일시정지 신호로 기록을 계산하지 않는다.** 신호는 유실되거나 조작될 수 있어, 기록은 수신한 좌표로만 계산한다. 대신 클라가 좌표마다 싣는 일시정지 구간 번호(`pauseSegment`)로 일시정지 구간을 뺀다 — 번호는 좌표와 함께 저장·재전송되므로 신호처럼 유실되지 않는다. 버튼 없이 멈춘 구간은 서버가 좌표만으로 판정한다 — 아래 도메인 제약의 트랙 필터 절.
  - **일시정지하면 콤보가 끊긴다.** 길이와 무관하며, 다시 함께 달리면 0부터 새로 쌓인다. 앱은 콤보 중에 일시정지 버튼을 누르면 이를 안내한다(아래 러닝 콤보 절).
  - 종료는 2초 이상 길게 눌러야 한다 — 러닝 중 오조작으로 기록이 끊기는 것을 막는다.
- 사진 촬영: 촬영본은 본인 디바이스 갤러리에만 저장. 서버 업로드/조회 API 없음.

**러닝 중 - 다른 유저**

- 유저 트랙: 다른 참가자 진행 상황을 트랙 형태로 표시.
- 유저 비교 정보: 앞뒤 참가자 거리·페이스 정보.
- 콤보: 특정 참가자와 나란히 달리는 동안 그 상대와의 콤보가 쌓인다. 상대마다 따로 세며 화면에는 상대별 현재 콤보와 최고 콤보를 보여준다. 판정 규칙은 아래 도메인 제약의 러닝 콤보 절에 있다.
- 음성 안내: 러닝 화면 상단 mic 아이콘으로 켜고 끈다. 본인의 1km 도달·구간 기록은 클라이언트가 처리한다.
- 추월·역전 코칭 문구는 **[MVP 제외]**다. 참가자 간 격차는 위 콤보 판정에만 쓰고 코칭 메시지로 만들지 않는다 — 서버가 보내는 참가자 간 비교 이벤트는 콤보 하나뿐이다.

**러닝 후 - 대시보드**

- 본인 경로 확인: 달린 경로 지도 표시.
- 참가자 공통 정보: 참가자별 러닝 시간·이동 거리.
  - **러닝 시간은 움직인 시간이다.** 트랙 필터가 정지·관측하지 못한 구간을 뺀 값이라 시작~종료 시각의 차보다 짧을 수 있다(아래 트랙 필터 절). 결과 화면에는 "움직인 시간"으로 표기한다.
- 참가자 상세 정보: 평균 페이스·소모 칼로리·평균 케이던스·구간별 평균 페이스. 같은 방 참가자끼리는 서로의 상세 기록 열람 가능(본인 제한 없음). GPS 트랙 저장 방식은 아래 GPS 트랙 절 참고.
  - **누적 상승 고도는 참가자 상세에 함께 보여준다** — `total_elevation_gain`이 결과 응답에 `totalElevationGainMeters`로 나간다.
  - **구간은 10m 고정이다.** 0m부터 10m씩 자르는 고정 경계(0-10, 10-20…)를 방 전체가 공유하며, 경계가 정확히 10m가 되도록 그 지점을 보간해 만든다. 목표 5,000m면 참가자당 구간이 500개다.
  - **목표를 넘겨 뛰어도 기록은 목표에서 끊는다** — 거리·종료 시각·소요 시간을 모두 목표 지점 보간값으로 확정한다. 그래야 참가자 전원이 같은 구간 경계를 갖고 구간별 비교가 성립한다. 목표 이후 좌표는 S3 원본 트랙에만 남는다.
  - **구간별 고저는 순고도차로 보여준다** — 구간마다 `elevation_change`(끝 고도 − 시작 고도, 일시정지를 걸친 구간은 경계 앞뒤 순고도차의 합)를 저장하고 `elevationChangeMeters`로 내린다. 부호가 그대로 구간 성격이라(오르막 `+`, 내리막 `−`, 노이즈 임계값(운영값, 현재 3m) 이하의 평지는 null) 오름/내림 분류를 따로 저장하지 않는다. 다만 **10m 구간에서는 GPS 수직 오차가 구간 길이에 맞먹어 대체로 null이다.**
    - **누적 상승과 순고도차는 다른 값이다.** 기록은 "얼마나 힘들었나"라 올라간 것만 합산하고, 구간은 "어떤 지형이었나"라 오르내림을 상쇄한다. 그래서 구간값을 세로로 더해도 기록의 누적 상승과 맞지 않는다 — 화면에서 총합처럼 보여주지 않는다.
    - 점별 고도는 표시하지 않는다. 서버는 기기 GPS 고도를 운영 설정 임계값으로 노이즈 필터링해 계산하며 외부 고도 API로 보정하지 않는다. 유효 고도 표본이 부족하면 고도 지표는 null이다.

### 기록

**기록**

- 일정 조회: 캘린더로 러닝 기록 확인 — 러닝한 날을 표시하고, 날짜를 선택하면 그날 기록을 보여준다. 같은 날짜에 기록이 여러 건이면 목록으로 표시한다.
  - 기록 카드에는 경로를 띄우지 않는다 — 목록 응답(7-1)은 경로를 싣지 않고, 경로는 기록 상세(6-1·6-2)에서 본다.
  - 날짜별 획득 색 표시는 **[MVP 제외]**다.
- 일정 상세 정보: 선택 일정의 경로·러닝 기록 확인.

> **대회 기능은 서비스에서 제외한다.** 마라톤 일정 조회·북마크와 관련 탭·라우트·테이블·API를 두지 않는다.

### 피드 [MVP 제외]

> 인앱 피드·댓글·대댓글·좋아요 전부 해당.

**피드 목록 페이지**

- 무한 스크롤 조회, 목록에서 바로 이미지/전체글/좋아요·댓글 버튼 노출.
- 좋아요 버튼: 목록에서 바로 토글.
- 댓글 버튼 → 댓글 모달로 이동.
- 친구 탭: 친구의 게시물 최신순. 공개 범위 필터: 친구의 "친구"/"전체" 공개 피드 + 내 피드 전부.
- 전체 탭: 친구 + 타 사용자 게시물 혼합(인스타 탐색 방식). 초기 버전은 최신순 + 가벼운 가중치(친구의 친구 등), 개인화 추천은 이후 확장. 공개 범위 필터: "전체" 공개 피드 + 친구의 "친구" 공개 피드.
- 프로필 클릭 → 프로필로 이동.
- 댓글: 작성/수정/삭제, 답글 작성/수정/삭제, 댓글 좋아요.
  - 수정은 작성자 본인만 가능(피드 소유자는 삭제만). 수정 시 이전 내용은 `delete_comments`에 스냅샷 보관(피드와 동일).
  - 대댓글 depth는 1단계 제한 — `comments.parent_comment_id`가 있는 댓글엔 답글 작성 API 자체를 차단.
  - 답글은 목록에 바로 포함하지 않고 "답글 N개 보기" 탭 시 지연 로딩(인스타그램 방식). 댓글 목록 정렬은 등록순.
  - 삭제 권한: 댓글 작성자 본인 또는 그 댓글이 달린 피드의 소유자(악플/스팸 관리 목적).

**피드 작성 페이지**

- 이미지 업로드: 여러 장 선택해 첨부.
- 글 작성: 텍스트/이미지 둘 다 비운 채 게시 불가 — 최소 하나 필수.
- 노출 범위 선택: 친구/전체/나만.
- 위치/경로 첨부: 별도 기능 아님 — 러닝 기록 템플릿 선택에 통합. 템플릿 카드에 경로 미리보기 지도 포함 — 피드 카드 `record.routePolyline`은 기록의 경로 조각(`running_segments.route_polyline`)을 이어 다시 인코딩한 encoded polyline(별도 API 없음).
- 러닝 기록 템플릿 선택: 과거 기록 선택 시 거리/시간/페이스·경로 미리보기가 카드로 자동 삽입. 대시보드에서 진입한 경우 방금 완료한 기록이 기본 선택.
- 게시 버튼: 등록 후 피드 목록 최상단에 노출.

### 프로필·설정

**프로필 페이지**

- 프로필 요약: 프로필 사진, 배경 사진, 닉네임, 소개글, 친구 수 표시. **친구 수는 확정 친구만 센다** — 요청 대기는 들어가지 않는다.
  - **러닝 통계(마일리지·최고 페이스·러닝 횟수)는 수치로 표시하지 않는다** — FE와 합의로 제외했다. 같은 지표는 아래 업적의 **단계**로만 드러난다.
  - 전체 사용자 대비 백분위는 표시하지 않는다.
- **업적**: 10칸을 보여주고 그중 4개만 활성이다 — **누적 거리 · 페이스 · 최고 콤보 · 매칭 러닝 횟수.** 나머지 6칸은 비활성(준비중)으로 그린다.
  - **단계형 배지다.** 업적마다 단계 기준값이 있고, 넘은 단계까지 배지가 켜진다. 수치(누적 23.4km 등)는 내리지 않는다. 판정 규칙은 아래 도메인 제약의 업적 절.
  - **비활성 6칸은 클라가 그린다.** 정의가 없는 업적이라 서버가 내릴 값이 없다 — 서버는 활성 업적만 내린다. 업적이 추가되면 응답 항목이 늘고, 클라는 빈칸 수를 줄인다.
  - 본인·타인 모두 볼 수 있다.
- **[MVP 제외]** 컬렉션: 획득한 색을 보유 수 / 전체 수와 함께 표시.
  - **못 얻은 색도 함께 보여준다** — 획득 조건 문구와 같이 표시해 "무엇을 더 모을 수 있는지"가 드러나야 한다.
  - 컬렉션은 하나뿐이다.
- 친구 수 클릭 → 그 사람의 친구 목록으로 이동. **타인 프로필에서도 열린다.** 본인 프로필이면 아래 친구 목록 페이지, 타인 프로필이면 그 사람의 확정 친구만 보여준다(추천 친구·요청 없음).
- 편집 버튼 → 프로필 편집 페이지로 이동.
- 설정 버튼 → 설정 페이지로 이동.
- 조건부 표시: 본인 프로필이면 편집/설정 버튼, 타인 프로필이면 친구 요청 버튼.
- 사진(프로필·배경)·닉네임·소개글·친구 수·친구 목록·업적은 항상 공개한다 — `profile_visibility`로 가리지 않는다.
- **[MVP 제외]** 컬렉션은 `profile_visibility=FRIENDS`일 때 친구가 아닌 타인에게 가린다(`403 PROFILE_NOT_VISIBLE`).
- **[MVP 제외]** 내가 올린 피드 그리드: 프로필 하단에 본인 작성 피드를 썸네일 그리드로 표시.
- **[MVP 제외]** 피드 작성 버튼: 누르면 피드 작성 페이지로 이동.
- **[MVP 제외]** 피드 편집: 게시글 수정/삭제, 노출 범위 설정.
- **[MVP 제외]** 신고 메뉴. 신고는 이용약관 제9조대로 운영 메일(`somabruteforce@gmail.com`)로 받는다.
- 차단 메뉴: 타인 프로필에서 차단한다(아래 차단 절).

**프로필 편집 페이지**

- 화면 진입 시 `GET /users/me/profile`로 소개글·성별·생일·키·몸무게의 현재 값을 받아 입력 칸을 채운다.
- 사진 변경, 닉네임 변경(서비스 전반 표시 갱신), 그리고 소개글·성별·생일·키·몸무게 수정. **앞의 둘만 저장 흐름이 달라 API를 나눈다.**
  - **사진**: 업로드 URL 발급 → S3 직접 업로드 → 키 반영의 3단계라 사진을 고르는 시점에 처리된다(저장 버튼과 무관). 삭제도 별도 동작이며, 삭제는 S3 객체를 남기고 DB의 키 연결만 끊는다.
  - **닉네임**: `user_onboardings`에 저장되므로 온보딩을 마쳐야 바꿀 수 있다. 남이 쓰고 있으면 `409 NICKNAME_ALREADY_EXISTS`, 현재 닉네임과 같으면 아무것도 바꾸지 않는다. 저장 전 중복 확인 API로 입력 중에 미리 알려주되, 확인과 저장 사이에 선점될 수 있어 최종 방어는 저장 시점의 409다.
  - **나머지**: 값을 저장하기만 하면 되므로 `PATCH /users/me/profile` 하나로 받는다. 저장 대상 테이블이 갈리는 것(`users`·`user_onboardings`)은 구현 사정이라 API를 나누는 근거가 아니다 — 한 트랜잭션으로 처리한다.
    - 편집 화면 구성이 확정되기 전이라 편집 가능한 값을 한 엔드포인트에 모았다. 저장 버튼이 하나로 묶이든 여러 화면으로 갈리든 클라이언트가 자기 필드만 보내면 되고, 한 저장 버튼이 요청 둘을 필요로 하는 상황이 생기지 않는다.
    - 소개글의 길이 제한(100자)은 요청 검증으로 걸러 `400`으로 답한다. 성별·생일·키·몸무게는 `user_onboardings`에 있어 온보딩을 마쳐야 바꿀 수 있고, 그중 하나라도 담겨 있는데 미완료면 아무것도 바꾸지 않고 `409`다.

**친구 목록 페이지**

- 친구 목록 조회, 이름 기준 검색. **타인의 친구 목록도 열린다**(위 프로필 페이지) — 같은 목록 API를 대상만 바꿔 쓴다. 항목마다 보는 사람 기준의 친구 상태가 실려, 타인의 친구 목록에서 바로 친구 요청을 보낼 수 있다.
- **추천 친구**: 친구 목록 아래에 친구 요청을 보낼 만한 사람을 보여준다. 기준은 **함께 뛴 사람**과 **페이스가 비슷한 사람**이다 — 판정 규칙은 아래 도메인 제약의 추천 친구 절.
  - 본인 친구 목록 페이지에만 있다. 타인의 친구 목록에는 없다.
- 본인 친구 목록은 **한 목록에 세 상태를 함께 담는다** — **받은 요청**(내 수락 대기), **보낸 요청**(상대의 수락 대기), **친구**(확정). 타인의 친구 목록에는 확정 친구만 있다.
  - 본인과 타인이 보는 범위만 다른 같은 목록이라 API는 하나이고 조회자로 거른다(api-spec 10-7). 요청을 따로 받는 API는 두지 않는다 — 이 화면 한 곳에서만 쓴다.
  - 받은 요청에서는 수락·거절, 보낸 요청에서는 취소를 한다. 받은 요청은 인앱 알림(아래 공통 절)으로도 들어온다.
  - 차단 관계에서는 남의 친구 목록도 보이지 않게 한다(아래 차단 절).
  - **친구는 요청 → 수락으로 성립하는 대칭 관계다.** 성립한 뒤로는 누가 요청했는지에 의미가 없다.
  - 서로 요청을 주고받으면(A→B 요청 중에 B→A 요청) **바로 성립한다** — 이미 합의된 상황이라 한 번 더 수락을 요구하지 않는다.
  - 거절·요청 취소·친구 삭제는 모두 관계를 없음(`NONE`)으로 되돌린다. 행은 지우지 않는다 — 지우는 것은 탈퇴뿐이다.
  - **관계 이력은 애플리케이션 로그로 남긴다** — 요청·수락·취소·거절·친구 삭제·차단·차단 해제를 성공할 때마다 `[관계]` INFO 로그로 남긴다(`userId`·`targetId`). 테이블은 지금 상태만 가져 취소와 거절이 구분되지 않으므로, 무슨 일이 있었는지는 로그가 정본이다. 보관 기간은 로그 보관 정책을 따른다.
- 사용자 클릭 → 해당 사용자 프로필로 이동.
- **사용자 검색**: 닉네임으로 전체 사용자를 찾는다(`GET /users/search`) — 친구를 추가하려면 먼저 사람을 찾아야 하므로 친구 기능의 진입점이다. 친구 목록 안의 이름 필터와는 대상이 다르다.

**차단**

> 친구 기능 중 가장 마지막에 구현한다. 아래는 지금까지 정한 방향뿐이고, **API·테이블·노출 규칙은 구현할 때 구체화한다.**

- **대상 `userId`로 차단한다** — 친구 요청·삭제와 같은 경로 체계를 따른다. 차단·해제는 `POST`·`DELETE /users/{userId}/block`, 내 차단 목록은 `GET /users/me/blocks`다(api-spec 10-12·10-13).
- 차단한 사람의 프로필은 보이지 않는다.
- 차단한 사람은 초대할 수 없다.
- 차단 관계에서는 서로의 친구 목록이 보이지 않는다.
- **랜덤 매칭에서는 막지 않는다** — 매칭 후보를 거르는 조건은 슬롯·거리·자리뿐이라는 원칙(도메인 제약의 방 배정 기준)을 유지한다.
- **차단하면 친구 관계·대기 중인 요청이 끝난다** — 저장 구조(`user_relationships`)가 한 쌍에 관계를 하나만 두기 때문이다. 해제해도 친구로 돌아가지 않는다.
- 구현 때 정할 것: 차단이 양방향으로 보이는지, 대기 중인 초대를 정리하는지, 검색·추천·친구 목록·알림·같은 방 참가자에서 어떻게 가리는지, 차단된 쪽에 보이는 응답(404·403).

**설정 페이지**

- 계정: 이메일과 로그인 수단을 표시한다. 값은 앱 진입 때 받아 둔 `GET /users/me` 응답을 그대로 쓰고, 설정에서 따로 호출하지 않는다. 이메일을 보여주는 화면은 여기뿐이다.
  - 로그인 수단은 `oauth_users` row 유무로 가른다 — 있으면 그 provider, 없으면 로컬.
  - **소셜 계정**: "구글/카카오/애플 계정으로 로그인 중"을 표시하고 비밀번호 변경 항목을 감춘다 — 어느 provider로 가입했는지 잊고 다른 소셜 버튼을 누르면, 이메일이 같으면 `409 EMAIL_ALREADY_EXISTS`로 막히고 다르면 별개 계정이 만들어진다.
  - **로컬 계정**: 로그인 수단 문구 없이 비밀번호 변경 항목만 노출한다.
- 비밀번호 변경: **로컬 계정만.** 현재 비밀번호로 본인을 재확인하고 새 비밀번호를 받는다(가입과 같은 규칙 — 6~16자, 영문·숫자·특수문자 각 1자 이상. 확인 일치 검증은 클라).
  - 소셜 계정은 비밀번호가 없어 변경 대상이 아니다. 클라가 항목을 감추더라도 서버가 `409 PASSWORD_NOT_SET`으로 막는다 — 구버전 앱과 직접 호출이 있다.
  - 비밀번호를 바꿔도 발급된 토큰을 따로 끊지 않는다. 전 기기 로그아웃은 **[MVP 제외]**.
  - **로그인 세션은 계정당 하나다.** 리프레시 토큰을 유저 단위로 보관해, 다른 기기에서 로그인하면 이전 기기의 토큰이 덮어써진다. 이전 기기가 재발급을 시도하면 서버는 토큰 불일치를 탈취로 보고 저장된 토큰을 지운다 — 이전 기기는 로그아웃되고, 새 기기도 다음 재발급 때 다시 로그인해야 한다. 새 로그인과 탈취를 구분하는 것(세션 식별자를 토큰과 저장소에 두기)은 기기별 세션 유지와 함께 **[MVP 제외]**이며 전 기기 로그아웃과 함께 다룬다.
  - **비밀번호 찾기(로그인 전 재설정)는 없다** — 초기 페이지에 "비밀번호를 잊으셨나요" 진입점을 두지 않는다. 이 기능은 로그인된 상태에서만 쓴다.
- 알림 설정: 전체 알림 on/off 단일 토글(`users.alert_consent` — 매칭 확정, 러닝 시작 리마인더, 친구 요청 도착·수락 네 종류 전부 관장). 종류별 개별 토글은 **[MVP 제외]**.
  - **푸시에만 적용한다.** 인앱 알림함은 토글과 무관하게 쌓인다 — 앱을 열어 직접 보는 목록이라 방해가 되지 않고, 꺼 둔 사이에 온 초대·요청을 나중에라도 찾을 수 있어야 한다.
  - **기본값은 on**(`default true`) — 넷 다 거래성 알림이라 별도 수신 동의 대상이 아니고, 가입 직후부터 매칭 확정 푸시가 도달해야 한다.
  - 앱 내 토글은 OS 알림 권한과 별개다. 둘 중 하나라도 꺼져 있으면 푸시가 도달하지 않는다.
- 프로필 공개 범위 설정: `users.profile_visibility`(지인 마스킹 on/off).
- **피드 기본 공개 범위는 저장하지 않는다.** 피드마다 선택하고, 작성 화면 기본값은 클라이언트가 PUBLIC으로 둔다.
- 로그아웃/회원탈퇴: 확인 팝업 후 처리. **탈퇴 팝업은 삭제·보관 데이터와 기간을 보여준다** — 되돌릴 수 없다.
  - 로그아웃: `POST /auth/logout`(바디 없음 — 서버가 요청 토큰으로 본인 식별). 해당 access 토큰을 서버 블랙리스트에 올려 즉시 무효화하고(만료 전이라도 그 토큰 요청은 `401 TOKEN_BLOCKED`), **저장된 리프레시 토큰도 함께 지운다** — 남겨두면 재발급으로 새 access 토큰을 받아 계속 쓸 수 있다.
  - 로그아웃하면 그 유저의 푸시 기기도 전부 끈다(`is_active=false`) — 로그아웃한 기기에 푸시가 가지 않게 한다. 다시 로그인해 기기를 등록하면 켜진다.

### 공통 (특정 화면 소속 아님)

**앱 업데이트**

- 앱 진입과 포그라운드 복귀 때 최소·최신 버전을 받아 판정한다. 최소 미만이면 닫을 수 없는 업데이트 화면, 최신 미만이면 닫을 수 있는 안내를 띄운다.
- 최소·최신 버전은 서버가 플랫폼마다 따로 가진다(`app_versions`) — 정본은 서버 하나이고 운영이 직접 바꾼다.
- **최소 버전은 지원을 끝낼 때만 올린다** — 서버 변경으로 구버전과 호환이 깨지거나, 구버전에 꼭 고쳐야 할 결함이 있을 때다. 새 기능이 나왔다는 이유(푸시 지원 등)로는 올리지 않고 최신 버전으로 안내만 한다.
- **스토어에서 받을 수 있게 된 뒤에 올린다** — 받을 수 없는 버전을 요구하면 사용자가 업데이트 화면에서 못 빠져나온다(심사 중이거나, 안드로이드 단계적 출시 대상에서 빠졌을 때).
- **진행 중인 러닝이 없을 때 올린다** — 올린 뒤에는 러닝 중의 재연결·결과 조회도 거절되어 그 러닝을 잃는다.
  - 호환을 깨는 배포와 함께 올릴 때는 **서버를 멈춰 새 요청을 막고 → 진행 중인 러닝이 없는지 확인한 뒤 → 최소 버전을 올리고 배포한다 → 확인하고 다시 연다.** 확인만 하고 서버를 열어 두면 그 사이 새 러닝이 시작된다.
  - 올리기 전에 시작 전 매칭 신청이 몇 건인지 확인하고, 가능하면 적을 때 올린다 — 신청은 서버에 그대로 남지만, 시작 시각까지 업데이트하지 못한 사람은 미출석으로 처리되어 제재를 받고, 막힌 앱으로는 취소도 할 수 없다.
- **서버도 최소 버전 미만 요청을 처리 전에 거절한다** — 앱의 확인은 화면을 막을 뿐이라, 이미 떠 있던 구버전 앱의 요청이 호환을 깨는 배포 뒤 기록·상태를 틀어지게 할 수 있다. 앱은 모든 요청에 버전·플랫폼 헤더를 싣고, 서버는 헤더가 없거나 틀린 요청(헤더를 싣기 전 버전)도 같이 거절한다(`api-spec.md` 공통 규칙).

**알림 (인앱)**

- 인앱 알림함: 받은 알림을 최신순으로 보여준다. 종류는 셋이다 — **친구 요청 도착**, **친구 요청 수락됨**, **러닝 초대 도착**.
  - 항목마다 **지금 상태**를 함께 보여준다 — 친구 요청 알림은 그 사람과의 현재 친구 상태(수락·거절 버튼을 그릴지), 초대 알림은 그 초대의 현재 상태(대기중이면 수락·거절 버튼, 그 밖이면 결과 문구). 알림이 쌓인 뒤에 요청이 취소되거나 초대가 만료될 수 있어서다.
  - 알림을 누르면 종류별 화면으로 간다 — 친구 알림은 그 사람 프로필, 초대 알림은 수락했으면 초대 방 화면.
  - **읽음 표시가 있다.** 하단 탭에 안 읽은 알림 배지를 띄우고, 알림함을 열면 모두 읽음 처리한다. 항목별 읽음 처리는 두지 않는다.
  - **앱 진입 때 목록 첫 페이지와 안 읽은 수를 받고, 이후 새 알림은 앱 스트림으로 밀어 준다.** 앱이 켜져 있는 동안 여는 개인 스트림(api-spec 2-3 아래 앱 스트림 `/app/stream`)이 새 알림을 목록 항목과 같은 모양의 이벤트로 보내고, 클라는 목록 맨 위에 붙이고 배지를 하나 올린다. 알림은 DB가 정본이고 스트림은 통지일 뿐이라, 끊겨 있던 사이의 알림은 다음 진입 때 목록 조회로 복구한다. 앱이 꺼져 있을 때의 도달은 푸시가 붙을 때 해결한다.
  - 보관 기간은 운영 설정이다 — 지난 알림은 조회에서 빠진다.
- 매칭 확정·러닝 시작 리마인더는 알림함에 쌓지 않는다 — 그 순간에만 의미가 있고, 홈 화면 상태와 매칭 배너가 이미 보여준다.
- **[MVP 제외]** 피드 좋아요/댓글.

**알림 (푸시)**

- 매칭 확정, 러닝 시작 리마인더, 친구 요청 도착·수락 — 알림 종류별로 눌렀을 때 최적 화면으로 랜딩.
- **러닝 시작 리마인더는 시작 5분 전에 그때 방에 남은 참가자에게 보낸다.** 매칭 방은 마감 뒤라 확정된 인원이, 초대 방은 아직 모집 중이라 그때까지 들어온 사람이 받는다. 시작 시각이 지났으면 보내지 않고, 꺼져 있던 폰이 시작 뒤에 켜져도 받지 않는다.
- 앱은 data의 `type`으로 눌렀을 때 갈 화면을 고른다 — 리마인더는 `type=RUNNING_REMINDER`와 `runningRoomId`를 싣는다.
- **초대 알림의 푸시는 나중에 붙인다.** 지금은 인앱으로만 전달한다 — 그래서 초대받은 사람이 앱을 열기 전에는 모를 수 있고, 모집 마감 전에 응답하지 못하면 초대는 만료된다.
- **푸시는 유저당 마지막에 등록한 기기 하나로만 보낸다**(`user_devices`) — 로그인 세션이 계정당 하나라서다. 새 기기를 등록하면 이전 기기는 꺼진다. 다른 기기에서 로그인해도 전부 꺼진다 — 그 기기가 등록에 실패해도 세션이 끝난 이전 기기로 푸시가 가지 않게 한다.
- 알림을 껐거나, 로그인 세션이 없거나, 켜진 기기가 없으면 보내지 않는다.
- 앱 삭제·토큰 만료로 FCM이 받지 않는 토큰이면 그 기기를 끈다 — 그사이 앱이 새 토큰을 등록했으면 끄지 않는다.

## 2. 도메인 제약

> 전체 테이블·컬럼·타입·PK 규칙·enum·단위는 `erd.md`가 단일 출처. 여기서는 API 작성·구현에 필요한 도메인 제약과 설계 맥락만 남긴다.

**API 리소스 네이밍**: 방을 가리키는 이름은 DB·API·팀 대화 모두 **`room` 하나로 통일한다**(`running_rooms` ↔ `runningRoomId` ↔ `/running-rooms`).

- **"세션"은 방을 가리키는 말로 쓰지 않는다.** 이 단어는 로그인 세션·WebSocket 세션에 이미 쓰이고 있어 겹친다. 러닝을 서술할 때는 "러닝 구간", 방을 가리킬 때는 "방"으로 적는다.
- **`match-room`과 `running-room`은 API 단계 이름이다.** 전자는 모집 단계(매칭 신청·대기·초대 — 매칭 방과 초대 방 모두), 후자는 방 단위 동작(솔로 개설·결과 조회)을 가리킨다.
- 신청 즉시 방이 생기므로 `runningRoomId`는 매칭 단계에서도 존재한다. 다만 **경로 체계는 단계로 갈린다** — 매칭 단계의 내 신청은 방 ID를 URL에 쓰지 않고(`POST /match-rooms`·`POST /match-rooms/leave`·`GET /match-rooms/stream`), 특정 방을 가리켜야 하는 초대만 쓴다(`/match-rooms/{runningRoomId}/invitations`). 방 단계는 반드시 쓴다(`GET /running-rooms/{runningRoomId}/results`).

**매칭·러닝 설계**: 구간마다 통신 방식이 다르다 — **매칭은 REST + SSE**, **러닝 구간은 WebSocket**(`/api/v1/ws/running`)이다.

- 매칭 구간은 클라가 보내는 것이 신청·취소 둘뿐이라 양방향 채널이 필요 없다 — REST로 보내고 현황은 SSE 스트림(`/match-rooms/stream`)으로 받는다. 러닝 구간은 위치를 주기 발신하는 고빈도 양방향 구간이라 WebSocket을 쓴다.
- 대기 인원·성사·취소는 SSE 이벤트로 전달된다(`api-spec.md` 5번).
- **SSE 연결은 화면 생명주기에 묶지 않는다.** 매칭 대기 중 현황 배너가 모든 화면에서 유지돼야 하므로 홈을 벗어나도 스트림은 살아 있어야 한다. 이는 클라이언트 아키텍처 제약이다.
- 방 상태 이벤트(`MATCH_STARTED`·`MATCH_ROOM_UPDATED`, 초대 방은 `INVITE_ROOM_ENTRANCE`·`INVITE_ROOM_UPDATED`)는 **전체 상태를 담는다** — 놓친 이벤트를 되짚을 필요가 없어 재연결은 곧 스냅샷 재수신이다. 앱 재시작처럼 스트림이 끊긴 뒤에는 다시 연결할 때 오는 스냅샷이 같은 정보를 돌려준다. `RUNNING_READY`는 스냅샷으로 다시 오지 않으며, 놓치면 아래처럼 기기 시각으로 대신한다.
- **SSE → WS 전환**: `start_at` 직전에 WS를 연결하고(`RUNNING_READY`를 기다리지 않는다), 서버의 `RUNNING_READY`가 준 `startsInMs`로 타이머를 걸어 `start_at`에 `RUNNING_START`를 보낸다. `RUNNING_STARTED` ack를 받은 뒤 SSE를 닫는다. 이벤트가 유실되면 기기 시각으로 `start_at`을 넘겼는지 보고 그냥 보낸다.
- 메시지 네이밍 규칙: 클라 발신 현재형 / 서버 발신 과거형.

**방 배정 기준**: **후보를 거르는 조건은 슬롯·거리·자리뿐이다.** 같은 `start_at`·`target_distance`로 모집 중이고 자리가 남은 방이면 전부 후보다. 페이스와 이탈 이력은 **그중 어느 방에 넣을지를 정하는 순서**일 뿐 자격이 아니다.

- 순서는 ① 신청자 페이스와 방 평균(`running_rooms.avg_pace`)의 차가 작은 방 ② 같은 구간이면 **신청자 본인이** 그 방을 나간 횟수(`running_room_sessions.leave_count`)가 적은 방 ③ 그래도 같으면 오래된 방(`running_room_id`)이다. ①은 차이를 운영값 단위로 끊어 같은 구간이면 동급으로 본다 — 그래야 ②가 순위를 가른다.
- **페이스가 아무리 멀어도 매칭한다.** 페이스 차로 후보를 쳐내면 함께 뛸 사람이 있어도 각자 1인 방으로 흩어진다 — 혼자 뛰게 두는 편이 더 나쁘다. 새 방은 **후보가 하나도 없을 때만** 연다.
- **전에 나왔던 방도 다시 들어간다.** 이탈 이력은 선택지가 여럿일 때 뒤로 미룰 뿐이고, 그 방이 유일한 후보면 그대로 배정한다.
- **①이 ②보다 위인 이유**는 같이 뛰는 경험을 결정하는 것이 결국 페이스라서다. 그래서 세 번 나왔던 방이라도 페이스가 더 가까우면 그 방으로 간다. ①의 구간 폭이 곧 "페이스 위주 ↔ 이력 위주" 손잡이다.
- **방 평균은 참가자 페이스의 산술 평균이라 편차가 큰 방에서는 실재하지 않는 값이 된다** — 330과 453이 한 방이면 평균은 391인데 그 속도로 뛰는 사람은 없다. 페이스로 후보를 거르지 않으니 편차 상한도 없다. 배정 품질이 실제로 문제가 되면 방 평균 대신 "참가자 중 나와 가장 가까운 사람과의 차이"로 정렬하는 것이 다음 수순이다.

**이미지 업로드**(`feed_images`, `users.profile_image_key`·`users.background_image_key` 등 전체 공통): Presigned URL 방식 — 클라이언트가 업로드용 presigned URL 요청 → 서버가 S3 presigned URL 발급 → 클라이언트가 S3에 직접 업로드 → 반환받은 key를 본 API(피드 작성, 프로필·배경 사진 변경 등) 요청에 포함해 전달.

**GPS 트랙**: 원본 트랙은 Postgres 테이블이 아님 — `running_records.gps_track_key`로 S3 객체를 참조. **매칭 러닝과 솔로 러닝이 같은 경로를 쓴다.**

- 클라이언트가 1~2초 간격으로 좌표를 수집해 **로컬에 쌓으면서** 10초마다 모아서 WS로 보낸다. 서버는 Redis(`runningRoomId+userId` 키)에 버퍼링하고, 종료 신호·목표 도달·강제 종료에 기록 생성 가능한 트랙이면 S3와 `running_records`에 저장한다.
- **러닝 중 상태는 DB가 아니라 Redis가 원본이다** — 좌표·누적 거리·참가자 상태·콤보 판정 상태 모두. Redis는 DB 앞의 캐시가 아니라 러닝 동안의 저장소이고, DB에는 종료 때 확정본만 옮긴다(write-behind).
  - 배치 하나가 상태 저장소를 읽기 약 4번·쓰기 약 5번 오간다. DB에 두면 이 왕복이 그대로 RDS 쓰기가 되고, 같은 방 참가자의 배치가 같은 콤보 관계 행을 동시에 갱신한다.
  - 종료 확정은 참가자·방 행을 잠근 채 러닝 하나치 좌표(5km면 수천 개)를 통째로 읽는다. 읽는 시간이 곧 잠금을 쥐는 시간이라, 같은 양을 읽어도 저장소가 느리면 같은 방의 다른 종료가 그만큼 줄을 선다.
  - **같은 부하로 RDS와 비교했다**(러너 1,000명까지, `load_test/RESULTS.md`). 사용자 체감은 같았지만 DB 쪽은 1,000명에서 커넥션 10개를 다 써 여유가 없었다. 그래서 Redis에 둔다.
  - **관측**: 상태 저장소 왕복의 횟수·시간을 `phase`(러닝 중 / 종료)로 갈라 남기고, 종료 집계 읽기는 읽은 개수를 함께 남긴다(`metrics-convention.md`의 `runiverse.running.state.*`). 저장소를 바꿔 끼운 어댑터도 같은 메트릭을 `store`만 달리 기록해, 같은 부하로 Redis와 DB를 비교한다.
- **거리·페이스·구간 분할은 서버가 받은 좌표로 계산한다.** 클라이언트 계산값은 러닝 중 화면 표시용이지 저장값이 아니다. 계산 전에 오염된 좌표를 거른다 — 아래 트랙 필터 절.
- 칼로리는 러닝 중 표시하거나 전송하지 않는다. 종료 시 서버가 확정 거리·시간과 사용자 체중으로 전체·구간 칼로리를 계산해 결과에만 제공한다.
- **화면에 그리는 경로는 S3가 아니라 DB에서 나간다.** 기록 생성 시 원본 트랙을 0m부터 10m마다의 경계점으로 줄이고, 끊긴 곳에서 조각으로 나눠 조각마다 `running_segments.route_polyline`(encoded polyline)으로 저장한다. 기록 상세는 조각별로 쓰고, 피드 카드는 조각을 이어 한 줄로 쓴다. 기록 목록은 경로를 쓰지 않는다. S3 원본은 재계산·분석용으로 남는다.
- **좌표에는 기기 GPS 고도를 포함한다.** 서버가 노이즈를 필터링해 고도 지표를 계산하며 외부 고도 API는 쓰지 않는다.
- **위치 배치에는 ack가 없다.** 재연결하면 클라이언트가 로컬 트랙 전체를 처음 `sequence`부터 다시 보내고, 서버는 이미 받은 순번을 무시한다. 로컬 트랙은 `RUNNING_FINISHED`를 받은 뒤 삭제한다 — `RUNNING_FINISH`의 ack든 목표 도달 자동 종료든 같다.
  - 연결이 복구되지 않으면 서버가 강제 종료 시각에 마지막 수신 데이터로 처리하므로 재연결 전 로컬에만 남은 구간은 기록에 포함되지 않는다.
- **솔로 러닝도 방을 만든다.** `running_rooms`는 개시 즉시 `type='SOLO'`, `status='MATCHED'`이고 참가자는 `JOINED`로 생성된다. 같은 WS를 쓰며 클라이언트가 만들 수 있는 방은 솔로뿐이다.
  - **솔로가 `MATCHED`에서 출발하는 이유**: 모집을 건너뛸 뿐 그 뒤는 매칭과 같은 길이어야 한다. 확정된 방에 WS로 붙어 `STARTED`·`RUNNING`으로 넘어가는 구간이 두 종류에서 한 벌로 유지되고, 핸들러가 `type`으로 분기하지 않는다.
    - **`RUNNING_START`의 상태 전환 규칙은 하나뿐이다** — `MATCHED`이고 `start_at`이 지났으면 `STARTED`로 올린다. 매칭 방은 정각의 시작 스케줄러가 이미 올려놔 통과하고(스케줄러가 밀렸으면 가장 먼저 도착한 참가자의 것이 대신 올린다), 솔로는 `start_at`이 개시 시각이라 본인 것이 올린다. 규칙이 하나라 핸들러가 `type`으로 분기하지 않는다.
    - **시작 스케줄러는 매칭 방에만 건다.** 솔로는 `start_at`이 곧 개시 시각이라 예약을 거는 순간 이미 발화 시각이고, 방을 만든 클라가 곧바로 WS로 붙는다. 매칭 방에 거는 이유는 **아무도 붙지 않아도 방이 `MATCHED`에 갇히지 않게** 하기 위해서다 — `MATCHED`는 `FINISHED`로 갈 수 없어 그대로 두면 종료 처리가 취소밖에 못 한다.
  - 대신 **방만 만들고 채널에 붙지 않은 솔로 방**이 생길 수 있다. 시작하지 못한 방은 활성 신청으로 남아 다음 러닝을 막는다. **강제 종료 예약은 매칭 방에만 걸어 서버는 이 방을 닫지 않는다** — 앱이 다시 켜질 때 `GET /users/me/status`가 솔로도 `READY`/`RUNNING`과 `runningRoomId`를 돌려주므로, `READY`면 `POST /match-rooms/leave`로 정리하고 `RUNNING`이면 다시 붙어 끝낸다. 러닝 중 앱이 죽은 솔로 방도 같은 경로로 푼다.

**트랙 필터**: 기록 계산(거리·시간·구간·경로) 전에 오염된 좌표를 거른다. 멈춘 동안의 흔들림, GPS 튐, 관측하지 못한 이동이 그대로 섞이면 기록이 부풀고, 그 기록으로 다시 내는 평균 페이스가 다음 매칭을 틀어지게 한다. **판정은 좌표만으로 한다**(좌표에 실린 `pauseSegment` 포함) — 일시정지 신호처럼 유실·조작될 수 있는 값은 쓰지 않는다.

- **칸 단위로 판정한다.** 순번(`sequence`) 순으로 이웃한 두 좌표를 한 칸으로 보고, 칸마다 인정 거리·인정 시간을 정한다. 거부한 칸은 **거리와 시간을 함께 0으로** 한다 — 하나만 빼면 시간 없이 거리만 늘거나 그 반대가 돼 10m 구간 페이스가 틀어진다.
- **좌표는 지우지 않는다.** S3 원본 트랙은 받은 그대로 남고 필터는 계산할 때만 적용한다. 규칙이나 판정값이 바뀌면 원본으로 다시 계산할 수 있다.
- **순서는 ⓪ 일시정지 경계 → ① 정확도 → ② GPS 튐 → ③ 관측 안 된 칸 → ④ 정지다.** 튄 점이 먼저 빠져야 정지 판정의 기준점이 흔들리지 않는다. ⓪은 칸 판정 중 가장 먼저 보는 것이고, 판정 대상은 ①·②가 점을 뺀 뒤 남은 이웃이다.
  - 구현은 ④를 ③보다 먼저 판정한다 — ③의 직전 속도에서 정지 구간을 빼야 해서다. 반경을 벗어나는 칸은 인정 여부와 무관하게 기준점을 새로 잡고, 반경 안에서 빈 칸은 그 칸 하나로 정지 최소 시간을 넘겨 항상 정지가 되므로 결과는 같다.
  0. **일시정지 경계**: `pauseSegment`가 다른 이웃 두 좌표 사이 칸은 일시정지 동안 관측하지 않은 칸이다. 다른 판정보다 먼저 거리·시간을 모두 0으로 한다. 이동 거리·속도와 무관하다 — ③으로 판정하면 일시정지한 채 뛰는 속도로 옮긴 거리가 인정된다.
     - **이웃은 ①·② 뒤에 남은 점끼리다.** 원본 이웃으로 판정하면 경계 옆 점이 정확도로 빠질 때 새로 생긴 칸(일시정지 직전 → 재개 뒤 둘째 점)이 경계로 잡히지 않고 ③으로 인정된다. 번호는 줄지 않으므로(api-spec) 점이 빠져도 경계는 사라지지 않는다.
     - **경계에서 판정을 새로 시작한다.** ② 튄 점 판정은 번호가 다른 점끼리 비교하지 않는다(경계 너머 점과 비교하면 일시정지 중 이동이 튐처럼 보인다). ④ 정지는 경계에서 머문 시간 판정을 마치고 경계 뒤 첫 좌표를 새 기준점으로 삼는다(경계 앞뒤 몇 걸음이 일시정지 시간과 묶여 정지로 빠지지 않게 한다). 누적 상승·구간 고도차의 기준 고도도 경계에서 새로 잡는다. ④는 반경 비교보다 경계 비교를 먼저 한다 — 반경 안에서 재개하면 경계 칸이 정지 범위에 들어가 같은 칸을 두 번 뺀다. 경계 바로 옆에서 튄 점은 ②에서 점째로 빠지지 않고, 그 칸이 튐 칸으로 0이 된다.
  1. **정확도**: `accuracyMeters`가 상한보다 나쁜 좌표는 계산에서 뺀다.
  2. **GPS 튐**: 칸 속도가 최대 속도를 넘으면 사람이 낼 수 없는 이동이다(속도 문턱 필터). 튀었다 돌아온 점(앞뒤 칸이 모두 넘고, 그 점을 건너뛴 칸은 정상)은 점째로 빼고, 튄 자리에서 이어 가면 넘은 칸 하나만 0으로 한다. 좌표 시각이 초 단위라 시간 차는 최소 1초로 본다. 같은 `pauseSegment` 안에서만 비교한다(⓪).
  3. **관측 안 된 칸**: 수집 간격이 문턱을 넘는 칸은 중간을 보지 못한 칸이다(정상 수집은 1~2초 간격). **거리 ≤ 상한, 속도 ≥ 하한, 속도 ≤ 직전 속도 × 배율**을 모두 만족할 때만 인정한다. 직전 속도는 이 칸 앞 일정 시간 동안의 평소 칸(정지·튐·관측 안 된 칸이 아닌 칸)들의 거리 합 ÷ 시간 합이고, 그 안에 평소 칸이 없으면(출발 직후·긴 정지 직후) 고정 상한을 쓴다.
     - **좌표만으로는 터널을 달린 것과 탈것으로 이동한 것을 가를 수 없다** — 서버가 받는 데이터가 같다. 그래서 정해진 알고리즘이 아니라 휴리스틱이며, 틀렸을 때 손해가 작은 쪽(거부)으로 기울인다. 잃은 거리는 더 뛰어 메울 수 있지만, 가짜 거리는 기록에 남아 되돌릴 수 없다.
     - **거리 상한을 두는 이유**: 칸이 길수록 양 끝으로 낸 평균 속도는 탈것 + 대기로 얼마든지 맞출 수 있다. 증명 없이 믿어 주는 거리를 상한으로 묶는다.
     - 속도 하한은 수집이 멈춘 동안 걸어서 옮긴 경우를 거른다. 버튼 일시정지는 ⓪에서 먼저 빠진다.
     - **연결 끊김은 해당하지 않는다.** 클라가 로컬에 계속 수집해 재연결 때 다시 보내므로 칸이 비지 않는다. 판정은 도착 시각이 아니라 수집 시각(`recordedAt`)으로 한다.
  4. **정지**: 기준점 반경 안에 최소 시간 이상 머문 구간을 정지로 본다(Stay Point Detection). 반경은 그 좌표의 `accuracyMeters`를 최소·최대 반경 사이로 자른 값이다 — 상한이 없으면 정확도가 나쁜 곳에서 달리는 사람도 반경 안에 머문 것으로 잡힌다.
     - 들고 다니는 상태는 기준점 `a`와, 반경 안에서 마지막으로 관측한 점 `inside` 둘이다. 첫 좌표가 첫 기준점이다. 반경 안 좌표가 오면 `inside`만 바꾼다. 반경 밖 좌표가 오면 `inside` 시각 − `a` 시각이 최소 시간 이상일 때 `a`~`inside` 사이 칸을 모두 0으로 하고, `inside` → 새 좌표 칸은 평소대로 센 뒤 새 좌표를 기준점으로 삼는다. 트랙이 끝날 때도 같은 판정을 한 번 더 한다.
     - **머문 시간은 반경 안에서 관측한 좌표의 시각으로만 잰다.** 반경 밖 좌표가 도착하기까지의 시간으로 재면 비었다가 멀리서 나타난 칸(터널)이 정지로 잡힌다.
     - 일시정지 버튼으로 멈춘 칸은 ⓪이 먼저 뺀다. 반경 안에서 비었다가 이어진 그 밖의 공백(수집 지연 등)은 이 규칙으로 잡힌다 — 빈 칸의 양 끝이 반경 안이다.
     - 정지 판정은 다른 단계가 0으로 한 칸을 따로 보지 않는다 — 기준점은 반경 밖 좌표가 올 때와 일시정지 경계를 넘을 때만 새로 잡는다.
  - **시계가 뒤로 간 칸은 거리·시간 모두 0이다.** 단말 재부팅·시간대 변경으로 다음 좌표의 측정 시각이 앞 좌표보다 이르면 시간을 믿을 수 없다 — 시간만 0으로 두고 거리를 인정하면 그 칸 페이스가 0이 된다. 한 점만 시계가 튀었다 돌아오면 그 점으로 드나드는 두 칸만 빠지고 기록은 정상으로 남는다. 뒤쪽 전체가 미래로 밀리면 기록 기간이 하루를 넘어 기록을 만들지 않는다.
- **시간은 움직인 시간이다.** `total_duration`과 구간 `duration`은 인정한 칸의 시간 합이다. `start_at`·`end_at`과 구간 시각은 실제 시각 그대로라, 멈춘 시간까지 포함한 전체 경과는 `end_at − start_at`으로 구한다. 클라가 일시정지 동안 경과 시간 표시를 멈추는 것과 맞춘다.
  - 버튼 없이 멈춘 시간도 빠지므로 결과의 시간이 러닝 중 화면 시간보다 짧을 수 있다.
  - 멈춘 시간을 그대로 두면 쉰 만큼 기록 페이스가 느려져 다음 매칭이 틀어지고, 페이스 상한(3600초/km)을 넘겨 기록 자체가 사라질 수도 있다.
- **경로**: 0으로 한 칸 위에는 10m 경계점이 찍히지 않는다. 정지 구간은 앞뒤 경계점 사이 직선(최대 반경 이하)으로 건너뛰고, 거부한 칸(일시정지 경계 포함)의 양 끝 경계점은 polyline에서 바로 이웃한다. 중간 좌표는 polyline에 들어가지 않는다.
  - **끊긴 곳에서 경로를 조각으로 나눠 저장한다**(`running_segments` — 기록 1 : 조각 N : 구간 N). 이웃한 두 경계점 사이에 0으로 한 칸이 있고 그것이 ④ 정지가 아니면 — ⓪ 일시정지 경계, ② GPS 튐, 거부한 ③ 관측 안 된 칸, 시계 역행 — 앞 점에서 조각을 닫고 뒤 점에서 새 조각을 연다. 기록 상세(6-1)는 조각마다 좌표 배열 하나로 내리고, 클라는 조각 사이를 잇지 않는다.
    - 간격으로 짐작하지 않고 필터 판정을 그대로 쓴다. 30m 같은 문턱은 일시정지 중 짧게(약 40m 이하) 옮긴 자리를 이어 그리고, 최대 반경을 바꿀 때마다 함께 맞춰야 한다.
    - 정지는 끊지 않는다 — 제자리라 앞뒤 경계점을 이어도 최대 반경 안의 직선이다.
    - 조각은 경계점을 나눌 뿐 점을 더하거나 빼지 않는다 — 조각을 이으면 기록의 경계점 전체다. 구간 번호는 조각과 무관하게 기록 전체에서 이어 센다.
    - **구간은 끝 경계점이 있는 조각에 속한다.** 구간의 경로 범위는 그 조각 안의 점 번호다. 끊긴 곳에 걸친 구간(일시정지 직전 경계점 → 재개 뒤 첫 경계점)은 뒤 조각의 첫 점 하나(`[0, 0]`)만 가리켜 6-2에서 선을 긋지 않는다. 거리 10m·움직인 시간은 다른 구간과 같다.
    - 콤보 점은 조각을 모른다 — 기록의 경계점 중 달성 시각에 가장 가까운 좌표를 고를 뿐이다.
    - 끊긴 곳 앞뒤로 10m가 안 되는 이동은 그려지지 않는다 — 경계점이 인정 거리 10m마다라서다. **[이후]** 일시정지·재개 지점을 조각 끝점으로 넣는다(경계점 수 = 구간 수 + 1 규칙과 분리해야 한다).
  - **피드 카드(8-1)는 조각을 이어 한 줄로 다시 인코딩한 `routePolyline`을 쓴다** — encoded polyline은 앞 점과의 차로 인코딩돼 문자열을 그대로 이어 붙이면 깨진다. 이웃한 경계점 사이 직선거리가 30m를 넘으면 클라는 선으로 잇지 않는다 — 인정한 칸만 지나면 10m 이하이고 정지를 건너뛰어도 10m + 최대 반경 이하라서다. 미리보기라 일시정지 중 짧은 이동이 이어 그려지는 것은 감수한다.
  - 인정한 관측 안 된 칸(짧은 터널)은 직선 위에 경계점이 10m마다 찍혀 직선으로 그려진다.
- **판정값은 전부 운영 설정이다**(`running-track-filter.*`). 휴리스틱이라 실제 트랙으로 조정한다. 아래는 시작값이다.

  | 단계 | 설정 | 시작값 |
  |---|---|---|
  | 정확도 | 정확도 상한 | 50m |
  | GPS 튐 | 최대 속도 | 12m/s |
  | 관측 안 된 칸 | 수집 간격 문턱 / 거리 상한 / 속도 하한 / 직전 속도 배율 / 직전 속도 창 / 직전 속도가 없을 때 상한 | 10초 / 500m / 1.5m/s / 1.3 / 300초 / 7m/s |
  | 정지 | 최소 반경 / 최대 반경 / 최소 시간 | 5m / 8m / 10초 |

  - **값 사이 관계는 앱 시작 때 검사한다.** 최대 반경 ≥ 최소 반경, 그리고 최대 반경 ÷ 최소 시간 < 관측 안 된 칸 속도 하한 — 반경 안에 최소 시간 머물렀다는 것은 그동안 평균 속도가 최대 반경 ÷ 최소 시간 이하였다는 뜻이라, 이 값이 하한보다 크면 한 방향으로 걷는 사람도 정지로 잡힌다.
    - 관측 안 된 칸 문턱 ≥ 정지 최소 시간 — 반경 안에서 비었다가 이어진 칸(일시정지 외의 공백)이 그 칸 하나로 항상 정지가 되게 한다. 이 관계가 있어야 ③과 ④의 판정 순서가 결과를 바꾸지 않는다.
  - 판정값을 바꿔도 이미 저장한 기록은 다시 계산하지 않는다(유효 러닝 판정과 같다).
- **감수하는 한계**
  - 반경 안에서 최대 반경 ÷ 최소 시간보다 느린 실제 이동은 기록되지 않는다 — 정지 1회당 최대 반경 이하다. 그 속도는 기록 대상이 아닌 속도로 정의한다.
  - 정확도가 최대 반경보다 나쁜 곳에서는 흔들림이 일부 남는다.
  - **수집이 멈춘 동안의 긴 이동은 실제로 뛰었어도 기록되지 않는다**(폰 꺼짐·앱 강제 종료). 증명할 데이터가 없다. 거리 상한 이하의 짧은 공백만 인정한다.
  - 거리 상한보다 긴 터널·지하 구간을 지나면 그 구간을 잃는다. 목표가 있는 방은 남은 거리 안내(아래 개인 단위 진행 상태 절)를 받아 더 뛰면 완주할 수 있다.
  - 짧은 공백을 자기 페이스와 비슷한 속도로 탈것을 타고 넘으면 걸러지지 않는다 — 얻는 거리는 거리 상한으로 묶인다. 버튼 일시정지로 만든 공백은 ⓪으로 빠지므로, 남는 것은 버튼 없이 수집이 끊긴 공백이다.
  - **재개 직후 GPS를 다시 잡기까지 뛴 거리는 빠진다** — 그 이동이 경계 칸에 묶인다.
  - **`pauseSegment`는 클라 규칙에 기댄다.** 버튼 일시정지가 아닌 때 올리면 그 자리 이동이 빠지고, 올리지 않으면 그 공백은 ③으로 판정된다. 줄어드는 번호는 입구에서 거부하지만, 재연결로 뒤늦게 메워진 좌표(마지막 반영 순번보다 작은 것)는 앞뒤 이웃과 비교하지 못한다.
  - 좌표가 계속 오는 탈것 이동(버스·자전거)은 칸마다 속도가 정상이라 걸러지지 않는다 — 구간 단위 페이스 검사가 필요한 별도 과제다.
  - **[이후]** 러닝 중 누적 거리(진행 통지·콤보·자동 종료 판단)는 필터를 거치지 않아 흔들림이 섞인다. 기록·완주 판정에는 영향이 없다 — 끝내기 직전에 확정 거리로 다시 판정한다.
    - **단 ⓪ 일시정지 경계는 누적에서도 뺀다.** 누적이 자동 종료 판단과 콤보 거리 차에 쓰여, 빼지 않으면 일시정지 중 이동으로 목표에 닿거나 앞선 참가자와 콤보가 붙는다. 확정 거리도 같은 칸을 빼므로 "같은 좌표라면 누적 ≥ 확정 거리"는 그대로다 — 번호가 줄지 않고(입구에서 거부) 재전송값이 처음과 같다는 전제다.
    - **콤보**: 멈춘 사람에게 콤보가 붙는 문제는 누적 거리가 아니라 의심점으로 막는다(아래 러닝 콤보 절의 참가자 상태). 남는 것은 서 있는 동안의 흔들림이 누적에 섞여, 다시 달리기 시작한 뒤 상대와의 거리 차가 그만큼 벌어져 보이는 것이다 — 창(30m)보다 크면 끊긴다.
    - 자동 종료 판단에는 문제가 없다. 같은 좌표라면 누적 ≥ 확정 거리라, 누적이 목표를 넘을 때만 확정 거리를 내는 관문이 완주를 놓치지 않는다. 대가는 누적만 목표를 넘은 동안 배치마다 재확인이 도는 것이다.
    - 재연결로 뒤늦게 채워진 좌표는 누적에서 빠지고 확정 거리에는 들어가, 드물게 확정 거리만 목표를 넘은 순간이 있다. 다음 배치가 누적을 넘기면 바로 끝나고, 사용자가 종료(`forced=false`)를 누르면 확정 거리로 판정해 완주다.
- **[이후]** 걸음 수 — 클라가 좌표마다 누적 걸음 수를 보내면 관측 안 된 칸을 걸음 수 × 보폭으로 검증할 수 있다(걸음 센서는 GPS 없이 동작한다). 좌표 필드 추가라 API 계약 변경이다.
- **관측**: 기록을 확정할 때마다 필터 결과를 로그 한 줄로 남기고(원본 거리·필터 거리·단계별로 뺀 거리·일시정지 경계 수·정지 수와 시간·관측 안 된 칸의 인정·거부 수와 최대 길이), 단계별로 뺀 거리와 관측 안 된 칸의 인정·거부를 메트릭으로 남긴다(`metrics-convention.md`). 원본 좌표는 로그에 남기지 않는다 — 들여다볼 러닝은 로그의 `roomId`·`userId`로 S3 원본을 찾아 다시 계산한다. 확정 거리가 목표에 못 미쳐 종료를 미룰 때도 일시정지 경계 수와 뺀 거리를 함께 남긴다 — 화면은 목표 도달인데 서버가 미루는 원인이 일시정지인지 가른다.

**러닝 콤보**: 러닝 중 참가자 둘이 비슷한 지점을 달리는 동안 쌓이는 지표다. 판정 상태는 Redis에만 두고, **방이 `FINISHED`로 닫힐 때 붙었다 끊긴 구간을 `running_combos`에 남긴다**(누구와·언제·각자 경로의 어디서 몇 콤보를 달성했나). 결과·기록 응답에는 아직 콤보 필드를 두지 않는다.

- **구간 단위로 남긴다.** 끊겼다 다시 붙으면 새 구간이다 — 끊긴 사이를 빼고 각 구간을 경로 위에 따로 그릴 수 있다. 최고 콤보는 구간에서 계산한다(`MAX(combo_count)`). 유지 횟수가 0인 구간은 남기지 않는다.
- **방이 닫힐 때 한꺼번에 쓴다.** 한 행에 두 참가자의 달성 위치가 들어가므로 둘 다 기록이 확정된 뒤여야 한다 — 먼저 끝낸 참가자의 콤보는 그때 이미 바뀌지 않지만, 상대의 기록이 없어 행을 완성할 수 없다. 끊긴 구간은 Redis 구간 목록에 쌓아 두고, 그때까지 이어지던 관계는 쌓인 시각에서 닫아 함께 넣는다. 저장한 뒤 방의 콤보 키를 지운다.
  - **방 닫힘이 커밋된 뒤 별도 트랜잭션에서 쓴다.** 같은 트랜잭션이면 콤보 읽기·저장이 실패할 때 마지막 참가자의 종료까지 롤백되고, 그동안 방·참가자 잠금을 쥔다. 대가로 실패하거나 그 사이 서버가 죽으면 그 방의 콤보는 남지 않는다(ERROR 로그, Redis 키는 TTL까지 남는다). 콤보는 아직 응답에 실리지 않는 곁가지 지표라 종료를 지키는 쪽을 택한다.
  - `CANCELLED`로 닫힌 방은 기록이 없어 남기지 않고, 콤보 키만 지운다.
  - 방이 열려 있는 동안 콤보는 Redis에만 있다 — 나중에 콤보를 조회하는 API가 생기면 열린 방은 Redis, 닫힌 방은 DB를 읽는다.
  - **구간은 끊기는 순간에만 쓴다.** 방마다 해시 하나(`running:combo:{roomId}:seg`)에 `쌍|시작 시각` → `끝 시각|유지 횟수`로 둔다. 시작 시각까지 칸 이름에 넣어, 같은 쌍의 두 참가자가 서로 다른 서버에서 같은 관계를 함께 끊어도 같은 칸을 덮어쓴다.
  - **구간 저장이 관계 저장보다 먼저다.** 관계를 끊긴 채로 저장한 뒤 구간 저장이 실패하면 그 구간은 되살릴 수 없다. 거꾸로면 관계가 이어진 채로 남아 다음 배치가 같은 구간을 다시 닫는다.
  - **관계는 쌓인 시각을 함께 들고 있다**(아래 유지 횟수) — 끊길 때 구간의 끝(`end_at`)이 된다. 최고 콤보는 관계 전체의 값이라 구간 끝을 대신할 수 없다. 이 값을 싣기 전에 저장된 관계가 끊기면 끝을 알 수 없어 그 구간만 남기지 않는다.
  - 구간 번호는 Redis에 두지 않는다 — 닫을 때 시작 시각 순으로 매긴다.
- **콤보 1회마다 경로 위 점 하나를 남긴다.** 클라는 기록의 경로 위에 콤보를 점으로 찍는다. i콤보의 점은 각자 기록의 10m 경계점 중 달성 시각(시작 시각 + i × 1회 길이)에 가장 가까운 점이다 — 러닝 중 화면 숫자가 i로 바뀐 순간의 자리다. 그 10초 안에 경계점이 없어도(아주 느리게 달렸다) 가장 가까운 점이 잡힌다.
  - **새 좌표를 만들지 않는다.** 기록 경로의 경계점을 그대로 골라 그려진 경로에서 벗어나지 않는다. 경계점 시각은 `running_splits`에서 얻는다.
  - **거리가 아니라 시각으로 찾는다.** 판정에 쓴 누적 거리는 트랙 필터 전 값이라 거리로 찾으면 확정 경로와 어긋난다. 시각은 하나뿐이다.
  - 그 참가자의 기록이 없으면 비운다.

- **거리는 좌표가 아니라 누적 주행 거리로 잰다.** 원격 동반 러닝이라 참가자들은 각자 다른 장소에서 뛴다 — 좌표상 근접은 아예 성립하지 않는다. 3,500m를 지난 사람과 3,480m를 지난 사람이 "20m 차이"다.
- **콤보는 사람이 아니라 관계에 붙는다.** A-B·A-C·B-C가 각각 독립적인 콤보를 갖고, 방 정원이 4명이라 관계는 최대 6개다.
  - 사람 단위로 세면 옆 사람이 B에서 C로 바뀌어도 콤보가 이어져 "누구와 얼마나 오래 함께 뛰었나"를 잃는다. 최고 콤보를 남긴 상대를 뽑으려면 관계마다 세는 수밖에 없다.
  - **각자 자기 창만 본다.** A-B가 20m, B-C가 20m, A-C가 40m면 B는 양쪽과 콤보지만 A와 C는 서로 아니다. 연결된 참가자를 한 무리로 묶으면 창을 두 번 건너뛴 사람까지 들어와 거리 기준이 무의미해진다.
- **판정은 위치 배치가 도착할 때마다 돈다.** 처음 들어온 `RUNNING_START`에서도 한 번 돌아 참가자의 기준(누적 거리·상태)을 세운다(재연결에는 다시 돌지 않는다). **출발선에서는 콤보가 붙지 않는다** — 둘 다 서 있어 아래 참가자 상태가 서 있음이다. 둘 다 출발해 의심점을 벗어나야 붙는다. 별도 스케줄러를 두지 않는다 — 서버가 러닝 중 정보를 얻는 경로가 그것뿐이라 판정 해상도는 배치 주기와 같다. 배치를 모아 두었다가 한꺼번에 처리하지도 않는다: 방 전체의 누적 거리가 이미 저장돼 있어 어느 배치가 도착하든 그 자리에서 전체를 판정할 수 있다.
  - **상태를 바꾸는 것은 보낸 참가자가 낀 관계뿐이다.** 나머지 관계는 값을 읽어 응답에 담기만 한다. 무관한 참가자의 배치가 남의 콤보를 끊어서는 안 된다.
- **함께 달린 것만 센다 — 판정 전에 참가자마다 상태를 정한다.** 누적 거리만 보면 서 있는 사람을 지나가는 사람, 출발선에 함께 선 두 사람에게 콤보가 붙는다.

  | 상태 | 조건(위에서부터 먼저 걸리는 것) | 예 |
  |---|---|---|
  | 일시정지 | 일시정지 표시가 있거나, 이번 배치가 일시정지 경계를 넘었다 | 사용자가 멈춤 |
  | 관측 없음 | 마지막 관측이 신선도 문턱보다 오래됐다 | 터널, 연결 끊김 |
  | 서 있음 | 관측은 있는데 의심점이 신선도 문턱보다 오래 그대로다 | 신호 대기, 출발선 |
  | 달리는 중 | 그 외 | |

  - **의심점**: 참가자가 머물고 있다고 의심하는 기준 좌표다. 새 좌표가 의심점 반경 밖이면 의심점을 그 좌표로 옮기고 갱신 시각을 남긴다 — 의심점이 옮겨졌으면 분명히 움직였다. 첫 좌표가 첫 의심점이고, 아직 한 번도 옮겨지지 않았으면 서 있음이다. 반경은 트랙 필터의 정지 판정과 같다(정확도를 최소·최대 반경 사이로 자른 값) — 기록과 콤보에서 "멈춤"의 뜻이 같아야 한다. **일시정지 경계를 넘으면 의심점을 비운다.** 경계 뒤 첫 관측 좌표가 첫 의심점이 되어 이동으로 보지 않는다 — 일시정지 중 이동은 달린 것이 아니다. 경계 뒤 첫 좌표가 정확도가 나빠 관측이 아니어도, 경계가 배치를 넘어가도 같은 규칙이 저장된 의심점(비어 있음)으로 이어진다.
  - **관측**: 정확도가 트랙 필터 정확도 상한 이하인 새 좌표다. 재전송분(이미 받은 순번)과 정확도가 나쁜 좌표는 관측이 아니다 — 터널에서 정확도가 나빠진 좌표가 와도 관측 없음으로 본다.
  - **서 있음과 관측 없음을 가른다.** 좌표가 오는데 제자리면 멈춘 것이고, 좌표가 안 오면 무슨 일이 있었는지 모르는 것이다. 트랙 필터가 정지와 관측 안 된 칸을 따로 다루는 것과 같다.
  - **상태는 저장하지 않고 판정 시각에 계산한다.** 시각만 지나도 바뀌는 값이라(15초 전 관측은 달리는 중, 20초 전은 관측 없음) 저장하면 아무 일이 없어도 틀려진다. 저장하는 것은 의심점 갱신 시각·마지막 관측 시각·일시정지 표시뿐이다.
    - 의심점 좌표와 마지막 좌표의 `pauseSegment`는 참가자별 누적 거리 값에 함께 둔다 — 누적기가 같은 좌표를 훑으며 갱신하고, 배치마다 이미 읽고 쓰는 값이라 왕복이 늘지 않는다.
    - 두 시각은 방 단위 콤보 스냅샷(`running:combo:{roomId}:dist`)에 함께 둔다 — 판정이 방 전체를 한 번에 읽으므로 상대의 상태를 따로 조회하지 않는다.
    - 일시정지 표시는 같은 해시의 별도 칸(`{userId}:paused`)이다. 스냅샷 값 안에 넣으면 일시정지 이벤트와 위치 배치가 같은 값을 읽고 고쳐 써 한쪽이 사라진다.
  - **화면 상태(`RUNNING`·`PAUSED`·`DISCONNECTED`·`FINISHED`)와 별개다.** 화면 상태는 `RUNNING_PROGRESS_UPDATED`로 나가는 공개 값이라 콤보용 상태를 섞지 않는다.
  - **끊는 근거는 일시정지 신호와 일시정지 경계 둘이고, 끊는 쪽으로만 쓴다.** `RUNNING_PAUSE`를 받으면 일시정지 표시를 남기고, 관측이 다시 들어오면 지운다. 표시는 상대의 다음 배치가 판정해야 끊기므로, 신호가 유실되거나 그 전에 재개하면 놓친다 — 관측 없음으로 보류됐다가 재개 뒤 거리 차가 창 안이면 일시정지 시간까지 콤보로 세어진다. 그래서 일시정지 경계를 넘은 배치는 표시가 없어도 그 판정에서 일시정지로 본다. 대가로 재개 후 첫 배치에서는 새로 붙지 않아 한 배치 늦게 붙는다. 경계 배치의 판정이 저장소 오류로 실패하면 그 일시정지는 끊지 못해, 일시정지 시간이 콤보에 들어갈 수 있다 — 경계 신호는 그 배치 한 번뿐이라 다음 배치가 바로잡지 못한다. 실패는 ERROR 로그로 남는다. 조작해 봐야 자기 콤보를 잃을 뿐이다. 연결 끊김 신호는 쓰지 않는다 — 좌표가 안 오는 것으로 충분하고, 서버가 끊김을 늦게 알아채도 판정이 흔들리지 않는다.
- **쌍 판정은 두 참가자의 상태로 갈린다.** 위에서부터 먼저 걸리는 것으로 처리한다.

  | 조건 | 처리 |
  |---|---|
  | 한쪽이라도 일시정지 | 즉시 끊는다 — 봐주기를 쓰지 않는다 |
  | 한쪽이라도 서 있음 | 빗나감 |
  | 한쪽이라도 관측 없음 | 보류 — 쌓지도 깎지도 않는다 |
  | 둘 다 달리는 중, 거리 차가 창 밖 | 빗나감 |
  | 둘 다 달리는 중, 거리 차가 창 안 | 겹침 |

  - **일시정지는 사용자의 선택이라 바로 끊는다.** 길이와 무관하다. 다시 달리면 새 구간이다.
  - **관측 없음은 사용자 잘못이 아니라 기다린다.** 터널을 나오거나 재연결해 좌표가 다시 들어오면, 누적 거리가 따라잡은 뒤의 거리 차로 다시 판정한다. 그때도 창 안이면 그동안 같은 페이스로 달렸다는 뜻이라 콤보가 이어지고, 보류한 시간도 함께 세어진다(아래 쌓인 시각). 끝내 돌아오지 않으면 방이 닫힐 때 마지막으로 쌓인 시각에서 닫힌다.
  - **러닝을 끝낸 참가자는 바로 끊고, 다시 붙지 않는다.** 관측 없음으로 두면 좌표가 다시 오지 않아 상대 화면의 콤보가 방이 닫힐 때까지 남는다. 일시정지와 달리 늦은 좌표가 들어와도 풀리지 않는다 — 끝난 사람은 더 함께 달릴 수 없다. 구간은 쌓인 시각에서 닫혀 방이 닫힐 때와 같다.
  - **서 있음을 관측 없음보다 먼저 본다.** 한쪽이 터널에 있어도 다른 쪽이 서 있으면 그 시간은 함께 달린 것이 아니다. 거꾸로면 한 사람이 터널에 있는 동안 상대가 아무리 오래 서 있어도 끊기지 않는다.
- **유지 횟수는 저장하지 않고 시작 시각부터 쌓인 시각까지에서 계산한다** — 그 경과 시간을 1회 길이로 나눈 몫이다. 붙는 순간은 0이다. 화면의 `comboCount`도 같은 값이다.
  - **쌓인 시각은 두 참가자의 의심점 갱신 시각 중 이른 쪽이다** — 둘 다 움직였다고 확인된 마지막 순간이다. 겹침 판정마다 이 값으로 앞당겨 저장하고, 시작 시각보다 앞서지 않게 한다. 둘 중 하나라도 의심점이 그대로면 쌓이지 않는다.
  - 판정 시각으로 쌓으면 서 있음으로 바뀌기까지의 신선도 문턱 동안에도 겹침이 나서, 신호 대기 시간이 함께 뛴 시간으로 들어간다. 그렇다고 "이번 판정에서 둘 다 의심점이 바뀌었나"로 보면 배치가 엇갈려 도착해 함께 달리는 동안에도 판정의 절반이 안 쌓인다 — 갱신 시각을 비교하면 엇갈림과 무관하다.
  - 대가는 함께 달리는 중에도 숫자가 상대의 마지막 배치만큼(최대 한 배치) 늦게 올라가는 것이다. 화면에 뜬 숫자가 나중에 줄어드는 것보다 낫다.
  - 도착한 배치를 세면 인원이 많은 방과 재전송이 몰린 배치에서 같은 시간을 뛰고도 값이 부풀려지고, 전송이 성긴 참가자는 같은 시간을 뛰고도 적게 받는다. 시각에서 계산하면 누가 몇 번 보내든 같은 답이 나온다.
  - 재연결 시 클라이언트가 로컬 트랙을 처음부터 재전송하는 것과도 앞뒤가 맞는다 — 배치가 몰려 들어와도 시작 시각은 바뀌지 않는다.
  - **1회 길이는 위치 배치 주기와 맞춘다.** 짧으면 배치 하나에 숫자가 여러 칸 건너뛰고, 길면 배치를 몇 번 받아야 한 칸 움직여 화면이 멈춘 것처럼 보인다.
- **한 번 빗나가도 바로 끊지 않는다.** 관계마다 봐주는 횟수를 두고, 빗나가면 쓰고 다시 겹치면 되돌린다. 남은 횟수가 없는 상태에서 또 빗나가야 끊긴다.
  - 상대 데이터가 낡았거나 GPS가 튄 한 번의 판정으로 오래 쌓인 콤보가 사라지면 안 된다. 이 장치는 곧 "상대의 다음 보고를 한 번 더 기다린다"는 뜻이라, 시간으로 유예를 재는 것과 달리 배치가 빠르든 늦든 알아서 맞춰진다.
  - **당사자가 보냈을 때만 소모한다.** 방 전체를 훑는 판정에서 무관한 참가자의 배치가 함께 깎으면, 인원이 많은 방일수록 빨리 닳아 같은 설정이 방마다 다르게 동작한다.
  - **보류는 소모하지 않는다.** 관측 없음 동안 배치가 오가도 봐주기는 그대로다.
- **끊기면 시작 시각과 쌓인 시각을 지운다.** 다시 겹치면 그때가 새 시작 시각이고 콤보는 0부터다. 지우지 않으면 끊겨 있던 구간까지 함께 뛴 시간으로 세어진다.
- **최고 콤보는 겹쳤다고 판정된 순간에만, 쌓인 시각으로 갱신한다.** 봐주는 구간에도 시각은 흐르므로 끊기는 순간의 값으로 굳히면 실제로 함께 있지 않았던 구간이 기록에 섞인다. 콤보가 끊겨도 최고 콤보는 남는다.
- **기준 시각이 다른 누적 거리는 보정해서 비교한다.** 참가자마다 배치 도착이 어긋나 마지막 누적 거리의 기준 시각이 서로 다르다 — 각자의 마지막 속도로 판정 시각까지 민 값으로 맞춘 뒤 비교한다. 보정하지 않으면 배치 위상차만으로 생기는 오차가 판정 창과 맞먹어, 나란히 달리는 두 사람의 콤보가 판정마다 붙었다 끊긴다.
  - **달리는 중인 참가자만 민다.** 서 있거나 관측이 없는 참가자를 마지막 속도로 밀면 멈춘 사람이 계속 앞으로 가는 것으로 계산된다.
  - **신선도 문턱은 보정이 감당하는 범위와 함께 정한다.** 보정이 지난 만큼을 추측으로 채우므로, 문턱이 길수록 추측 거리가 판정 창을 넘어서 판정 자체가 무의미해진다. 짧으면 배치 하나만 늦어도 관측 없음·서 있음이 된다 — 배치 주기보다는 길어야 한다.
- **양쪽이 모두 조용하면 판정이 돌지 않는다.** 배치가 와야 판정이 도는데 둘 다 보내지 않으면 관계는 그대로 남는다. 누가 다시 보내면 그 시각의 상태로 판정하고, 끝내 아무도 보내지 않으면 방이 닫힐 때 마지막으로 쌓인 시각에서 닫힌다.
- **한계**
  - 러닝 중 누적 거리는 관측 없음 구간의 입구와 출구를 직선으로 잇는다. 휜 터널을 함께 지나도 거리 차가 벌어져 보여 끊길 수 있다.
  - 정확도가 상한 이하인데 위치가 튀는 좌표(빌딩 숲)는 의심점을 벗어나 달리는 중으로 보일 수 있다 — GPS 튐 필터 수준의 처리가 필요한 별도 과제다.
  - 콤보 시각은 서버가 배치를 받아 판정한 시각이라 실제보다 0~배치 주기(10초)만큼 늦다. 경계점 시각은 단말이 좌표를 잰 시각이라, 저장한 달성 위치가 실제보다 경계점 몇 개 뒤에 찍힐 수 있다. 판정 시각을 배치 안 마지막 좌표의 측정 시각으로 바꾸면 줄지만 판정 규칙을 건드리는 별도 과제다.
- 다섯 값은 운영 설정으로 뺀다 — **붙는 거리**, **끊기는 거리**, **신선도 문턱**(관측 없음·서 있음을 가르는 창), **유지 횟수 1회의 길이**, **봐주는 횟수**. 의심점 반경과 관측 정확도 상한은 트랙 필터 설정을 그대로 쓴다.
  - 붙는 거리와 끊기는 거리를 다르게 두면 경계에 걸친 두 사람이 판정마다 붙었다 끊기는 것을 막을 수 있다. 다만 봐주는 횟수가 이미 한 번의 어긋남을 흡수하므로 지금은 둘을 같게 둔다.
  - 봐주는 횟수를 0으로 두면 첫 판정에서 바로 끊는다 — 이 장치를 끄는 방법이다.

**컬러 시스템 [MVP 제외]**: 러닝 지표가 조건을 충족하면 고정 팔레트의 색이 열리는 **잠금 해제 모델**이다. 색을 새로 만들어내지 않는다.

- 생성 모델을 쓰지 않는 이유는 수집이 성립하지 않기 때문이다 — 색 공간이 무한하면 같은 5km를 100번 뛴 결과가 비슷한 색 100개로 쌓인다. **시그니처 컬러도 블렌드 색도 없다** — 사용자가 색을 고르는 지점이 서비스 어디에도 없다.
- 마스터(`colors`)는 운영이 채워 넣는 고정 데이터이고, 획득 이력(`user_colors`)은 복합 PK라 **같은 색을 두 번 얻는 상황이 없다**.
- 12범주 × 셰이드 3~4로 구성하되 **총 색 개수는 명세에 적지 않는다.** 진행률은 마스터 행 수로 계산하므로 색을 추가해도 코드가 바뀌지 않는다.
- **획득 조건은 DB에 두지 않는다.** 조건의 축이 제각각이라(단일 러닝 거리 / 누적 거리 / 페이스 …) 데이터로 표현하기 어렵다 — 판정은 서버 로직에, DB에는 안내 문구만 둔다.
- 범주별 획득 조건표와 자동 획득은 MVP에서 제외한다. 향후 판정을 위해 `total_elevation_gain`·`weather_code`·`temperature`는 지금부터 저장한다.

**피드-러닝 기록 연결**: `feeds.running_record_id`는 `running_records` 참조 — 피드 작성 시 "러닝 기록 템플릿 선택"에 대응. nullable — 러닝 기록 없이 글+사진만으로도 작성 가능.

**피드 공개 범위**: `feeds.visibility` 값은 3종(친구/전체/나만) — "나만"은 본인 피드 목록/프로필 그리드 조회 시에만 노출, 친구 피드·전체 피드 조회에서는 제외.

**날씨**: 홈 화면 날씨는 클라이언트가 키리스 무료 날씨 API(예: Open-Meteo)를 직접 호출한다. 서버 API는 없다.

- **기록에 남기는 날씨는 이것과 별개다.** 기록 생성 시 서버가 시작 좌표·시각으로 날씨를 조회해 `running_records.weather_code`(WMO 4677 코드)·`temperature`(섭씨)에 저장한다. 향후 컬러 `ADVERSITY` 판정에 쓸 관측값이라 클라이언트 신고값을 쓰지 않는다.
  - **이 조회는 시작 좌표를 외부 사업자에게 보낸다.** 제공자는 `OpenMeteo GmbH`(스위스, `api.open-meteo.com`)이며 요청 쿼리에 위도·경도와 시각이 담긴다. 개인위치정보의 국외 이전에 해당하므로 개인정보처리방침의 고지 대상이고, Google Play 데이터 보안에는 `정확한 위치 = 수집됨 + 공유됨`으로, App Store 개인정보 라벨에는 `정확한 위치`(앱 기능)로 신고한다. 제공자를 바꾸거나 다른 외부 API에 좌표를 보내게 되면 방침과 두 스토어의 신고를 함께 고쳐야 한다.
  - 무료 엔드포인트는 제공자 약관상 **비상업적 이용으로 제한된다** — 광고·구독 등 수익화를 붙이면 유료 전환이 필요하다.
- 날씨는 화면·API에 노출하지 않고 판정용 관측값으로 저장한다. `total_elevation_gain`은 `totalElevationGainMeters`로 응답한다.
- **조회에 실패해도 종료 처리를 막지 않는다.** 두 컬럼이 NOT NULL이라 비워 둘 수 없으므로, 서버가 정해진 횟수만큼 재시도하고 끝내 실패하면 기본값을 넣는다. 재시도 횟수와 기본값은 운영 설정이다. 한 시간짜리 러닝 기록이 외부 API 하나 때문에 통째로 날아가면 안 된다.
  - **기본값은 악조건이 아닌 쪽으로 고른다**(맑음·평상 기온). 실측이 아닌 값이 섞이는 건 감수하되, 향후 컬러 `ADVERSITY` 판정에서 **없던 악조건을 만들어내지는 않게** 하기 위해서다. 오차는 "악조건을 놓치는" 방향으로만 생긴다.

**이탈 페널티 판정**: 제재 대상 여부는 이탈 시점에 정해 `status`에 굳힌다. **모집 마감(`start_at - 오프셋`)을 지났고 이탈 시점 `current_player_count`가 2 이상**이면 `MATCHED_LEFT_PENALTY`, 둘 중 하나라도 아니면 `MATCHED_LEFT_NO_PENALTY`다(솔로 방 제외). **유예는 두지 않는다** — 마감 시각은 클라가 `closeAt`으로 이미 표시하고 있어 모르고 나가는 경우가 없다. 인원 조건이 붙는 이유는 혼자 남은 방을 나가는 데는 손해를 보는 상대가 없기 때문이다. **대기 취소(마감 전)는 이 판정에서 자연히 `_NO_PENALTY`가 되므로 분기가 따로 없다.**

**쿨다운 저장**: 근거는 DB(`status`)에 영구히 남기고, **"지금 막혀 있나"는 Redis 키의 존재로 판정한다** — 제재 이탈 시 `match:cooldown:{userId}`를 쿨다운 길이만큼 TTL로 걸고, 신청 시점에 그 키를 확인해 남아 있으면 `409 MATCH_COOLDOWN`으로 막는다(액세스 토큰 블랙리스트와 같은 구조). 만료 계산과 정리를 코드가 하지 않아도 되고 신청 경로에서 DB를 한 번 덜 친다. Redis가 유실되면 쿨다운이 풀리지만 20분짜리 소프트 제재라 감수한다 — 필요해지면 `status`가 남아 있으므로 DB 폴백을 얹을 수 있다.

- 네 값은 운영 설정으로 뺀다 — **모집 마감 오프셋**(마감 = `start_at - 오프셋`), **쿨다운**(확정 후 이탈·조기 종료를 따로 둔다), **조기 종료 제재 거리 비율**, **강제 종료 유예**(강제 종료 = `start_at + 유예`).
- **판정 결과를 저장하는 대가**: 거리 비율을 조정해도 이미 쌓인 row는 당시 기준으로 남는다. 쿨다운 길이는 제재를 거는 시점의 설정으로 TTL이 정해진다.
- **DB 폴백을 얹는다면 이탈 row의 `deleted_at`으로 잰다.** `deleted_at` 자체는 완주에도 찍히지만, 위 `status` 조건이 이탈만 걸러 낸다.

**개인 단위 진행 상태**: `running_players.status`가 갖는다. 러닝 중은 `RUNNING`, 목표 거리 도달은 `COMPLETED`, 조기 종료는 거리 비율에 따라 `RUNNING_LEFT_*`다(목표가 없는 솔로는 끝내면 `COMPLETED`). 아래 유효 러닝 판정을 통과한 트랙이면 상태 전환과 같은 트랜잭션에서 `running_records`를 만든다.

- **목표를 채우면 서버가 끝낸다.** 목표가 있는 방(매칭)은 좌표 배치로 목표를 채우면 `RUNNING_FINISH`를 기다리지 않고 종료를 확정하고 `RUNNING_FINISHED`를 보낸다. 사용자가 종료를 누르지 않아도 완주가 그 시점에 굳는다. 솔로는 목표가 없어 해당 없다.
  - **끝내기 전에 확정 거리로 다시 확인한다.** 러닝 중 누적 거리는 트랙 필터를 거치지 않아 확정 거리보다 크거나 같다. 누적이 목표에 닿으면 저장된 트랙을 필터·분석해 확정 거리를 내고, **확정 거리도 목표 이상일 때만** 끝낸다 — 누적만 보고 끝내면 확정 거리가 목표 직전으로 나와, 서버가 끊은 러닝이 조기 종료로 남는다.
  - 확정 거리가 목표 미만이면 **끝내지 않고 아무것도 보내지 않는다.** 사용자가 아무것도 하지 않았으니 알릴 것이 없다 — 러닝은 그대로 계속되고 다음 배치가 다시 확인한다.
- **화면으로는 다 뛰었는데 서버가 인정하지 않으면 종료를 미루고 남은 거리를 알린다.** 사용자가 종료를 누르면 클라는 화면 거리가 목표 이상일 때 `RUNNING_FINISH`(`forced=false`)를 보낸다. 서버 확정 거리가 목표에 못 미치면 확정하지 않고 본인에게 남은 거리(`RUNNING_GOAL_PENDING`)를 보내며, 클라는 "N m 더"를 보여주고 계속 뛰게 한다.
  - 그대로 확정하면 다 뛰었다고 믿는 사용자의 러닝이 조기 종료로 남는다 — 화면 거리는 오염 좌표까지 센 값이라 서버 확정 거리보다 길 수 있다.
  - 그래도 끝내려면 `forced=true`로 다시 보낸다. 클라가 "완주로 기록되지 않는다"를 한 번 확인받은 뒤다. 처음부터 화면 거리가 목표 미만이면 `forced=true`라 바로 확정한다.
  - 자동 종료와 강제 종료 시각에는 쓰지 않는다 — 사용자가 직접 끝내려는 순간에만 필요한 안내다.
  - **허용 오차를 두지 않는다.** 확정 거리가 목표 이상이어야 `COMPLETED`다 — 참가자가 같은 거리를 뛴다는 비교의 전제를 지키기 위해서다. 필터가 실제 이동을 깎은 몫(정지 1회당 최대 반경 이하)은 남은 거리 안내를 받아 더 뛰어 메운다.
  - **종료 경로와 무관하게 판정 규칙은 하나다.** 자동 종료·사용자 종료·강제 종료 모두 확정 거리로 판정한다. 목표 미만일 때 확정하지 않고 미루는 것은 자동 종료와 `forced=false` 사용자 종료뿐이다. 사용자 종료라도 남은 좌표까지 계산해 목표를 넘었으면 `COMPLETED`다.

**유효 러닝 판정**: 기록을 **만들지 말지**를 가르는 단일 문턱이다. 두 조건을 모두 만족해야 저장한다 — 거리·시간·경로를 **산출할 수 있고**(평균 페이스가 허용 범위 안이어야 한다), **최소 거리·최소 시간**을 넘겨야 한다. 몇십 초 뛰다 멈춘 러닝이 기록·통계·컬러 판정에 섞이는 것을 막기 위한 것이다.

- 두 값(**최소 거리**, **최소 시간**)도 운영 설정으로 뺀다. 현재 운영값은 **100m·60초**다.
- **미달이면 기록을 만들지 않는다.** 이탈 판정은 그대로 돌아 `running_players.status`는 `RUNNING_LEFT_*`로 남는다(목표 없는 솔로는 `COMPLETED`) — **기록 유무와 개인 종료 상태는 별개다.** 결과 조회도 기록 없는 참가자를 유지한다(erd 결과 조회 절).
- **판정은 저장 시점에 한 번 하고 되돌리지 않는다.** 임계값은 정책이라 바뀌지만 조정해도 이미 쌓인 row는 당시 기준으로 남는다(위 판정 결과를 저장하는 대가와 같다). 대신 저장된 기록은 전부 유효하므로 **유효 여부 컬럼을 두지 않고** 조회 쪽에서 다시 거르지 않는다.
- **저장된 기록의 쓰임에는 예외가 없다**: 본인 기록 목록·캘린더·러닝 후 대시보드·업적·컬러 획득 판정·피드 템플릿이 같은 집합을 본다. (프로필 요약의 수치 통계는 표시 자체가 제외됐다 — 되살려도 같은 집합이다) 단, 관리자가 숨긴 방([MVP 제외])의 기록은 기록 목록과 대시보드에서 함께 빠진다.

**평균 페이스 갱신**: 기록을 저장한 러닝마다 `user_onboardings.avg_pace`를 최근 기록 **5건**으로 다시 낸다. 온보딩에서 받는 값은 자기 신고라 실제와 어긋나기 쉬운데, 매칭이 그 값으로 상대를 고르기 때문이다. 기록을 만들지 못한 종료(위 유효 러닝 판정 미달)는 표본이 늘지 않았으므로 갱신하지 않는다.

- **5건이 다 차야 갈아탄다.** 미만이면 갱신하지 않고 온보딩 입력값을 유지한다 — 한두 번의 실측으로 덮으면 컨디션 나쁜 하루가 그대로 실력으로 굳는다. 자기 신고값이 정확하진 않아도 "평소"에는 더 가깝다.
- **기록별 페이스의 산술 평균이 아니라 5건의 거리 합 ÷ 시간 합이다.** 산술 평균은 300m 러닝과 10km 러닝을 같은 무게로 세서 짧은 기록이 값을 끌고 간다.
- **표본은 이동 창(rolling)이다.** 최신순 5건이라 6번째 러닝을 끝내면 가장 오래된 기록이 빠진다. 조기 종료 기록(`RUNNING_LEFT_*`)도 저장됐다면 표본에 넣는다 — 실제로 뛴 데이터이고, 거리 가중이라 짧게 그만둔 기록은 비중이 저절로 작아진다.
- **범위가 좁아지는 구간에서는 경계로 맞춘다.** 기록 페이스는 걷기 구간까지 담아 120~3600초/km인데 온보딩 페이스는 120~1800초/km다. 계산값이 넘치면 갱신을 포기하지 않고 1800으로 적는다.
- **매칭 쪽에 갱신 코드가 없는 것이 정상이다.** 매칭 신청·솔로 방 개설은 `user_onboardings.avg_pace`를 읽어 `running_players.avg_pace`에 복사할 뿐이고, 그 복사본은 신청 시점 스냅샷으로 굳는다. 활성 신청이 하나뿐이라 대기 중에 페이스가 바뀌는 경로가 없다 — **직전 러닝까지 반영된 값으로 다음 매칭을 잡는다**가 실제 동작이다.

**`STARTED` 종료 전환**: 각자의 `RUNNING_START`로 `RUNNING`이 된 참가자가 모두 종료 상태(`COMPLETED`·`RUNNING_LEFT_*`)가 되고 기록 확정이 끝나면 즉시 전환한다. 강제 종료 시각에는 남은 참가자를 마지막 수신 데이터로 종료 처리한 뒤 전환한다.

- **행선지는 유효 기록 유무로 갈린다** — 위 유효 러닝 판정을 통과해 저장된 기록이 하나라도 있으면 `FINISHED`, 하나도 없으면 `CANCELLED`다. 시작만 눌렀거나 몇십 미터 만에 그만둔 방을 완료로 남기지 않기 위한 것이다. 방 상태는 기록 확정이 끝난 시점 값으로 굳는다.
- **유효 기록이 있는 방은 `CANCELLED`로 닫지 않는다.** `CANCELLED`는 terminal이라 `FINISHED`에 도달할 수 없고, 그대로 닫으면 기록 확정과 결과 조회 경로가 함께 끊긴다.
- **`CANCELLED`로 닫힌 방에는 기록이 없다.** 저장 문턱과 방 상태 문턱이 같은 판정을 쓰므로 "취소된 방에 매달린 기록"은 생기지 않는다. `running_records.running_room_id`가 NOT NULL인 것과 앞뒤가 맞는다.

**강제 종료**: `start_at + 유예`(운영값)에 방마다 걸어둔 예약이 깨어, 그때까지 닫히지 않은 방과 남은 참가자를 서버가 닫는다. 앱이 죽거나 네트워크가 끊겨 종료 메시지가 영영 오지 않으면 방이 열린 채로 남고, 그 참가자의 신청도 활성으로 남아 다음 러닝이 영영 막히기 때문이다. 방을 주기적으로 훑지 않고 그 시각에만 깨운다.

- **남은 참가자를 상태로 갈라 각자의 정상 경로에 태운다.** `RUNNING`이면 위 러닝 종료 판정을 그대로 적용하고(마지막 수신 좌표까지로 지표를 내며, 산출할 수 없으면 실제 거리를 0으로 본다), 한 번도 채널에 붙지 않아 `JOINED`로 남은 참가자는 **확정 후 이탈로 판정한다**.
  - **미출석을 확정 후 이탈과 같게 다루는 이유**는 함께 뛰기로 한 사람을 곤란하게 만든 결과가 같아서다. 나가기를 누르지 않았을 뿐 상대는 똑같이 기다렸다. 그래서 상태도 `MATCHED_LEFT_*`이고, 쿨다운도 조기 종료 쪽이 아니라 이탈 쪽 값을 쓴다.
  - **제재 면제도 확정 후 이탈과 같은 기준이다** — `current_player_count`(취소·탈퇴한 미출석자는 빠진 값)가 1이면 곤란해진 상대가 없어 `_NO_PENALTY`다. 마감 시각 조건은 이미 한참 지나 판정에서 빠진다.
  - **판정 기준이 되는 인원은 순회 전에 굳힌다.** 처리하면서 인원을 줄이면 순회 순서에 따라 뒤쪽 참가자만 1인 방으로 보여 면제받는다.
- **방은 위 `STARTED` 종료 전환과 같은 규칙으로 닫는다** — 저장된 유효 기록이 하나라도 있으면 `FINISHED`, 없으면 `CANCELLED`다. 아무도 붙지 않은 방은 기록이 없으니 `CANCELLED`다.
- **이미 닫힌 방에도 남은 참가자가 있을 수 있다.** 뛴 사람이 전원 정상 종료하면 방은 그 시점에 닫히는데, 미출석자는 `RUNNING`이 아니라 그 판정에 세어지지 않아 `JOINED`인 채로 남는다. 그래서 강제 종료는 방이 이미 닫혔는지와 무관하게 남은 참가자를 먼저 닫는다. **이 경우는 예약 시각을 기다리지 않는다** — 방을 닫은 트랜잭션이 커밋되면 바로 강제 종료를 돌린다. 기다리면 그동안 미출석자는 할 일이 없는데도 활성 신청에 막혀 다음 매칭·솔로를 열 수 없다. 즉시 실행이 실패해도 예약이 그대로 남아 다시 닫는다.
- **매칭 방에만 건다.** 솔로 방은 서버가 닫지 않는다 — 위 솔로 절의 복구 경로를 따른다.
- **유예는 러닝 트랙 보관 기간보다 짧아야 한다.** 트랙은 좌표를 받을 때마다 만료가 갱신되는 임시 저장이라, 유예가 보관 기간과 같으면 발화가 조금만 밀려도 트랙이 먼저 사라져 실제로 뛴 사람이 기록 없이 제재를 받는다.

**초대 러닝 생명주기**: 초대 방은 **모집 단계와 제재만 매칭과 다르다.** 방이 열리는 방식(사용자가 직접 연다)과 사람이 들어오는 방식(초대 수락)이 다르고 제재가 없을 뿐, 모집 마감부터는 매칭 방과 같은 경로를 탄다.

- **방 생성**: `running_rooms`를 `type='INVITE'`, `status='MATCHING'`, `max_player_count=4`, `current_player_count=1`로 만들고, 입력받은 시작 시각·목표 거리를 `start_at`·`target_distance`에 넣는다. 만든 사람의 `running_players(status='JOINED')`와 배정 세션도 함께 만든다. 예약(`MATCH_CLOSE`·`RUNNING_REMINDER`·`RUNNING_READY`·`RUNNING_START`·`RUNNING_FORCE_FINISH`)도 매칭 방과 같은 종류로 건다.
  - **모집 마감 = `start_at - 초대 마감 오프셋`(운영 설정 `invite.close-offset`, 현재 1분)이다.** 매칭의 마감 오프셋(10분)을 쓰지 않는다 — 매칭은 모르는 사람끼리 인원을 미리 굳혀야 하지만, 초대는 친구끼리라 시작 직전까지 받아 주는 게 낫다. 다만 시작 통지(`RUNNING_READY`, 매칭과 같은 10초 전)보다는 앞서야 한다 — 통지 뒤에 들어온 사람은 카운트다운 기준을 받지 못한다. 그래서 오프셋은 시작 통지 리드타임보다 커야 한다(설정 검증).
  - 클라에 내려가는 `closeAt`도 이 값이다.
  - 매칭 후보 스캔(`type='MATCH'`)과 슬롯별 대기 인원 집계에 잡히지 않는다 — 잡히면 모르는 사람이 배정된다.
- **초대는 신청이 아니다** — 초대받은 사람의 `running_players` 행을 만들지 않고 `running_room_invitations`에 따로 둔다. 활성 신청은 `running_players.deleted_at IS NULL` 하나로 판정하므로, 초대만 받아도 신청 행이 생기면 초대 여러 개가 쌓인 사람이 매칭도 다른 초대도 못 하게 된다. 그래서 `running_players.status`에 초대 상태를 두지 않는다.
- **초대 조건**: 보내는 사람이 그 방의 현재 참가자이고(`is_connected=true`), 방이 `MATCHING`이며 모집 마감 전이고, 받는 사람이 친구(`FRIEND`)여야 한다.
  - **한 번에 한 명이다** — 방 행을 먼저 잠가 같은 방의 초대가 한 줄로 선다.
  - **못 보내는 경우는 건너뛰지 않고 이유를 에러로 알린다**(api-spec 4-2 에러 표): 친구가 아님, 이미 이 방에 있음, 다른 방에서 매칭 중, 러닝 중(솔로 방을 열고 아직 시작 전인 경우 포함), 이 사람에게 보낸 횟수가 상한(`invite.max-invite-count`, 현재 5)에 닿음.
  - **대기 중인 초대에도 다시 보낼 수 있다** — 상태는 `PENDING` 그대로이고 보낸 사람의 횟수(`invite_count`)만 오른다. 다른 참가자가 같은 친구를 부르면 그 사람의 행이 하나 더 생기고, 상태는 받는 사람 기준으로 늘 같다.
  - 초대받은 사람은 매칭·솔로를 그대로 할 수 있다 — 초대는 신청이 아니다. 그 사이 매칭을 시작했으면 수락이 막힌다.
  - **친구 여부는 초대 시점에만 본다.** 초대 뒤에 친구를 끊어도 대기 중인 초대는 유효하다.
- **수락**: 방을 잠그고 다시 본다 — `MATCHING`이고 마감 전이며 자리가 남았고(`current_player_count < max_player_count`), 받는 사람에게 활성 신청이 없어야 한다. 통과하면 매칭 참가와 같게 `running_players(JOINED)`·배정 세션을 만들고 인원·방 평균 페이스를 갱신한 뒤 초대를 `ACCEPTED`로 바꾼다. **먼저 수락한 순서로 자리가 찬다** — 방 행 잠금이 그 순서를 정한다.
  - 자리가 차서 거절된 초대는 `PENDING`으로 남는다 — 누가 나가면 다시 수락할 수 있다.
  - 매칭 쿨다운 중에도 수락할 수 있다(초대 방 생성과 같다).
- **거절**: `DECLINED`로 바꾸고 이력으로 남긴다 — 방 화면에는 보이지 않지만, 다시 초대할 때 보낸 횟수를 이어서 세야 해서 친구 요청 거절처럼 지우지 않는다.
- **나가기**: 수락해 들어온 사람이 방을 나가면 초대를 `ACCEPTED` → `LEFT`로 바꾼다 — `ACCEPTED`는 "지금 방에 있음"만 뜻한다.
- **다시 초대**: 거절(`DECLINED`)했거나 나간(`LEFT`) 친구는 그 받는 사람의 행을 모두 `PENDING`으로 되살린다. 방에 있는(`ACCEPTED`) 친구는 "이미 방에 들어와 있는 친구"로 거절된다. 보낸 횟수는 되살려도 이어서 센다.
- **수락·거절·나가기는 받는 사람 기준이다** — 방을 잠그고 그 방의 그 받는 사람 행(보낸 사람별)을 모두 함께 바꾼다. 누구의 초대로 수락하든 결과가 같다.
- **만료**: 모집 마감 확정(`MATCH_CLOSE`)이나 방 취소(`CANCELLED`)와 **같은 트랜잭션에서** 남은 `PENDING`을 `EXPIRED`로 바꾼다. 마감 뒤에 받아 주면 시작 통지와 겹치거나 그 뒤에 들어와 카운트다운을 받지 못한 채 출발을 맞을 수 있다.
- **방에 남은 사람이 없으면** 매칭 방과 같이 `CANCELLED`로 닫는다. 만든 사람이 나가도 방은 유지된다 — 방장이 없다.
- **나가기는 매칭과 같고 제재는 없다.** 나가기는 `POST /match-rooms/leave`를 그대로 쓴다. 초대 방에서는 시점·인원과 무관하게 이탈은 `MATCHED_LEFT_NO_PENALTY`, 조기 종료는 `RUNNING_LEFT_NO_PENALTY`(목표를 채우면 `COMPLETED`), 미출석 강제 종료도 `_NO_PENALTY`로 남기고 쿨다운을 걸지 않는다. 제재는 모르는 사람끼리 모이는 매칭에서 약속을 지키게 하려는 장치라, 서로 아는 사이인 초대 방에는 필요 없다.
- **방 상태 이벤트는 초대 방 전용이다** — 스트림(`/match-rooms/stream`)은 같지만, 연결 직후 스냅샷은 `INVITE_ROOM_ENTRANCE`(방 정보 + 시작까지 남은 시간 `startsInMs`), 그 뒤 변화는 `INVITE_ROOM_UPDATED`가 나른다. 초대 현황도 방 정보(`RoomInfo`)에 실린다.
  - 매칭 방의 `MATCH_STARTED`·`MATCH_ROOM_UPDATED`는 보내지 않는다. 초대 방의 마감은 "더 이상 초대받지 않는다"일 뿐 매칭 성사가 아니라 확정 연출이 없다. 마감은 `INVITE_ROOM_UPDATED`(초대 만료 반영)로만 알리고, 카운트다운은 매칭과 같이 `RUNNING_READY`로 들어간다.

**업적**: 저장된 기록에서 **조회할 때 계산하는 파생값이다.** 획득 테이블을 두지 않는다 — 달성 시각·달성 알림이 없어 굳혀 둘 이유가 없고, 기준값을 바꾸면 바로 반영된다.

| 업적 | 판정 값 | 출처 |
|---|---|---|
| 누적 거리 | 기록의 `total_distance` 합 | `running_records` — 솔로·매칭·초대 전부 |
| 페이스 | 기록 `avg_pace`의 최솟값(빠를수록 작다) | `running_records` 중 `total_distance`가 페이스 업적 최소 거리(운영값) 이상인 것 — 짧게 전력 질주한 기록이 최고 페이스가 되지 않게 한다 |
| 최고 콤보 | `combo_count`의 최댓값 | `running_combos` 중 `first_user_id`·`second_user_id` 어느 쪽이든 본인인 행 |
| 매칭 러닝 횟수 | 기록 수 | `running_records` 중 방이 `type='MATCH'`인 것 — 솔로·초대는 세지 않는다 |

- **단계 기준값은 운영 설정이다** — 업적마다 기준값 목록을 두고, 판정 값이 넘은 기준값 개수가 단계다(페이스는 기준값 이하일 때 넘은 것으로 본다). 단계 수를 명세에 박지 않는다 — 응답이 최대 단계를 함께 내린다.
- 기록은 유효 러닝 판정을 통과한 것뿐이라 다시 거르지 않는다(위 유효 러닝 판정).
- **콤보는 방이 `FINISHED`로 닫힌 뒤에 쌓인다** — 러닝 중이거나 막 끝난 방의 콤보는 아직 반영되지 않는다.
- 기준값을 올리면 이미 켜졌던 단계가 꺼질 수 있다. 굳혀 두지 않는 대가로 받아들인다.

**추천 친구**: 조회할 때마다 계산하고 저장하지 않는다. 두 갈래를 차례로 채운다.

1. **함께 뛴 사람** — 본인이 러닝 단계에 들어간(`RUNNING`·`COMPLETED`·`RUNNING_LEFT_*`) **가장 최근 매칭 방(`type='MATCH'`) 하나**에서 함께 러닝 단계에 들어간 사람. 솔로·초대 방은 보지 않는다 — 마지막 러닝이 솔로·초대여도 그 전의 마지막 매칭 방을 본다. 초대 방은 서로 아는 사람끼리 모여 추천할 거리가 아니다.
2. **페이스가 비슷한 사람** — `user_onboardings.avg_pace` 차이가 운영값 이내인 사람. 차이가 작은 순서다.

- 1을 먼저 채우고 남은 자리를 2로 채운다. 총 인원은 운영값이고 페이지네이션은 없다. 두 갈래에 모두 걸리면 1로 한 번만 낸다.
- **제외**: 본인, 이미 친구인 사람, 어느 방향이든 요청이 대기 중인 사람, 온보딩 전인 사람. 결과는 모두 친구 요청을 보낼 수 있는 사람이다.
- 항목마다 추천 이유(함께 뛰었음 / 페이스가 비슷함)를 싣는다. 상대의 페이스 값 자체는 싣지 않는다.
- 추천 숨기기는 두지 않는다.

**인앱 알림 저장**: `user_notifications`에 받는 사람 기준으로 쌓는다. **알림을 만드는 동작과 같은 트랜잭션에서 넣는다** — 요청은 됐는데 알림이 없거나, 알림만 남는 상태를 만들지 않는다.

- 친구 요청 → 받는 사람에게 `FRIEND_REQUESTED` / 수락(서로 요청해 바로 성립한 경우 포함) → 요청했던 사람에게 `FRIEND_ACCEPTED` / 러닝 초대(다시 초대 포함) → 받는 사람에게 `RUNNING_INVITED`.
- **알림은 사건의 기록이라 원 상태가 바뀌어도 지우지 않는다.** 요청이 취소되거나 초대가 만료돼도 행은 남고, 화면에 보일 현재 상태는 조회할 때 `user_relationships`·`running_room_invitations`에서 읽어 붙인다.
- 보관 기간이 지난 알림은 조회에서 빠진다. 정리 주기는 운영에서 정한다.

**회원탈퇴 시 연관 데이터 처리** (테이블별):

- 탈퇴를 막지 않는다. 삭제 전에 대기 중이면 취소하고 확정 방이면 이탈한다. 방이 시작됐는데 한 번도 붙지 않았으면 강제 종료와 같은 기준의 이탈로 닫는다. 러닝 중이면 마지막 수신 데이터로 일반 종료 판정을 적용해 생성 가능한 기록을 확정한다. 시작 전 방이거나 시작 후 한 번도 붙지 않았으면 인원을 갱신하고 남은 참가자에게 알린 뒤 계정을 삭제한다 — 상대가 탈퇴해 혼자 남은 사람이 이어서 나가거나 강제 종료될 때 면제되도록 시작 후 취소와 같게 둔다.
- **유지**: `feeds`, `comments`, `running_records`(+`running_splits`) — 같은 방 참가자의 기록 비교를 위해 탈퇴해도 남긴다. `user_id`는 DB FK 없이 애플리케이션에서 처리하며, 응답의 탈퇴 사용자는 `{ userId, nickname: "탈퇴한 사용자", profileImageUrl: null, isDeleted: true }`로 대체한다.
- **유지 (카운트 재계산 안 함)**: `feed_likes`, `comment_likes` — 탈퇴자가 누른 좋아요는 남겨두고 `like_count` 그대로(인스타그램 방식).
- **즉시 삭제**: `user_relationships`(양쪽)·`user_notifications`(받은 쪽)·`running_room_invitations`(받은 쪽)와 개인 데이터 테이블(`user_onboardings`, `user_devices`, `oauth_users`, `user_colors`). 탈퇴자가 일으킨 알림(`payload`의 유저 ID)과 탈퇴자가 보낸 초대는 남긴다 — 방장이 없어 초대는 그대로 유효하고, 보낸 사람은 탈퇴 유저 형식으로 보여준다. 온보딩 값과 로그인 수단은 지우기 전에 `delete_users`로 옮긴다 — **닉네임 중복 검사는 `delete_users`를 보지 않으므로 탈퇴 즉시 그 닉네임을 다른 사람이 쓸 수 있다.**
- **러닝 참가 이력 유지**: `running_players`와 `running_room_sessions`는 상태와 무관하게 전부 유지한다. 시작 전 신청도 지우지 않고 일반 취소처럼 닫으며(사유는 취소와 같게 남기고 쿨다운은 걸지 않는다), 시작한 방은 기록이 없는 참가자도 과거 결과에 남는다. 신청 이력은 통계에 쓴다. 사용자 정보는 탈퇴 유저 형식으로 대체한다.
- 친구 수는 집계 컬럼이 아니라 `user_relationships` COUNT라 **재계산이 필요 없다** — 탈퇴자의 행이 지워지면 수도 함께 줄어든다. (`feed_likes`는 row를 유지해 카운트도 유지 — 기준이 다름.)
- **DB 밖도 함께 지운다**: Redis의 리프레시 토큰은 즉시 삭제하고, 지금 쓰던 액세스 토큰은 블랙리스트에 올린다 — 리프레시 토큰을 남기면 탈퇴 후에도 재발급되고, 액세스 토큰은 남은 유효 기간 동안 그대로 통과한다. S3 프로필 사진(`profiles/{userId}/`)과 배경 사진(`backgrounds/{userId}/`)은 **프리픽스 전체**를 90일 뒤 삭제한다(사진을 바꿀 때마다 객체가 쌓여 `profile_image_key`·`background_image_key` 하나로는 과거 것이 남는다). **GPS 원본 트랙은 유지** — `route_polyline`이 DB에 남아 경로는 어차피 보관되고 재계산에 쓴다.
- **카카오 연동 해제**: `oauth_users`를 지우기 **전에** `provider_id`를 확보하고 커밋 후 unlink를 호출한다 — 지운 뒤에는 대상을 특정할 수 없다.
  - **구글·애플은 해제하지 않는다** — 취소 엔드포인트가 사용자 토큰을 필수로 받는데 우리는 저장하지 않고, 카카오 어드민 키 같은 대체 수단이 없다. 사용자가 구글 계정 설정·애플 ID 설정에서 직접 해제해야 한다.
- **90일 뒤**: `delete_users`의 `email`·`nickname`을 `NULL`로 갱신하고 S3 프로필·배경 사진 프리픽스를 삭제한다 — 신고 대응 목적이 끝나는 시점이다.

**삭제 처리 방식** (리소스별로 다름 — API 설계 시 각각 구분해서 반영):

- **`users`**: 하드delete + 아카이브 — 실제 DELETE 전에 `delete_users`에 스냅샷 먼저 저장(신고 대응·통계 용도, 복구 기능 없음).
- **`feeds`**: `deleted_at` 소프트delete(복구 가능·조회 제외 처리).
- **`comments`**: 답글 유무로 분기(레딧 방식, 두 경우 모두 `delete_comments` 스냅샷 먼저 저장) — 답글 없으면 하드delete, 답글 있으면 톰스톤(row 유지 + 내용 비움 + `deleted_at` 기록, "삭제된 댓글입니다" 자리표시로 노출하고 답글 스레드 유지).
