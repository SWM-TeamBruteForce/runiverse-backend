## AOF 적용 후 재검증 (run 18)

run 16과 같은 시나리오(400명, 5분쯤 `systemctl kill -s KILL redis-server`)를 Redis에 AOF(`appendonly yes`, `appendfsync everysec`, `CONFIG REWRITE`로 설정 파일 저장)를 켠 뒤 다시 돌렸다.
테스트 RDS를 지운 뒤라 DB는 Redis와 같은 서버(.198)의 테스트 PostgreSQL을 썼다 — 지연 수치는 run 16과 조건이 달라 비교하지 않는다.

| 항목 | run 16 (AOF 없음) | run 18 (AOF) |
|---|---|---|
| 복구 | RDB 스냅샷만 읽음 | `DB loaded from base file … / incr file … / append only file: 0.346 seconds` |
| **좌표 공백(≥10초)이 생긴 러너** | **400 / 400** | **13 / 400** |
| 사용자 에러 | 0 | 16 (`RUNNING_TRACK_UNAVAILABLE`, 앱 로그 `트랙 저장 실패: Redis 오류` 16건) |
| 종료 완료 | 400/400 | 400/400 |

- 13명의 공백은 Redis가 잃은 데이터가 아니다. AOF를 읽는 0.35초 동안 Redis가 요청을 거절했고, 그 순간 보낸 배치 16개가 저장되지 않았다. AOF 손실은 최대 1초라 10초 공백을 만들 수 없다
- 실제 앱은 거절된 배치를 로컬 트랙에서 다시 보내므로 이 공백은 메워진다. k6 스크립트는 거절된 배치를 다시 보내지 않아 공백이 남았다
- 결론: **AOF로 "조용한 1분치 손실"이 사라졌다.** 남는 것은 재시작 순간 거절된 요청이며, 에러로 드러나고 클라이언트 재전송으로 복구된다

## 결론

0. **여유** — 사용자 체감은 1,000명까지 같았지만, DB 프로필은 1,000명에서 커넥션 풀(10)을 다 썼다(Redis 프로필은 3개 안팎). DB 배치 최대 654ms가 그 순간이다. 1,000명을 넘기면 DB 프로필이 커넥션 대기로 먼저 무너지고, 같은 풀을 쓰는 종료·기록 트랜잭션(run 14의 고갈)도 더 일찍 막힌다.
1. **성능** — 러너 1,000명(초당 배치 약 100건)까지 DB도 Redis와 사용자 체감이 거의 같다. 배치 왕복 중앙값만 약 4ms 늘었다(배치당 상태 접근 9번의 RDS 왕복). 종료는 S3 업로드·기록 저장이 지배해 저장소 차이가 묻힌다.
2. **몰림** — 동시 시작으로 배치가 한순간에 몰릴 때 Redis의 꼬리 지연(p95 377ms)이 DB(43ms)보다 컸다. 앱의 Redis 연결 하나 + Redis 단일 스레드(Lua)에 줄을 서고, DB는 커넥션 10개로 병렬 처리하기 때문으로 본다 — 1회 측정이라 재현이 필요하다.
3. **안정성** — EC2 Redis는 프로세스가 죽어도 0.1초 만에 자동 복구돼 사용자 영향은 없었다. 대신 AOF가 꺼져 있어 마지막 RDB 스냅샷(약 1분) 이후의 러닝 상태가 **에러 없이 조용히** 사라졌다(400/400명 좌표 공백). AOF를 켜고 같은 장애를 내자 조용한 손실은 사라졌다(run 18).
4. **진짜 병목은 저장소가 아니다** — 한 순간 400명 종료(run 14)는 Redis 프로필에서도 68% 실패했다. 종료 트랜잭션이 커넥션(10개)을 쥔 채 S3 업로드·날씨 조회를 하는 구조가 원인이다.
5. **비용** — pub/sub 때문에 Redis EC2는 어느 쪽이든 남는다. 이 규모에서는 테스트 RDS(운영과 같은 등급)가 증설 없이 상태 저장까지 받아냈으므로, 상태를 RDS로 옮겨도 **추가 비용은 거의 없고 Redis 비용도 줄지 않는다.** 선택 기준은 비용이 아니라 데이터 손실 위험과 운영 부담이다.

## 권장

- 단기: EC2 Redis에 `appendonly yes` + `appendfsync everysec` — 손실을 1분에서 1초 이내로 줄이는 가장 싼 조치. **run 18로 검증 완료**(공백 러너 400 → 13, 남은 13은 재시작 순간 거절된 요청)
- 단기: 종료 경로에서 S3 업로드·날씨 조회를 트랜잭션 밖으로 — 동시 종료 실패(run 14)의 원인 제거
- 중기: 러닝 상태를 RDS로 옮기는 안은 1,000명까지는 성능상 가능하지만 커넥션 여유가 사라진다. 옮긴다면 커넥션 풀 확장(과 RDS 최대 커넥션·메모리), RDS CPU·IOPS를 함께 재고 1,000명 이상 단계를 다시 잰다
- 지금 구조(Redis 상태 + AOF)를 유지하는 쪽이 여유·비용 면에서 낫다 — 남는 위험(조용한 손실)은 AOF로 대부분 막힌다

## 한계

- 각 시나리오 1회 측정 — 중앙값을 낼 만큼 반복하지 못했다
- Redis 1회차(11~17)는 배포 이미지, DB는 실험 이미지 — 같은 코드 기준이지만 빌드가 다르다
- RDS CPU·IOPS(CloudWatch)와 Performance Insights는 수집하지 않았다
- 한 순간 400명 종료는 DB 프로필로 재지 않았다
- 가짜 트랙이 직선이라 좌표 손실이 거리 손실로 드러나지 않았다

## 메모

- run 11(100명)이 run 12(400명)보다 느렸다 — 앱 재기동 뒤 첫 본 측정이라 JVM 워밍업 영향으로 본다. 2·3회차에서는 측정 전 워밍업 회차를 따로 두고 버린다.
- run 14는 설계 실수로 동시 시작 + 동시 종료가 됐다. 시작은 통과(왕복 37ms → 941ms), **400명 동시 종료는 68%가 실패**(30초 무응답 271, INTERNAL_SERVER_ERROR 95). 종료 한 건이 트랜잭션 안에서 S3 동기 업로드까지 하므로 커넥션 풀(10) 고갈로 추정 — 로그·커넥션 지표로 확인 필요. 이후 start-storm은 종료를 2분에 퍼뜨린다.
- run 14 서버 지표(Grafana, 동시 종료 시점 19:08:40 KST 전후):
  - 커넥션 active 10/10, pending 최대 24. 획득 대기·사용 시간 최댓값 약 30초(획득 제한 30초에 걸림)
  - CPU 프로세스 74%·서버 97%까지 치솟음. 힙은 최대 약 300MiB/460MiB, GC 정지 최대 3ms — 메모리·GC는 원인이 아니다
  - 약 35초 동안 모든 지표가 비었다 — 앱이 Prometheus 수집 요청에도 응답하지 못했다
  - 같은 구간 Redis 상태 접근 실패 0건. p50 1~2ms → 동시 종료 때 최대 67ms, p99는 동시 배치 몰림마다 100~330ms
  - 결론: 원인은 Redis가 아니라 종료 트랜잭션이 커넥션을 쥔 채 S3 업로드·날씨 조회·트랙 분석을 하는 구조. 같은 방 행 잠금을 기다리는 트랜잭션도 커넥션을 쥐고 기다린다
- run 17(동시 시작, 종료 분산)은 전원 성공. 같은 400명인 run 12(시작 60초 분산)와 비교하면:
  - 시작 왕복 med 49ms → **1,090ms**, p95 81ms → 2,140ms. 핸드셰이크도 med 7ms → 463ms
  - 배치 왕복 med는 같고(6~7ms) p95가 23ms → **377ms** — 같은 초에 시작해 10초마다 400개 배치가 한꺼번에 들어오는 몰림이 꼬리 지연을 만든다
  - 종료 왕복은 더 빠르다(med 82ms) — 러닝이 5분이라 트랙이 짧고, 종료가 2분에 퍼졌다
- run 15(400명이 1분 안에 종료, 초당 약 7건)는 전원 성공, 종료 med 188ms·p95 326ms. run 14(400명이 같은 순간)는 68% 실패 — 같은 인원이라도 **몰리는 밀도**가 갈랐다. Redis 프로필의 안전 구간은 "1분에 400건"과 "한 순간 400건" 사이에 있다.
- run 16(Redis 장애): 11:20:04 UTC에 `systemctl kill -s KILL redis-server` → systemd가 0.1초 뒤 재시작(`Restart=always`), 마지막 RDB 스냅샷(약 1분 주기, AOF 꺼짐)을 읽어 복구.
  - **사용자 체감은 거의 없다** — 에러 0, 끊김 0, 종료 400/400. 배치 왕복 최대만 607ms로 튐. 앱 로그의 Redis 연결 오류 3건, 재시작 순간 상태 접근 지연 WARN이 몰림
  - **데이터는 조용히 잃었다** — 종료 시 좌표 공백(`gapEdgeCount ≥ 1`)이 있는 러너가 run 12는 0/400, **run 16은 400/400**. 스냅샷 이후의 좌표가 모든 러너에서 사라졌다
  - 기록 거리는 run 12와 똑같았다(평균 1,704m) — 가짜 트랙이 직선이라 공백을 직선으로 이어도 거리가 같기 때문이다. 곡선을 달리는 실제 사용자는 같은 공백이 거리 손실로 나타난다(테스트 설계의 한계)
  - 콤보는 14,932 → 14,774(약 1% 감소) — 콤보 상태 일부 손실로 보이나 오차 범위와 겹친다
  - 결론: EC2 직접 운영 Redis의 위험은 "멈춤"보다 "AOF 없이 1분치 상태가 조용히 사라지는 것"이다. 에러가 나지 않아 운영 중에는 알아차리기 어렵다
- 1,000명에서도 배치 왕복이 400명과 거의 같다(med 7ms, p95 27ms). 러너 1,000명 = 초당 배치 약 100건이라 처리량으로는 아직 여유 구간이다. 한계는 이보다 위에 있다.
